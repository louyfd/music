## 0. 一句话现状

工程主线是「**基于 FPGA 的实时多音色合成电子乐器引擎**」（全国大学生竞赛选题二）。
截至交接时：**V29 ~ V45 已归档**。★ **当前可用版本是 `V45_节拍器`**
（V39 的 bitstream 有 bug，别烧）。V36 = 立体声，V37 = 逐音八度，
V38 = 修起音噗声（+ 一版被回滚的蓝牙误触发修复），V39 = 回滚门控 +
分块/超时修复（**超时阈值设错，播放会乱**），V40 = 把阈值从 6.24ms 改成 500ms，
**V41 = LED 演奏指引接入 + 顺手把 CLKOUT1 的历史遗留临界路径治好了**
（CLKOUT1 从 50.007MHz 的刀刃变成 58.046MHz，余量 16%）。
★ **综合/布线从 V37 起越来越慢**（V36 7~8 分钟 → V40 28.8 分钟，
V41 约 25~30 分钟），见第 5 节坑 13 与待办。
★★ **V38/V39 两次踩坑的教训先看第 5 节坑 20 和 23**：
  一个"用状态位门控用户操作"、一个"兜底超时没按真实时间尺度定" ——
  都是没算清改动的实际影响范围。**V40 起加任何东西都要先问"它会不会卡住/
  阈值够不够大"。**

## 1. 工程位置与关键事实

```
工程根: D:\CODE\FPGA_Gowin\Gowin\Gowin_V1.9.11.03_Education_x64\IDE\bin\Documents\60k\music_player\music

工具  : Gowin V1.9.11.03 Education，gw_sh.exe（命令行）
```

**时钟树**（别乱动）：
- `clk_50m` = 板上 22 脚 50MHz（按键/TTP229/效果寄存器域）
- PLL `MDIV=14` → VCO 700MHz → `CLKOUT0 /56` = **clk_audio 12.5MHz**（合成/包络/效果）
- `CLKOUT1 /14` = **clk_50m_ext 50MHz**（UART + LCD）
- 采样率 = `12.5MHz / 256 = 48828 Hz`（`FRAME_DIV`）
- UART：`BAUD_DIV 5208 @50MHz` = 9600 8N1（蓝牙模块固定这个）

**音域/键号**：36 键 = MIDI **45..80（A2..G#5）**。
★ **键号是 TTP229 的"接线顺序"，不是音高顺序**：`键号 = PERM[(MIDI-45) mod 12] + 12*⌊(MIDI-45)/12⌋`，
`PERM = [5,0,6,1,7,8,2,9,3,10,4,11]`。锚点：键5=A2、键13=C4、键29=A4、键35=G#5。

**主要文件**：
| 文件 | 干什么 |
|---|---|
| `src/top.v` | **全部合成**：36 声部（相位累加器 + 常数频率字 + ADSR）、谐波混合、滑音/移调、效果器（颤音/合唱/延迟/混响）、KS 吉他（`ks_string` 模块在**文件末尾**，不单独成文件）、LCD 例化 |
| `src/uart_packet_echo.v` | 协议接收/Echo、乐谱播放器（`slot_mask`/`slot_dur`）、录音回传、效果/音色/映射/八度偏移写口 |
| `src/lcd_master.v` | ST7789 320×240：清屏、频谱、波形、**李萨如**、数字显示 |
| `src/ttp229_reader.v` | 3 片 TTP229（36 键）+ 16 键按钮板 |
| `src/ads1115_ctrl.v` `uart_tx_ads.v` | 摇杆/采集（I2C，**里面的 I2C PHY 可以复用去驱动 LED 芯片**） |
| `src/led_guide.v` | ★ V41：36 颗 LED 的演奏指引（IS31FL3236A，**第二路 I2C**），整个跑在 `clk_audio` 域 |
| `src/i2c_master.v` | ★ V41：从独立工程 `LEDs` 逐字节复制过来的 I2C 主机（只做"写一个寄存器"） |
| `src/sine_rom.v` `sine_table.mi` | **单周期正弦表**（不是音频样本，合规关键） |

1. **两个 always 块驱动同一个 reg → EX2000**。加寄存器时先把"谁拥有它"想清楚
   （`fx_req`、`fx_tgl`、`oct_cur` 都踩过）。
2. **跨时钟握手：数据必须先稳定，翻转沿要晚 1~2 拍**。原来数据与沿同拍变化，
   接收侧两条同步链谁先到看布线 → **按「谐波」结果翻了「滑音」**（用户实测报的）。
3. **命令的操作数会被当成音符**：`in_window` 是组合逻辑，必须把**所有**"等操作数"状态
   （`cfg_left/dur_wait/map_left/oct_left/fx_left/tone_left`）都挡掉，否则插队发命令会凭空多一个音。
4. **存储数组多一个读口 → BSRAM 推断失败**，退化成几千个触发器。`slot_dur` 只读 `rd_next` 一个地址
   （八度/音量都塞进同一个字里带出来）。
5. **数组别用变量下标赋值**（`inc[tr_gi] <= ...`）→ 综合器生成寄存器堆 + 36 路 36:1 选择器，多烧几千 LUT；
   要用 `generate` 展开成固定下标的独立寄存器。
6. **"常数化"是这个设计的省资源关键**：滑音目标、KS 弦长都用 `localparam` 常数；
   改成运行时常量会各烧一套 32 位加减器（实测 24 键 +2300 ALU）。
7. **注释乱码**是 Latin-1 与 cp1252 **混着**坏的（0x80~0x9F 那段只有 Latin-1 能解，`€/š` 只有 cp1252 能解）
   → 反查表要两种编码合起来建；`D:\CODE\_tmp\fix_mojibake.py` 是现成脚本。
8. **PowerShell（这台机器）**：写 `.ps1` 必须 **UTF-8 带 BOM + CRLF**；`$PSScriptRoot` 在 `param()` 默认值里为空；
   `[IO.File]::ReadAllText` 用**进程 CWD** 不是 PowerShell 的 `cd`；`pwsh` 不在 PATH（用 `powershell`）。
9. **上位机窗口**：`geometry` 存得比 `minsize` 小会把发送区裁掉；**两个 Frame 放进同一个 grid 单元会互相盖住**

15. **中文参数别经过命令行**：归档时 `-Name "V37_逐音八度"` 如果直接写在命令行里，
    按本机教训可能被转成 `?`。安全做法是**用同进程的 `&` 调用脚本**，
    版本名从文件系统读出来当变量传（V37 这么做的，归档名正确）。
16. **别用 `Tee-Object` 接长时间构建的输出**：`gw_sh` 的输出改走纯文件重定向
    （`*> file`），否则后台 job 的缓冲会把它憋住，看起来像"卡住了"。
17. **★ 插队发命令会把正在传的帧打断**（V38 修掉的实机 bug，最值钱的一条）：
    `0xC9`/`0xCA` 这类命令是"命令字 + 1 字节操作数"。谱子是**分批**发出去的，
    上位机用 `appendleft` / 优先队列把命令插进队列 —— 那个位置正好是两批之间
    = **帧的内部**。板子老老实实把紧跟的那个字节当成操作数**吃掉**，于是从
    那里开始整帧字节边界全错，而效果开关**已经被翻转了**。
    表现就是"播放时滑音/延音自己开了，谐波自己关了"（多个开关一起变）。
    ★ 当时 `_send_front` 的注释甚至写着"夹在谱子字节中间也不会被当成音符"——
      不会被当成音符是对的，但会被当成**命令+操作数**，漏了后半句。
    修法：命令只在**发完谱子之后**才发；板子在开窗期直接忽略 `0xC9/0xCA`。
18. **★★ Verilog 非阻塞赋值：同一拍里"写进去"和"读出来"是两个时刻**（V38 踩）：
    ```verilog
    if(bps_cnt == samp_c) samp_v[2] <= rx_i;                    // 下一拍才成立
    if(bps_cnt == samp_c) recv_reg <= {maj(samp_v), ...};       // 同一拍读 = 旧值！
    ```
    这个错误让"三次采样多数表决"用上了**上一位**的采样值，比原来的单点采样还糟。
    凡是"先寄存、后使用"的流水，取用点必须比写入点**晚一拍**。
    ★ 这类错误靠肉眼审不出来 —— `testfiles\sim_uart_rx.py` 是逐拍复刻
      `uart_rx.v` 的仿真，第 [1] 节专门钉住 `samp_d = samp_c + 1`。
      **改 UART/采样类逻辑后务必跑它。**
19. **"按整数个数查表"会变成电平台阶**（V34 埋、V38 才修）：
    `voice_scale(n_voice)` 的输入是【整数声部数】，7 档之间是硬跳变。
    每起音一个音系数就整档跳（N=1→2 是 256→192，掉 25%），一个采样点内完成
    —— 听感就是每个音头上"噗"一声。修法是让系数**每采样点走一小步**爬到目标，
    而不是一步到位（3.4ms 走完最坏一档，人耳无感）。
    ★ 这个工程在别处（`n_keys` → `env_sum`）已经修过同类问题一次，
      结果新加的 `voice_scale` 又犯了一遍 —— 凡是"离散输入 → 增益"的地方都要想一下台阶。
20. **★★★ 不要做"卡住就永久失灵"的设计**（V38 修错、V39 回滚，最贵的一次教训）：
    V38 为了挡住"插队命令吃掉谱子字节"，在板内加了一道
        `else if ((rx_data == FX_TGL_BYTE) && !armed)`
    看着很合理，但 `armed` **全工程只有两处赋值**：`0xAA` 置 1、`0xFF` 清 0。
    ★ **`0xC7`（停止演奏）不清 `armed`** —— 所以只要发帧中途出过状况
      （发了 `0xAA`、`0xFF` 没等到），`armed` 就**永久卡在 1**，
      效果开关**从此再也点不动**，用户没有任何办法自救。
    用户实测："**现在的'延迟'关不掉了，感觉逻辑乱了**"。
    **判据（加任何门控之前先问两句）**：
      ① 这个状态位会不会卡住？② 卡住之后用户还能不能自己恢复？
    只要任一答案是"会/不能"，这个门控就不能加。
    ★ 同一个 V38 还把上位机插队改成"排队"，而界面 `_fx_pending_check`
      1.2 秒就撤掉"待确认" —— **改了响应速度必须连界面一起看**，两边没对齐
      用户看到的就是"点了没反应"。
    ★ **修复要算总账**：V38 修的是"偶发帧错位"（还只在"一边发谱子一边点开关"
      时），代价是"开关可能永久失灵"。**宁可接受偶发的小毛病，也不要引入
      用户无法自救的死状态。**
    ★ 如果以后真要治"插队打断帧"，正确做法是**给帧加帧级校验**
      （让错位的帧整帧作废），**不是**去堵命令。
21. **★★ 整帧分块必须切在【协议单元边界】上**（V39.1 才找到的真隐患）：
    上位机把整帧按固定块长（256 字节）丢进发送队列，而控制命令是【插队】发的
    （插到下一块之前）。固定块长**完全可能把一个"命令字 + 它的操作数"从中间切开**，
    插队命令于是正好落进那一对中间：
        `... C4 | (插队) C9 04 | 00 E8 01 ...`
    板子收到 `C4` 后等 3 个参数，把插队的 `C9`、`04` 和下一块开头的 `00`
    **当成参数吃掉** —— 参数被污染（时间格设成错值）、整帧从那里错位。
    ★ 这比"插队插在帧中间"更糟：那个只是错位，这个还污染参数。
    ★ 一直没暴露是因为切中概率低（每帧约 1%）—— 用户说"原来没有误触发"是对的，
      不是没有，是极罕见。
    修法：`fpga_proto.safe_chunk_ranges()` / `FpgaProto.safeChunkRanges()`
    —— 按协议单元边界切块（单元 = 单音/休止/整个和弦/命令+它全部操作数）。
    ★ 只要切点在单元边界上，**插队就完全无害**（收到的是
      "…单元A | C9 04 | 单元B…"，两个都是完整单元）。
    ★ 契约脚本 `fpga_proto selftest` 第 [10] 节钉住这条：九种块长 + 长单元定向用例。
22. **★★ 状态卡住要用"超时自动恢复"，不要用"门控"**（V39.2，坑 20 的正解）：
    板内有两处会永久卡住的状态：
      · `armed` —— 只在 `0xAA` 置 1、`0xFF` 清 0，而**上位机的"停止演奏 / 重播 /
        按键映射下发"都会清发送队列**，正好能把帧发到一半截断，`armed` 就永久为 1；
      · 五个"等操作数"状态（`map_left` / `oct_left` / `key_oct_left` /
        `cfg_left` / `dur_wait`）**一个超时都没有** —— 操作数丢了就永久卡住，
        之后每个字节被当成操作数吃掉（`map_left` 是每 2 字节吃掉一对）。
    修法：**给全部等待状态加统一超时（6 个字节时间）+ 开窗 500ms 超时**。
    ★ 原则：**门控是"状态不对就不许用户操作"，超时是"状态不对就自己退回去"**。
      凡是要引入状态位影响用户操作的改动，**优先做成后者**。
    ★ `check_rtl_contract.py` 第 [8] 节会自动核对：`any_op_wait` 必须覆盖全部
      7 个等待状态、超时分支必须把它们**全部**清掉、`armed` 必须有超时关窗。
      以后新加"等操作数"状态忘了接超时，这项会红。
23. **★★★ 给"兜底超时"选阈值，必须先把【所有真实的间隔上限】列出来**
    （V39.2 设错、V40 才修，实机事故："蓝牙播放完全乱了，一直播放着不知道
    什么旋律，所有效果都没法通过上位机修改"）：
    V39.2 把"等操作数"的兜底超时设成 **6 个字节时间（6.24ms）**，理由是
    "操作数紧跟命令字，间隔 1 个字节约 1.04ms"。**这个前提是错的** ——
    真实的时间尺度是【上位机分批之间的间隔】：
        · 一批 256 字节 @9600 波特 = **266ms**
        · 安卓版背压 `while (pendingCount() > 64) Thread.sleep(20)` = **20ms**
    两个都远大于 6.24ms → **每次跨批都误触发**：
    `0xC2` 在批尾、操作数在下一批开头时，超时先清掉 `dur_wait`，
    操作数随后到达就**被当成音符** → 凭空多一个音，一首曲子累积下来全乱。
    ★ **判据（以后再设任何超时都照这个来）**：
      把**所有**可能的时间间隔列全 → 取**最大**的那个 → 至少留 2 倍余量。
      （V40 取 500ms：比最坏的 266ms 大近 2 倍、比背压 20ms 大 25 倍。）
    ★ 另一个刻意的选择：**阈值要大到"不依赖上位机版本"** ——
      即使跑的是老的 App（按 256 字节硬切、会把命令+操作数切开），
      500ms 也够等它跨过批边界。**让修复在任何组合下都成立。**
    ★ 检查脚本原来写的判据是"≥ 4 个字节时间"—— **那正是错的标准**，
      已改成"≥ 500ms 且必须远大于背压间隔 20ms"。

24. **★★★ 「上一笔 done 了就发下一笔」必须带 `!done` 条件**（V41 才彻底搞明白；
    独立工程 `LEDs` 上实测出过事故）：
    典型写法：
    ```verilog
    if (!busy && !go) begin
        if (step <= STEP_LAST) go <= 1'b1;
    ```
    ★ **少了 `!done` 就会多发一笔事务。** 原因是握手时序：
    从机的 `done` 脉冲和 `busy <= 0` 是【同一拍】生效的 ——
    也就是说 **`done` 那一拍 `busy` 已经是 0**；而 `step` 要到
    【那一拍结束】才 +1。于是 `done` 那一拍拿**旧的 step** 又排了一笔 `go`，
    下一拍 `step` 已经 +1，那笔 `go` 就发出去了 —— 一共发了 N+1 笔。
    ★ 在独立工程的 LED 驱动上，多出来的那一笔落在解码器最后一个 `else` 上，
    而那里写的是 `0x00 = 0x00`（**SSD=0 软件关断**）—— 实机现象就是
    **「全部 LED 亮了一瞬间就灭了」**：第 76 笔写 SSD=1 点亮，
    第 77 笔紧接着写 SSD=0 关断，中间只隔一笔事务 ≈ 290µs。
    ★ 判据（写任何「逐笔推进」的状态机都照这个查）：
      ① 发起条件里有没有 `!done`？
      ② `done` 那一拍 `busy` 到底是 0 还是 1？（去从机的 `S_DONE` 看：
         它和 `busy <= 0` 同时赋值，所以那一拍**已经是 0**）
      ③ 越界的 step 落到哪个分支？那个分支**绝不能**做「关掉/清空」这类动作
         —— 要写成安全值（这里兜底也返回 SSD=1）。
    ★ 这类错误**肉眼审不出来**（每个分支单看都对），必须靠逐拍仿真钉住。
      `testfiles\sim_led_guide.py` 里有两条专门的断言：
      「恰好 N 笔」和「go 与 done 从不同拍」。

25. **★★ 布线拥塞会把【别人】的临界路径压过线**（V41 实测）：
    给工程加了约 190 个 LUT 的 `led_guide`，而且它的逻辑**全在音频域、
    一个门都不在 CLKOUT1 上**，结果 CLKOUT1 还是从 50.007MHz 掉到
    **48.039MHz、TNS -4.938ns / 8 条**。
    ★ 这不是「新逻辑本身慢」，是**布局被扰动**：V40 那条路径本来就只有
      +0.003ns 余量（19.997ns / 20ns），贴在约束线上，任何改动都会压过去。
    ★ 教训：**「我的改动不在那个域」≠「那个域的时序不会变差」。**
      加完东西要重新看【每一个】时钟域的 Fmax/TNS，不能只看自己那个域。
    ★ 治法见坑 26。

26. **★ LCD 波形那条 21 级组合链（CLKOUT1 唯一的历史遗留瓶颈）已经治好了**
    （V41）：
    路径是 `u_lcd/wave_buf.../DO` → … → `u_lcd/cur_data_*/D`，数据延迟 20.7ns：
        BSRAM 输出 → 取绝对值 → 16 位桶形移位(>> wave_sh) → 补符号
          → 17 位加中线 → 上下限幅 → 线段比较 → 像素字节 → cur_data
    ★ 治法就是**从中间插两级寄存器**（和 V17c 把 `peak_msb` 打一拍同一个套路）：
        · `wave_y0/y1` 打一拍 → `wave_y0_r / wave_y1_r`
        · 缩放结果打一拍     → `v0_sc_r / v1_sc_r`
          （★ 符号位 `v0_sgn_r` 必须【同步】打一拍，否则符号比幅值早一拍，
            负半周会画反）
    结果 CLKOUT1：48.039 → **58.046MHz**，三个域 TNS 全 0。
    ★ **为什么插在那里一定安全**（以后动 LCD 前先读这三条）：
      ① 读地址 `wave_rd_addr0 = frame_wr - 320 + wave_col` 只跟 `wave_col` 走；
         `frame_wr` 是「一帧开始时锁住的写指针」（第 246 行注释），
         **不是连续推进的指针** —— 所以一整列里 `wave_v0/v1` 和 `wave_sh` 都不变，
         这两级寄存器每拍寄存的都是同一个值，只是晚 20ns 生效。
      ② 时序余量足：`wave_col` 一整列才 +1 一次，之后 state 先跳到
         `S_WAVE_WIN` 把 11 字节窗口命令发完（88 拍）才读第一个像素；
         而 `wave_y0` 在 `wave_col` 变化后 3 拍内就稳定。
         一整列 ≈ 5760 拍，这 3 拍占 0.05% —— 显示上看不出来。
      ③ 下游一个字没动：`wave_seg_lo/hi`、`wave_draw_seg`、`wave_pix_hi/lo`
         全部照旧，波形的「哪一列用哪两个采样点」【逐位不变】。
    ★ **代码注释里标了「别删」** —— 删掉任何一级，CLKOUT1 立刻回到 48MHz。

27. **★★★ 【未结案】`RAM16` 从 214 涨到 808 —— 三个猜测全被实测推翻**（V43.5→V44.2）：
    【现象（这一条是真的）】
      V43.4 之前：`--SSRAM(RAM16) 214`，`BSRAM 88`，`Logic 38687`
      V43.5 起    ：`--SSRAM(RAM16) 808`，`BSRAM 86`，`Logic 43894`   ← 一直没降回去
      多出来的 ~594 块分布式 RAM 正好 = 一块 36×1024 的数组。

    【三个被推翻的猜测 —— 每个都做过单变量实验，全部无效】
      猜测①「影子数组的【写语句】写法不好，所以推断不出 BSRAM」
             → 试了 5 种写语句变体，**一次都没变**。变量根本不在写语句上。
      猜测②「`slot_mask` 的读地址从 `rd_slot` 换成 `rd_next`（`rd_slot + 1`，
             一个加法器输出），地址前串了加法器所以掉出 BSRAM」
             ★ 这条当时被写进本文档当成结论，**是错的**。
             → V44.1 把读地址【改回 `rd_slot`】重新构建，
               `RAM16` 仍然是 **808**，`BSRAM` 仍然是 **86**，一点没降。
               猜测②被实测否掉。
      猜测③「`slot_cur` 的消费者（扇出）太多」
             → 也做了实验，无效。

    【结论】**根因至今未明。** 上面三条都不是原因，别再照着它们改代码。
      已知的边界条件（供后续排查用）：
        · 与 `syn_only.tcl`（只综合）对比时，必须 PnR 对 PnR（见坑 28）。
        · `RAM16 808` / `Logic 74%` 是**当前既成事实**，功能正常，
          只是把 `CLKOUT1` 的 Fmax 压在 51.9MHz、余量只剩 26%。

    【★ 附带发现，比坑本身更重要：PnR 是【确定性】的】
      同样的输入，**两次完全相同的重新构建会产出逐字相同的资源数和 Fmax**
      （V44.1 与 V44.2 实测：`Logic 43894 / Register 14050 / BSRAM 86 / DSP 55.5`
       以及 `65.150 / 28.712 / 51.909 MHz` 全部相同）。
      ★★ 所以**不要指望「重跑一次构建」能把时序或资源改好** ——
         那不是运气问题，是输入没变。要变，必须真的改代码或改约束。

28. **★★ 对比资源必须 PnR 对 PnR，绝不能拿综合比 PnR**（V43 踩，浪费了 5 次构建）：
    `syn_only.tcl` 产出的是 `impl\gwsynthesis\music_syn.rpt.html`（**综合**阶段）；
    资源与时序的最终值只能看 `impl\pnr\music.rpt.txt` 和
    `impl\pnr\music_tr_content.html`（**PnR**阶段）。
    ★ 综合之后 PnR 还会做一轮优化，post-PnR 的逻辑数通常比 post-综合【少】——
      两个阶段的数字混着比，会得出完全错误的结论。
    ★ `syn_only.tcl` 的正确用途只有一个：**快速看"数组有没有进 BSRAM"**
      （看 BSRAM / SSRAM 两项），别用它比 LUT 数。
    ★ 另：`syn_only.tcl` 原来写的是 `run synthesis`，gw_sh 报
      `unknown process: synthesis` —— 这个脚本【从写下来就是坏的】，
      交接文档却一直把它列为"日常迭代首选"。V43 已改成 `run syn` 并实测可用。

## 5.5 实装/交付：两份并列的引脚约束（V46 新增）

工程里有**两份并列**的引脚约束，同一时刻只能启用一份：

| 文件 | 用途 |
|---|---|
| `src\music.cst` | **调试版**（原来的，一个字节没动） |
| `src\music_release.cst` | **实装版（交付用）** |

两者差别**只有 8 个引脚**（实装 PCB 的走线）：

| 信号 | 调试版 | 实装版 | 说明 |
|---|---|---|---|
| `uart_txd` | W22 | **V18** | 蓝牙是【开发板这头】的 TX/RX |
| `uart_rxd` | W21 | **G21** | |
| `scl` / `sdo` | C22 / F18 | **B22 / E18** | 琴键1 = 键 0~11（RTL `kp1`） |
| `scl2` / `sdo2` | E21 / E22 | **C22 / F18** | 琴键2 = 键 12~23（RTL `kp2`） |
| `scl3` / `sdo3` | B22 / E18 | **E21 / E22** | 琴键3 = 键 24~35（RTL `kp3`） |

★ 琴键那三组是**整个轮换了一圈**的（1←3、2←1、3←2），因为实装 PCB 就是这么布的。
★ 没被提到的引脚一律保持原样（`led`=U12 / `led_glide`=G11 / `lat_key`=C19 /
  `lat_pcm`=C18 / `led_scl`=V17 / `led_sda`=W17 ……），所以 build 脚本里那三行
  `set_option -use_done_as_gpio 1` / `-use_ready_as_gpio 1` / `-use_cpu_as_gpio 1`
  **不用改**。

### 怎么切换（★ 别手改 music.gprj）
