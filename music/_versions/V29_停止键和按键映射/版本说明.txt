需求
------------------------------------------------------------------------
1) 两端（手机和电脑）都要加"蓝牙播放乐谱的停止键"。先做电脑端。
   用户选的是 A+B：
     A = 停播+松键+清空乐谱（纯软件，板子不改）
     B = 停播但【保留乐谱】，能续播/重播（要给板子加新指令）
2) 演奏按键自定义：演奏者能把某个按键重新指定成另一个音。
   用户指定的规格：映射表存在 FPGA 里，通过蓝牙可写，
   掉电保存【先不做】（每次连上由软件下发一遍）。
   范围：36 个键各自指定到 36 个音里任意一个。
3) 电脑端是否跟着反查映射表：用户选了"要"，但最终实现
   【不需要反查】—— 原因见下面"设计决定"。

------------------------------------------------------------------------
协议新增三个字节（都不受开窗限制，随时可用）
------------------------------------------------------------------------
    0xC6 + 键号 + 音符     写一条按键->音符映射（音符给 0x3F = 禁用该键）
    0xC7                   停止演奏（★ 保留乐谱，可重播）
    0xC8                   重播板内已经存着的那一帧

  · 三个都能在【关窗状态】下用 —— 板子放完 0xFF 之后窗口是关着的，
    而"停下来"恰恰是那时候要做的，所以它们和 0x5C 一样放在
    "不受开窗限制"的那条分支里。
  · 0xC6 的两个操作数是【原始数据】，用 map_left 计数器挡（和 0xC2 同理）。
    另外它们被限在 0..35 / 0x3F，最大 0x3F，而所有控制字节都 >= 0x5A ——
    天然不可能撞车，这是设计性质不是巧合（自检里有这条断言）。

  ★ 三个字节原先在文档里是预留给"整帧移调 / 音色切换 / 实时 Note On"的，
    这一版把它们占用了，预留表已经划掉并注明。

------------------------------------------------------------------------
★★★ 设计决定：映射做在"物理键 -> 声部"这一步 ★★★
------------------------------------------------------------------------
最直觉的做法是加一张 key_map[]，让发音取 delta[key_map[g]]。
**这个做法是错的**，因为 top.v 的滑音那段有一条实测注释：

    ★ 目标必须是【常数】delta[g]！一旦改成运行时寄存器，
      每个键都要一套真的 32 位加减法器，实测 24 键就多烧 2300 个 ALU。

36 个键按这个比例要 3400+，而且全压在音频关键路径上。

所以改成：**声部一个都不动**（还是常数 delta[g]），只把"哪个物理键按下"
搬到对应的声部位上：
    按下物理键 p  ->  点亮声部 key_map[p]
实现是一个 36x36 的 one-hot 选择网络（每个物理键做一次 36 位译码，
按"这个键按下了吗"选通，最后 36 路或起来）。实测代价：
    Logic  21013 -> 23621  (+2608，和预估的 2600 基本一致)
    Register 5896 -> 6156  (+260，key_map 那 216 位 + 同步用的)
    BSRAM / DSP 不变，时序 0 违例

这个位置换来三个好处（都不是巧合，是选它的理由）：
 ① 滑音 / 移调 / 包络 / 相位那一整套一个字都不用改；
 ② 【乐谱播放不受映射影响】—— midi_keys 本来就是声部号，所以同一份谱子
    不管映射怎么改，弹出来还是谱子上写的音。**电脑发谱不需要按映射反查**；
 ③ 录音回传采的也是声部掩码，**电脑合成 MIDI 时也不用套表**。

也就是说：**映射只影响手弹，不影响放谱** —— 这正是想要的语义，
而且比"电脑反查"更简单，还避开了"两个键映到同一个音导致反查歧义"的问题。

key_map[p] 给 >=36 的值（用 0x3F）表示【禁用该键】，按了不发声。
两个物理键映到同一个声部也可以（或在一起）；反过来，一个声部如果没有任何
物理键映过去，那就只能由乐谱来弹。

怎么用
------------------------------------------------------------------------
【烧录】_versions\V29_停止键和按键映射\bitstream\music.fs（必须重烧，
        0xC7/0xC8 是新指令，老 bitstream 不认）

【停止演奏】放谱子的时候想中途掐掉：
    · 「停止演奏」= 停播 + 松键，乐谱【留着】，想再听点「重播」
    · 「停止并清空」= 连乐谱一起清掉（用老协议 AA FF，不依赖新指令）
    ★ 两个都会先把还没发出去的队列清掉 —— 不然指令排在几百字节谱子后面，
      等它轮到板子早弹完了。

【按键映射】点「按键映射…」-> 36 行，每行给自己想要的音（或「禁用」）
    -> 「下发到板子」。改完存在 spp_config.json 里，每次连上会自动下发。
    ★ 只影响手弹。放谱子还是谱子上写的音，不受影响。

★ 补记（归档之后修的两处上位机界面问题 + 安卓版同步）
------------------------------------------------------------------------
【一】上位机「加了按钮但界面上看不见」——两个独立原因，都修了：
  1) 两个 LabelFrame 放进了同一个 grid 单元（演奏控制行和演奏录音行都是 row=3），
     后建的把先建的整个盖住。
     → 「演奏录音」挪到 row=4；selftest.py 第 [12] 节加了布局自检：
       全界面扫描"有没有两个控件占同一格"、跨满整行的功能行各占一行、
       窗口需要的宽度不超过默认窗口宽、新控件确实在布局里。
  2) 配置里存着一个 668x537 的窗口大小，比程序自己声明的 minsize(820x560) 还小；
     Tk 的 minsize 管得住用户拖边框，管不住 wm geometry 直接设更小的值，
     结果发送区下半截被裁掉，新加的行正好在裁掉的那部分里。
     → _apply_config 恢复 geometry 前先判尺寸，小于 minsize 就退回 980x720 并说明原因。
  ※ 这两条都是"编译过、跑起来也对，就是看不见"的坑，只能靠自检和截图发现。
