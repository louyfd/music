### B. ★ 立刻要做的：V48（用户已确认"一次修好"）

**三件事，用户明确要求合到一版：**

**① LCD 显示模式接上位机 + 双向同步**（用户原话："所有 TTP 上的可调按键全部在上位机上也可调，并且状态保持同步"）
- 已核对：按钮板 16 键里 **9 个功能已经有上位机控制**，真正缺口只有两个：
  - **键3 = LCD 显示切换**（`disp_mode`）—— 完全没接上位机
  - **键10 = 录音开关** —— 能发（`0x5C`）但**板子按下时不回报**
- **协议（已钉死，上位机侧已按此实现，别改）**：
  ```
  上位机 -> FPGA：0xD0 + 1 字节 disp_mode    (0=频谱 1=波形 2=李萨如，超出夹到 0~2)
  FPGA -> 上位机：0x5F + 2 字节 disp_mode, rec_on   ← 全新独立帧，【不动 0x5D】
  ```
  `0x5F` 在**值变化时**发 —— **包括板子上按 TTP 键3/键10 的时候**，这才叫双向同步。
- RTL 要动的地方：
  - `uart_packet_echo.v`：加 `DISP_SET_BYTE=0xD0` / `DISP_STAT_BYTE=0x5F`；`disp_wait`+`disp_hold`（照 `vel_wait`/`vel_hold` 的写法）；**新开一台小状态机发 `0x5F`**（★ 不要复用它 `fx_idx`，那会动到 `0x5D`）；加输入 `disp_mode_in` / `rec_on_in`
  - `top.v`：`disp_mode` 现在在 **`clk_50m` 域、由按键驱动**（`top.v` 约 312~321 行，`wave_mode <= (disp_mode == 3'd1)`）。要**加一条 UART 路径**（用 `metro_tgl` 那套"翻转沿+数据握手"跨到 `clk_50m`），**不能破坏按键的循环切换**；再把 `disp_mode` / `rec_on` 送回 `clk_50m_ext`
  - 有**两处跨时钟域**要做

**② 频谱切模式回来变空白** —— ⚠️ **上一轮说"已改完"，其实是【没修好】，本版重做了**
- 病灶（这一条是对的）：`bar_state[0:59]` 是"每列上次画完的高度"缓存，
  `bar_dirty = (bar_state[col] != tgt_q)` 决定要不要重画；切模式时清了屏但
  **没清 `bar_state`** → 切回来时每列高度和缓存一样 → `bar_dirty` 恒 0 →
  **一根都不重画** → 空白（声音一直正常）
- ★★ 上一轮的修法**两层错**（详见第 5 节**坑 40 / 坑 41**）：
  ① 置 `bar_force` 的那个分支在 `S_BAR_WIN` 里，判据是 `wave_mode` ——
     而**频谱和 3 档李萨如的 `wave_mode` 全是 0**，用户报的那条路
     （频谱 ↔ 李萨如）**永远进不去**；而且频谱显示时状态机
     `S_BAR_WIN ↔ S_BAR_DATA` **自循环、根本不回 `S_IDLE_WAIT`**。
  ② 那个 `24'd17_500_000`（想表达 0.35s）**装不进 24 位**，被静默截断成
     **14.5ms** —— 连清屏一项（147.5ms）都盖不住，一列都不会重画。
- ✅ **本版正解**：**不作废标志，作废缓存** —— 三个切模式点把 `bar_state[]`
  整片写成哨兵值 `9'h1FF`（`col_target` 最大只有 179，取不到这个值），
  每列画完自动写回真实值 = **逐列自动消耗**。
  `bar_dirty` 表达式**逐字回到原样**；代价 Logic +96 / Register +34。
  验证：`testfiles\sim_bar_cache.py`（36 项，含"上一版 0 列 vs 本版 60 列"的对照）

## 0.6 本轮（V44 ~ V47.2）新增的坑 —— 编号接 §5 的 31

32. **★★★ "先用后声明" —— 本轮踩了三次，是本工程最高频的低级错**：
    Verilog 里 `wire`/`reg` **必须在使用之前声明**。不提前声明的话工具会**建出隐式 1 位线**，
    综合不报错、行为却是错的（或宽度被截成 1 位），极难查。
    **本轮的三个实例：**
    - `uart_packet_echo.v`：`mt_start` 用了 `st_start`/`fx_start`，但那两个声明在它后面
      → 把 `st_start`/`fx_start` **挪到前面**
    - `uarT_packet_echo.v`：`mt_want`/`mt_start` 在"总线仲裁"那一段就要用，声明却放在帧那一段
      → 把 `mt_*` 的 reg 声明**挪到 `fx_idx` 那一堆旁边**
    - `top.v`：`midi_vel_aud` 在"混音缩放"（`voice_scale` 附近）就要用，声明却在 4400 行以后
      → 在**文件前面**（`metro_led` 那一片）先声明 `wire [6:0] midi_vel, midi_vel_aud;`，
        后面的 `wire ... = midi_vel_s2;` 改成 `assign midi_vel_aud = midi_vel_s2;`
    **判据**：新加的信号，先在文件**靠前**的地方声明，再在需要的地方用。

33. **★★★ 共用路径不能拿来放"逐音"的东西**（V47.1 踩，用户实测"噗声还在"）：
    `mix_scale`（混音总增益，`top.v`）是**所有发声部共用**的。V47.1 把力度瞬时乘在它上面，
    结果**力度一变，所有正在响的音（含延音尾巴）都跟着跳** → 每个音一声"噗"。
    **正解**：力度走**每个音自己的包络峰值**（`gen_env` 里的 `vel_peak_k`）——
    起音就从正确音量开始、**没有任何增益跳变**、正在延音的音一个比特都不动。
    ★ 判据：**如果一个量是"逐音"的，它就不能乘在"共用"的路径上。**

34. **★★ `mix_scale_r` 那条斜坡是治"起音噗声"的（V38），别往它的目标里塞东西**：
    斜坡 `SCALE_STEP=1/采样点`，落差 96 步要 **~2ms**。把力度接到斜坡**目标**上
    → 起音那 2ms 按**旧的大音量**出来再缩下去 = 一声"噗"。
    ★ 斜坡只跟**声部数**；任何"瞬时"的量都不要走它。

35. **★★ 跟谱模式的 `gate_snd` 不能带 `|| slot_go`**（V47.2 修，用户实测"同一个音的又一次触发"）：
    `gate_snd = gate && ((!wait_mode) || slot_go)` 里那个 `slot_go`：
    用户按对键时若 `ev_left` 还没走完，下一拍 `gate_snd=1` → **谱子把当前这一格弹了出来**，
    而当前格正是他刚按的音 → 听着是"同一个音的又一次触发"。
    **正解**：`gate_snd = gate && !wait_mode` —— **跟谱模式下谱子永不出声**。
    ★ 语义：跟谱模式的声音来自**用户自己按的键**（手弹那条路），FPGA 不该替他弹。
    ★ 正常模式 `gate_snd ≡ gate`，逐位相同。
    ★ 为什么"开了力度才出现"：每事件多 2 字节 → 帧更长 → 用户更容易在 `ev_left` 没走完时按下。

36. **★★ `need_mask` 比 `rd_slot` 慢一拍 → 假报"休止格"**（V47.1 修，用户实测"没锁住第一个音"）：
    `cycle N` 装载（`rd_slot ← 0`），但 `need_mask` 那一拍采到的还是**哨兵时期的 0**；
    `cycle N+1` `need_done=1` → `slot_go` 被顶回 1 → 这一格被替弹。
    **正解**：`load_now` 打一拍（`load_now_d`），`need_none_ok = need_none && !load_now_d`
    把**装载后那一拍**屏蔽掉。
    ★ 影响面只有那一拍；正常模式 `slot_go` 那条 `if` 链第一条就是 `!wait_mode`，
      我改的那条**根本轮不到被判断** → 正常播放逐位不变（有仿真断言）。

37. **★★ LCD 的"脏缓存"要在切模式时失效**（V48 修，用户实测"切到李萨如再切回来频谱空白"）：
    `bar_state[0:59]` 是"每列上次画完的高度"缓存，`bar_dirty` 决定要不要重画。
    切模式时 `S_CLEAR_BAR` 清了屏但**没清 `bar_state`** → 切回来 `bar_dirty` 恒 0 → **一根都不重画**。
    **正解**：切模式时置 `bar_force`，`bar_dirty` 或上它，约 0.35s 后清掉。
    ★ 数据没丢、声音没受影响 —— 丢的是"该重画"这个标记。**这类"缓存没失效"的 bug，
      症状永远是"屏幕不对但功能正常"。**

38. **★ 跟谱模式下 `ev_left` 会照常走完 —— 这是设计，不是 bug**：
    等待用户按键期间 `ev_left` 一直在倒数，走完就停在那一格等。因为跟谱的声音来自用户的手指，
    所以"谱子不出声"是**正确**的。★ 别看到 `ev_left` 归零就以为出问题了。

39. **★ 本机环境三个坑（写脚本用）**：

    - **控制台是 cp1252** → Python 打中文会 `UnicodeEncodeError`。

22. **★★ 状态卡住要用"超时自动恢复"，不要用"门控"**（V39.2，坑 20 的正解）：

23. **★★★ 给"兜底超时"选阈值，必须先把【所有真实的间隔上限】列出来**

24. **★★★ 「上一笔 done 了就发下一笔」必须带 `!done` 条件**（V41 才彻底搞明白；
    独立工程 `LEDs` 上实测出过事故）：
    典型写法：
    ```verilog
    if (!busy && !go) begin
        if (step <= STEP_LAST) go <= 1'b1;
    ```
    ★ **少了 `!done` 就会多发一笔事务。** 原因是握手时序：
    从机的 `done` 脉冲和 `busy <= 0` 是【同一拍】生效的 ——
    也就是说 **`done` 那一拍 `busy` 已经是 0**；而 `step` 要到
    【那一拍结束】才 +1。于是 `done` 那一拍拿**旧的 step** 又排了一笔 `go`，
    下一拍 `step` 已经 +1，那笔 `go` 就发出去了 —— 一共发了 N+1 笔。
    ★ 在独立工程的 LED 驱动上，多出来的那一笔落在解码器最后一个 `else` 上，
    而那里写的是 `0x00 = 0x00`（**SSD=0 软件关断**）—— 实机现象就是
    **「全部 LED 亮了一瞬间就灭了」**：第 76 笔写 SSD=1 点亮，
    第 77 笔紧接着写 SSD=0 关断，中间只隔一笔事务 ≈ 290µs。
    ★ 判据（写任何「逐笔推进」的状态机都照这个查）：
      ① 发起条件里有没有 `!done`？
      ② `done` 那一拍 `busy` 到底是 0 还是 1？（去从机的 `S_DONE` 看：
         它和 `busy <= 0` 同时赋值，所以那一拍**已经是 0**）
      ③ 越界的 step 落到哪个分支？那个分支**绝不能**做「关掉/清空」这类动作
         —— 要写成安全值（这里兜底也返回 SSD=1）。
    ★ 这类错误**肉眼审不出来**（每个分支单看都对），必须靠逐拍仿真钉住。
      `testfiles\sim_led_guide.py` 里有两条专门的断言：
      「恰好 N 笔」和「go 与 done 从不同拍」。

         `frame_wr` 是「一帧开始时锁住的写指针」（第 246 行注释），
         **不是连续推进的指针** —— 所以一整列里 `wave_v0/v1` 和 `wave_sh` 都不变，
         这两级寄存器每拍寄存的都是同一个值，只是晚 20ns 生效。
      ② 时序余量足：`wave_col` 一整列才 +1 一次，之后 state 先跳到
         `S_WAVE_WIN` 把 11 字节窗口命令发完（88 拍）才读第一个像素；
         而 `wave_y0` 在 `wave_col` 变化后 3 拍内就稳定。
         一整列 ≈ 5760 拍，这 3 拍占 0.05% —— 显示上看不出来。
      ③ 下游一个字没动：`wave_seg_lo/hi`、`wave_draw_seg`、`wave_pix_hi/lo`
         全部照旧，波形的「哪一列用哪两个采样点」【逐位不变】。
    ★ **代码注释里标了「别删」** —— 删掉任何一级，CLKOUT1 立刻回到 48MHz。

27. **★★★ 【未结案】`RAM16` 从 214 涨到 808 —— 三个猜测全被实测推翻**（V43.5→V44.2）：

      V43.4 之前：`--SSRAM(RAM16) 214`，`BSRAM 88`，`Logic 38687`
      V43.5 起    ：`--SSRAM(RAM16) 808`，`BSRAM 86`，`Logic 43894`   ← 一直没降回去
      多出来的 ~594 块分布式 RAM 正好 = 一块 36×1024 的数组。

             → 试了 5 种写语句变体，**一次都没变**。变量根本不在写语句上。
      猜测②「`slot_mask` 的读地址从 `rd_slot` 换成 `rd_next`（`rd_slot + 1`，
             一个加法器输出），地址前串了加法器所以掉出 BSRAM」

             → V44.1 把读地址【改回 `rd_slot`】重新构建，
               `RAM16` 仍然是 **808**，`BSRAM` 仍然是 **86**，一点没降。
               猜测②被实测否掉。

             → 也做了实验，无效。

    【结论】**根因至今未明。** 上面三条都不是原因，别再照着它们改代码。
      已知的边界条件（供后续排查用）：
        · 与 `syn_only.tcl`（只综合）对比时，必须 PnR 对 PnR（见坑 28）。
        · `RAM16 808` / `Logic 74%` 是**当前既成事实**，功能正常，
          只是把 `CLKOUT1` 的 Fmax 压在 51.9MHz、余量只剩 26%。

    【★ 附带发现，比坑本身更重要：PnR 是【确定性】的】
      同样的输入，**两次完全相同的重新构建会产出逐字相同的资源数和 Fmax**

41. **★★★ "置个标志 + 计时清掉"这种修法，两个坑：触发点会打偏、窗口长度是个隐藏前提**
    （V48 踩；第一版修法整个被否掉，改成"作废缓存"）
    【用户的 bug】"切到李萨如图形后再切回来，频谱就被清空了，但是那些音还在发出！"
      病灶：`bar_state[0:59]` 是"每列上次画完的高度"缓存，`bar_dirty` 靠它判重画。
      切模式把屏清了、**但没动作废这个缓存** → 切回来每列高度和缓存一样 →
      `bar_dirty` 恒 0 → **一根柱子都不重画** → 空白。
      ★ 这类"缓存没失效"的 bug，症状永远是 **"界面不对但功能全正常"**。
    【第一版错在哪】
      ① **触发点打偏**：标志只加在 `S_BAR_WIN` 里，判据是 `wave_mode != wave_mode_d`。
         但 **频谱和 3 档李萨如的 `wave_mode` 全都是 0**（只有波形是 1），
         用户报的那条路（频谱 ↔ 李萨如）**永远进不了那个分支**。
         更隐蔽的是：**频谱显示时状态机在 `S_BAR_WIN ↔ S_BAR_DATA` 里自循环，
         根本不回 `S_IDLE_WAIT`** —— 所以"进出李萨如"这个切换只能在
         `S_IDLE_WAIT` 里被发现，而那里没置标志。
         ★ 教训：**改状态机里的"切模式"逻辑之前，先把状态流向画出来**，
           确认你要挂的那个分支到底会不会被走到。
         三个真正的切换检测点：
             ① `S_BAR_WIN`   : `wave_mode` 变了   （频谱 ↔ 波形）
             ② `S_IDLE_WAIT` : 进出李萨如          （★ 用户报的就是这一条）
             ③ `S_IDLE_WAIT` : `wave_mode` 变了   （波形 → 频谱）
      ② **窗口长度是个没人算过的隐藏前提**：标志必须在"清屏 + 重画一整轮"
         结束前一直有效。实测：清主区 147.5ms / 全屏清 196.6ms / 重画 60 列 83.8ms
         → 退出李萨如那条路一共要 **280.4ms**，第一版设的 0.35s 只有 1.25 倍余量，
         再叠上坑 40 的截断（14.5ms）就彻底失效。
    【正解】**不作废标志，作废缓存**：把 `bar_state[]` 整片写成哨兵值
      **`9'h1FF`**（`col_target` 最大只有 179，这个值永远取不到），
      于是每一列都"脏"，直到它真的被重画完 —— 而画完一列本来就会写回真实值，
      所以这个"强制"是**逐列自动消耗**的：
        · 不需要计时器、**不需要任何窗口长度假设**
        · 反复快按按钮 3 也不会漏（每次切模式都重新作废）
        · **`bar_dirty` 的表达式逐字回到原样**（正常刷屏路径零影响）
        · 代价：Logic **+96** / Register **+34**（BSRAM 不变）
    【★ 可迁移的判据】
      · **能用"状态自然消耗"表达的修复，不要用"计时器"表达。**
        计时器方案永远隐含"窗口必须比 X 长"，而 X 往往能算出来。
      · 三个作废点**必须都在**；`check_rtl_contract.py` 第 **[11]** 节钉住这条
        （`bar_dirty` 不许有强制项、作废点恰好三处、"进出李萨如"那处必须在）。
      · 定量核算在 `testfiles\sim_bar_cache.py`（36 项，含"第一版 0 列 vs 最终版 60 列"
        的对照）。

44. **★★★ 板子会【原样回显】收到的字节 —— 操作数一旦撞上帧头，上位机就会读出一帧假状态**
    （V48 踩，用户实测报的："每次发谱，软件自己就把**混响和合唱**显示成打开，
      音色有时还变成**笛子**；点一下「刷新状态」就正常了。"）
    【机制】板子把收到的字节原样回显（v1 就有的行为，只有 `0xAA` 不回显），
      而上位机要在同一条流里找板子**主动发**的状态帧。于是：
      **只要上位机发出去的操作数里出现了帧头字节，它的回显就会被当成一帧真状态。**
      而谱子里的【力度】是任意 0~127 —— 力度 `0x5D`(=93) 一出现：
          C3 5D C0 01 ...   老代码读成  fx=0xC0(混响+合唱)  tone=0x01(笛子)
      ★ 这不是罕见数据：本机 MIDI 目录 **12 首里 10 首**会命中（93 很常见）。
      ★ 而且它**只在按下"刷新状态"（0xCB）后才好** —— 因为板子真的会回一帧正确的
        状态把它盖掉。**"刷新一下就好了"这个特征，就是"上位机状态被污染"的指纹。**
    【治法 · 两道一起上，缺一不可】
      ① **发送侧消毒**（`fpga_proto.safe_operand` / `safe_u24`）：
         操作数里凡是会撞帧头的值，微调 1~2（力度差 1/127、时间参数差几 µs、
         时值差 1 格、BPM 差 1）—— 听感上完全无感。
         ★ 涉及的帧头是 **90/91/93/94/95 连在一起**的，所以"±1"不够，
           必须一圈一圈往外找（`94` 的左右邻居 `93/95` 也都是帧头 —— 踩过）。
         ★ **力度/时值/时间参数/`0xCF` 的 BPM 四处都要过**，漏一处就还漏一个洞。
      ② **接收侧候选帧**（`fpga_rec._fx_cand`）：`0x5D` 先不写 `fx_state`，
         等后面的字节确认；**同一批里能拿到反证就否掉，批内证不了就当真的**
         （★ 这一条是关键：老契约要求 `[0x5D][fx]` 单独一批到也【立刻】更新状态、
           音色可以下一批再补 —— 一次读到底就把候选结清，老行为才一个字节不变）。
         `0x5B` 也补了校验（开关字节必须 ≤1）—— 它更危险：**假帧的"上升沿"
           会把已录到的事件整段清空，那是真丢数据。**
    【判据】`test_echo_collision.py`：全部真实谱子 + 穷举力度 0~255、
      时值、时间参数、256 个 BPM（含板子紧接着回的 `0x5E`），
      断言"发出去 -> 回显 -> 解析"之后状态一个比特都不许变。
    【★ 更彻底的做法（已列入待办）】板子侧"**操作数不回显**" ——
      回显里真正危险的只有操作数（命令字都在 `0xC0~0xD0`，不是帧头）。
      这和"录音期间不回显"是同一个理由，项目自己已有先例。做了它，
      这一类就从根上没了，第三方上位机也不会再踩。

45. **★★★ 「搜索窗口要扫多远」必须按【数据形态】算，不能按"差一点点"想**（V48.2 踩）
    背景：坑 44 的发送侧消毒里，时间参数是 3 字节，要找一个"三个字节都不是帧头"的
    近似值。第一版写的是 `for d in range(0, 256)`，理由看着很合理：
    "时间参数的单位是 µs，最多挪 255µs，完全无感"。
    **错。** 帧头是**连成一段**的（`0x5A 0x5B 0x5D 0x5E 0x5F`）：
      · 当【中间那个字节】落进这一段时，**整个 256 的块全是坏的**，
        ±255 根本跳不出去；
      · 实测 `v = 0x005E5F`（= 24159µs ≈ 一格 24ms，快曲子真的会用）：
        `b0=0x5F`、`b1=0x5E` 两个都是帧头，往下 3 只修好 `b0`，
        要一直走到 `0x006000` 才安全 —— **需要 +417，超出 255 窗口**。
    ★★ **是安卓侧的子代理用独立脚本穷举 0~0xFFFFF 抓出来的**：
      ±255 时仍有 **4160 个值不安全**，而且包含 tick ≈ 23~24.6ms
      （`0x5A00~0x5FFF`）**一整段**。
    【正解】窗口放到 **4096**，并补一层"逐字节兜底"。
      ★ 为什么 4096 一定够（这个论证比数字本身重要）：
        d 从 0 增到 4095 时，`b1` 至少要进位/借位 **16 次**，
        而坏值只有连着的那 5 个 —— 所以必然存在某一段 `b1` 是好的；
        `b1` 一旦变好就**保持 256 个值不变**，而那 256 个值里 `b0` 会取遍 0~255，
        其中 251 个安全 → 必定命中。
    【判据】**先写出"坏值的形态"，再定窗口大小**；
      只要是"按字节判断"的约束，窗口就得按 **256 的整数倍**去想，
      不能按"差 1 个就够"。
    【验证】修完穷举 `0~0xFFFFF` 零漏网；并且 Python 与 Java 两边的
      消毒函数对拍 **131,463 行逐字节一致**。
    ★ 附注：同一天还发现**摇杆那两条链**是同类的"超长组合链"（`js_x` 一次、
      `js_z` 一次），都用"插两级流水"治了（见坑 41 的做法）。
      判据一样：**先算"这个量多久才变一次"** —— js_* 每 2.6ms 才更新，
      迟 2 拍（40ns）完全看不见。★ 插完要重新构建并**看三个域的 Fmax**，
      因为瓶颈会在布局扰动下从一条链跳到另一条链。

48. **★★★ 同一份协议里的两条命令，"越界怎么退化"可以【故意不一样】——必须以 RTL 原文为准**（V48.3 踩）
    背景：V48.3 把音色从 3 档扩到 4 档（加小号）。我（主 agent）凭记忆口头告诉子代理
    "`0xCA` 的操作数**夹紧**到 0~3，不是取模"，子代理照此在 Java 里写了
    `clampTone(4) = 3`；而**板子 RTL 和电脑版 Python 里其实都是"越界一律当 0"**：
    ```verilog
    tone_val <= (rx_data > 8'd3) ? 2'd0 : rx_data[1:0];   // uart_packet_echo.v 0xCA 分支
    ```
    ★★ 于是同一条命令出现了**三方两派**：RTL 与 Python → `0`，Java → `3`。
    ★ 抓到它的是**子代理自己**（它在报告里单列了一条"唯一需要你对齐的地方"并给了对拍数据），
      不是我的回归 —— 因为**界面只能产出 0~3，这条纯防御分支在真实路径上永远走不到**。
    【根因】两条命令的越界语义**本来就是故意不同的**，我却按"一类东西应该一致"的直觉去记：
      · `0xD0` **显示模式**：`(rx_data > DISP_MAX_MODE) ? DISP_MAX_MODE : rx_data[2:0]` —— **夹紧**（留在最接近的有效档）
      · `0xCA` **音色**    ：`(rx_data > 8'd3) ? 2'd0 : rx_data[1:0]` —— **退化成最保守的"普通"**
      两者都对，但**理由不同**：显示模式"夹紧"是为了别让界面跳档；音色"退化"是因为
      **越界值不该让板子突然发出一档用户没选过的音色**（最保守 = 什么都不加）。
    【纪律】① 跨语言实现同一协议时，**"越界/非法值怎么退化"必须从 RTL 原文抄**，
      不许凭记忆口头传达 —— 口头传达等于让三个人各自实现三个版本；
      ② **裁决顺序钉死：RTL（板上真值）> 电脑版 Python > 安卓 Java**，
         以低位为准往上对齐，**不许反过来为了迁就实现去改 RTL**；
      ③ **防御性分支也要有判据**：这条分支真实路径走不到，但正因为走不到，
         它错了**永远不会自己暴露** —— 必须专门写一条用例钉住（已加：
         `4/255/-1 → CA 00`，判据里逐字引 RTL 原文）；
      ④ **名字要跟着语义走**：`clamp*` = "给最接近的一头"，和"退化成普通"不是一回事。
         Java 侧已改名 `safeTone()`，并在 javadoc 里写明"别和 `0xD0` 看齐"。

50. **★★★ 看门狗：「没活干」和「卡死」在状态编码上是同一种形状**（V48.4 踩，用户实测报的）
    用户原话：「**LCD 不会卡死了，但是延音时谱线会被刷掉**，即延音没办法保持谱线，
    **这个看门狗把延音状态当卡死给刷掉了**」—— 用户判断的方向完全正确。
    【根因 1：判据漏了"合法的原地踏步"】
      V47.2 的判据是 **`state` 连续 0.8s 不变 = 卡死**，注释里还写着
      "正常工作一次都不会触发" —— **这句话是错的**。
      频谱这一屏的状态机是 `S_BAR_WIN <-> S_BAR_DATA` 自循环，而"这一列要不要重画"
      由 `bar_dirty` 决定：
        · 有列脏 → 每画完一列都在两个状态间跳 → state 一直在变；
        · **没有列脏（高度恒定）→ `S_BAR_WIN` 的 phase0 只做
          「`play_idx` 自增 + `phase <= 0`」，state 一个时钟都不变。**
      实测（`sim_lcd_watchdog.py` 逐拍数出来）：每列 3 拍 = 6 时钟，
      一圈 60 列 = 360 时钟 = **7.2 µs** → **第 111,112 圈、正好 0.800s 攒满阈值**。
      ★ 也就是说：**静态画面每 0.8 秒就被整台重来一次**（S_POWER_ON → S_INIT → 全屏清），
        而"延音"正是"高度恒定不变"的典型场景 —— 所以用户只在延音时看见它。
      ★★ 一般化的教训：**看门狗判的必须是"有没有在干活"，不能只看状态编码。**
        "在等一个永远不会来的事件"（真卡死）和"本来就没活干"（空转）
        **在 state 这一维上完全同形** —— 必须找一个"真干活时一定会动"的量陪着看。
        这里的量就是 `play_idx`（空转一圈它必然走满 60 个值）。
    【根因 2：恢复路径不作废谱线缓存 —— 与 V48 那个 bug 同源，**同一个不变量又漏了一处**】
      误判/真触发之后走 S_POWER_ON → S_INIT → **全屏清一遍**，
      但 `bar_state[]` 里存的还是清屏前的高度，**和当前目标高度一模一样** →
      `bar_dirty` 恒 0 → **一列都不重画** → 屏幕就空在那里。
      ★ 这就是用户看到的"谱线被刷掉"。
      ★★ V48 已经为"切模式"补过三个作废点，**这次是第 4 个场景**：
        **凡是"清了屏 / 重开一屏"的地方，都必须作废 `bar_state`** ——
        这条不变量应该被当成清单逐处对照，而不是每次等用户报。
      ★★★ **而且第 4 个场景【不能用"再写一遍哨兵"实现】** —— 这是本次新踩的一个坑：
        照抄那三处"把 `bar_state` 整片写 `9'h1FF`"，实测 **Logic 从 46941 涨到 47988**
        （+1047，79% → **81%**）；查综合报告，涨的**全在 `u_lcd`**：
        Lut **3000 → 4023（+1023）**，其它模块一个数没变。
        原因：`bar_state` 是 **60 列 × 9 位 = 540 位**的数组，
        **再给它加一个写入源 = 每一位都多一级选择**（6 选 1 变成 7 选 1）。
        【正解】把"作废"这一位**从 9 位高度里拆出来单独放**：
          `reg [59:0] bar_bad;` —— 写入源只加在 **60 位**上，代价 ~60 个 LUT。
          `wire bar_dirty = bar_bad[play_idx[5:0]] || (bar_state[play_idx[5:0]] != tgt_q);`
          置位：看门狗分支 `bar_bad <= {60{1'b1}};`
          清除：**画完那一列的同一处** `bar_bad[play_idx[5:0]] <= 1'b0;`
        ★ 语义与哨兵**完全一样**（逐列自消耗、不需要任何窗口），只是省了 10 倍面积。
        ★★ 别把它和 V48 否掉的 `bar_force` 搞混：`bar_force` 是**一个**标志位 +
          **一个计时器**清它 —— "窗口要多长"这个假设正是当初翻车的地方；
          `bar_bad` 是**每列一位**、由画完那一列就地清掉。判据里专门写了这两条区分
          （`bar_dirty` 只允许出现 `bar_bad` 这一项，且 `force` 字样不许出现）。
    【修法（两条一起，缺一条都不行）】

      ② 看门狗分支把 `bar_bad` 整片置 1（第 4 个作废场景），恢复后逐列自动重画。
    【判据】`testfiles/sim_lcd_watchdog.py`（**21 项**）：
      · 逐拍数出"每列 3 拍 / 一圈 360 时钟"（不手抄常数）；

      · 恢复后重画：**不作废 → 0 列**（复现 bug）/ **作废 → 60 列**；
      · 反面例子：高度真在变时（新弹一个音）不作废也会重画 60 列
        —— 解释了用户为什么偏偏在"延音"时才看得见。
      ★ 另外 `sim_bar_cache.py` 里那句"作废点必须是三处"跟着改成

    【纪律】① 加任何看门狗/超时，先回答："**这段时间里，正常情况下它会不会合法地不动？**"
        会，就必须再找一个"干活时一定会变"的伴生量；

        把画面内容弄丢了：防住了 A，弄坏了 B）。

    【还有三样也一起漏了，都是"AGP 合并清单"替我们做的事】：
      · `com.spp.assistant.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`
        （targetSdk≥33 且代码里调 `registerReceiver` 时 AGP 注入；
         本工程 `BtSpp.java:207` 就有这么一处 → 缺了它在 Android 14 上会抛 SecurityException）；
      · `androidx.startup.InitializationProvider`（3 个 initializer 的 meta-data）；
      · `androidx.profileinstaller.ProfileInstallReceiver`；
      · 另外 `.MainActivity` 这种**相对包名的缩写**要展开成全限定名（AGP 会展开）。
      ★ 后三样来自**库自带的 AndroidManifest**，而 `aapt2 link` 只吃一份清单、
        **不会替我们合并库清单** —— 这是"离线拼包"和 AGP 最本质的差别。
    【★★ 真正该吸取的教训：验证没有"跟能装的版本对比"】
      我当时"验过了"的内容是：包名 / 标签 / 入口 Activity / 签名 / d8 缺类告警 ——
      **全都通过，但全都没和上一次确实能装的那个包比过**。
    【正解 · 已经做成常驻判据】`tools\_check_apk_manifest.py`：
      · 基准 = `tools\_ref\app-debug_20261007_gradle.apk`（**上次 Gradle 打的、确实能装的包**，
        特意留了一份当"金标准"，别删）；
      · 逐项对拍：package / versionCode / versionName / **sdkVersion / targetSdkVersion** /
        uses-permission / uses-feature / 组件（activity/receiver/provider + exported + authorities）/
        入口 Activity / **资源表各类型条目数（新包不许少于基准）**；
      · 基准里有的新包缺一项 → **直接判失败，不许出包**（`build_apk_offline.ps1` 最后一步就是它）。
    【纪律】① **离线复刻 AGP 的产物时，"AGP 替我做了什么"要列成清单逐项对**
        （合并清单、注入属性、R 类、资源覆盖…），别只补自己想到的那几个；
      ② **验证必须有一个"已知能工作的参照物"**：能装的老包、能跑的老固件、
        上一次的日志 —— 跟它比，比"我觉得这些检查够了"强得多。

52. **★★★ 离线打 APK：库的 R 类必须【按当前资源表重新生成】——错了编译期完全看不出来**（V48.4 踩）
    本机 Gradle 坏，安卓 APK 只能离线拼（`build_apk_offline.ps1`：aapt2 → javac → d8 →
    zip → zipalign → apksigner）。这一路上最阴的一个坑是**库的 R 类**：
    【事实】`androidx` 的 `classes.jar` 里**一个 R 类都没有**（AGP 打包时会剥掉；
      实测 `appcompat-1.6.1-runtime.jar` 里 `androidx/appcompat/R*` 条目数 = **0**），
      而库代码**运行时要读自己的 R**（那些字段在【库】里是非 final 的，不是编译期内联）。
      所以离线打包必须自己补一份 —— 不补就是 `NoClassDefFoundError`。
    【★★ 真正的坑】**不能直接复用上次 Gradle 留下的那份 `androidx_R.jar`**。
      逐条对拍发现 **整个 `id/` 表偏移了 1 位**（因为后来给布局加过一个
      `@+id/rbToneTrumpet`，id 类型整体后移）：
        `id/center`：旧 R = 0x7f08007f，当前表 = 0x7f080080
      直接用会让库代码**加载到错的资源**（找 `id/center` 拿到 `centerCrop`）
      —— **编译期一点提示都没有，只在手机上表现为界面错乱或崩溃**。
    【正解】`tools\gen_lib_R.py`：把旧 jar **只当"符号清单"**（类名/字段名是稳定的），
      **值一律从当前资源表重新解析**。唯一例外是 `styleable`：
      它在 R 里是 **`int[] 数组 + 下标`**，数组元素是 **attr 的 id**；
      实测 **attr 1154 条全部未移位**，所以那 19 个类**原样拷贝**（脚本里写了这条判据）。
    【怎么验的（javap 看不到数组内容，所以要真跑）】
      `tools\_check_gen_R.py` 把生成的 R 类**加载进 JVM 反射读**，逐条对拍：
      ① 每个 `int` == 当前资源表里的 id；
      ② 每个 styleable 数组元素：要么是框架 attr（0x01xxxxxx），要么是**当前表里的 attr id**；
      ③ 下标字段与数组长度自洽。
      实测 **12729 个 int + 329 个数组，零不一致、零野 id、零下标越界**。
      出包后再验一层：`apksigner verify` + `aapt2 dump badging` + d8 的
      **"Missing class" 告警数（本版为 0）** + `dexdump` 查关键类，
      并在 dex 里搜新功能串（`safeTone` 在、`clampTone` 不在 → 证明对齐那次改动也进包了）。
    【同一条路上的其它刺】
      · **d8 不接受目录**（`Unsupported source file type`），要先把 class 目录打成 jar；
      · `resources.arsc` / `classes.dex` 必须**不压缩**存（Android 11+ 要求），
        而 .NET / `Compress-Archive` 不能逐条控制压缩方式 → 用 Python 的 zipfile；
      · `& exe ... | Select-Object -First N` 然后读 `$LASTEXITCODE` 会**假失败**
        （`-First` 提前关管道，子进程写失败就返回非零）—— apksigner 明明通过了却被判成"签名失败"。
    【纪律】① **"编译期看不出来"的错，必须专门设判据**（这里就是"把类跑起来逐条比"）；
      ② **空对空的检查器会给出假绿**：本脚本第一版因为两条正则写错（`resource` 行有前导空格、
      库 R 字段**没有 `final`**），解析结果全是 0 条，却打印了 "ALL CHECKS PASSED" ——
      所以现在两个脚本都在"解析为空"时**直接判失败**，并**先证明它能红**再用它说全绿。

53. **★★★ 看门狗只能看它看得见的东西 —— "屏失步"和"画面本来就静态"在没有反馈时长得一模一样**（V48.5 踩）
    用户第二次实测报告（V48.4 之后）：
      「**还是容易在数据量多时卡死**，虽然在软件上**各个按键状态同步没问题**，
        但是就是 **LCD 卡住不动**」
    追问了三条，缺一条都推不出结论：
      · ① 卡住时**连换显示模式画面都不变** → 不是"某一块画面不更新"，是整屏不响应；
      · ② 画面**完全定住**；
      · ③ **看门狗毫无动作**（屏幕不闪、不清）。
    【推断链】③ 说"状态机还活着"（真卡死的话看门狗 0.8s 必触发，而且 V48.4 之后
      触发时会**顺手作废缓存**、屏幕会闪一下）；① + ② 说"屏这一侧不响应"。
      两条合起来只剩一个解释：**FPGA 状态机健康，是【屏自己失步了】**
      （排线受干扰 / 命令被截断 / 密集按键时 36 颗 LED 一起亮导致电流噪声上去 →
       屏那一侧抖了一下）。
    【★★ 结构性结论】**这类失效看门狗救不了，别在这儿加自动恢复**：
      · 看门狗看的是 `state`/`play_idx`，**它看不到屏**；
      · "屏失步"与"画面本来就是静态的"**在可见信息上一模一样** ——
        按时间瞎重置就退回"每 0.8 秒刷一次屏"的老毛病（V48.4 刚把合法的
        静态画面从误触发里摘出来，见坑 50）；
      · 想自动就得有**反馈**（读屏的 TE 脚 / 读回寄存器 / 屏回传），本设计没有。
    【解法】给一条**人来按**的逃生通道：`0xD1` 手动重置 LCD（见协议说明 §17.8）：
      重跑整张初始化表（表尾 `SLPOUT`+`DISPON`，足以救回被假命令搞乱的屏）
      + 全屏清 + 作废谱线缓存，而且**先等 1.0s**（比开机那 0.2s 长，
      给失步/抖动的屏更久稳定时间）。上位机两端各加一个「重置LCD」按钮。
      ★ 它用**翻转沿**跨到 lcd_master（两边同在 `clk_50m_ext` 域，本可直接连线）：
        电平方案万一接收侧正忙漏采一拍，用户这一下就白按了。
      ★ 优先级**高于看门狗**（用户明确按下的动作先满足）；
      ★ **必须顺手作废 `bar_bad`** —— 否则清完屏一列都不画（坑 50 那个坑）。
      ★ 它同时是**判别工具**：按一下能回来 = "屏被搞乱了"；按了还不回来 =
        "屏/排线/供电真坏了"（软件无能为力，别在这上面浪费时间）。
    【判据】`testfiles/sim_lcd_watchdog.py` 加了 [G] 段（**29 项**），其中最关键的一条是
      **"状态机健康时看门狗绝不会触发"** —— 把用户那句"毫无动作"复现出来了，
      也就证明了"不能指望看门狗救屏"这件事。
    【纪律】① 收到"某模块不动"的报告，**先分清是"逻辑死了"还是"外设失步"**：
        问三句就够 —— **换个输入它响应吗？看门狗有没有动作？上电重来能好吗？**
      ② **别给没有反馈的东西加自动恢复**：判不出来就别猜，
        宁可给一个"人按一下"的确定性通道（这也是用户自己要的）。
    【★★★ V48.5 之后的追加观察（很重要，别误判成"新版本更容易卡"）】
      用户上了 V48.5 之后报："**现在的 V48.5 的 LCD 更容易卡住了**"。
      这**不是**"新版本引入了新问题"，而是**旧版本一直在偷偷帮我们治**：
        · **V48.3 及以前**：看门狗**过于敏感**（只看 `state`），静态画面每 0.8 秒
          就误触发一次 → 那一轮 `S_POWER_ON → S_INIT → 全屏清` 正好也把
          **失步的屏重新初始化了一遍** —— 于是"屏失步"这个故障被掩盖了
          （用户当时看到的是"延音时谱线被刷掉"，那就是误触发的副作用）。
        · **V48.4 起**：看门狗精确了（"没活干"不再算卡死）→ 误触发没了
          → **屏失步不再被自动治好** → 表现成"一直卡住"。
      ★ 一句话：**"更容易卡"= "不再自动恢复"**。同一个故障，之前被另一个 bug 盖住了。
      ★★ 由此还有一条通用教训：**修掉一个"过于激进的自愈机制"时，要想到
      它可能在掩盖别的问题** —— 修之前先问一句"它一直在替我做什么？"。

49. **★★★ TNS 汇总表【不覆盖跨域路径】—— 只看 TNS 会漏掉违例**（V48.3 踩）
    V48.3 第一次构建（18:04）的报告里：
      · `Total Negative Slack Summary` **六项全是 0.000 / 0 端点**（看着完美）；
      · 同一份报告却写着 `Numbers of Setup Violated Endpoints = 1`、
        `Numbers of Hold Violated Endpoints = 6`；
      · 路径表里明明白白：`SETUP slack = -0.155ns`（CLKOUT0 -> CLKOUT1）。
    ★ 根因：那 4 条 setup、6 条 hold 违例**都是跨域路径**
      （CLKOUT0 <-> CLKOUT1，见坑 48 后面那段关于 `set_clock_groups` 的说明），
      而 TNS 表是**按单个时钟**归行的 —— 跨域路径归不到任何一行上，
      于是"表里全 0"和"实际有违例"同时成立。
    【纪律】**构建完判时序必须同时看三处，缺一条都不算验过**：
      ① `Total Negative Slack Summary`（分域 TNS）；
      ② `Numbers of Setup/Hold Violated Endpoints`（**全局计数，跨域也算**）；
      ③ 路径表里 slack < 0 的条目，**以及最差那几条离 0 有多近**
         （V48.2 最差 hold 只有 +0.001ns —— "通过"和"没过"就差一根头发丝，
          下一次布局扰动就可能翻过去，所以必须看余量而不只看正负）。
    ★ 另外一个坑：**这三处数字只有 `impl\pnr\music_tr_content.html` 里有**，
      `music.rpt.html` / `music.rpt.txt` 只有资源表和引脚表。
      归档脚本原先不带它 —— 于是上一版归档后**"时序全 0"这句话无法复核**。
      V48.3 起 `make_version_archive.ps1` 会把它一起归档。
    ★ 顺带记录（**没修，因为 SDC 是红线**）：`music.sdc` 里
      `set_clock_groups -asynchronous -group [get_clocks {clk*}]`
      的本意是把三个域标成互异步，但 PLL 派生时钟的真实名字是
      `u_pll/u_pll_0/PLLA_inst/CLKOUT0.default_gen_clk`（**不以 clk 开头**），
      所以 `clk*` 只圈到了 `clk_50m` 一个时钟 —— **这句没起到它注释里说的作用**，
      跨域同步器输入那类"假违例"一直是靠**碰巧有正余量**在过关。
      证据：V48.3 报告里仍能查到 `CLKOUT0 -> CLKOUT1` 的跨域路径被分析。
      本版的做法是在 **RTL 侧把跨域链修短**（插一拍，见版本说明 §1 ③），**不碰红线**；
      要不要真正修 SDC，留给用户决定。

55. **★★★ 提高采样率时，第一件事是把逻辑分成【时间语义】和【内容】两类**（V49 踩出了这个方法论）：
    `sample_en`（每个采样点一拍）这句话里其实混着两种东西：
      · **内容**：相位累加、波表读相位、逐键包络乘法、KS 弦推进 —— 必须跟**采样率**走；
      · **时间**：包络计时、滑音、颤音/合唱/延迟/混响的时间常数、LCD 扫描、AGC 斜坡 ——
        必须跟**真实时间**走，跟采样率无关。
    采样率一翻倍，如果全都"跟着走"，包络衰减时间会正好减半、混响尾巴短一半 ——
    **板上只表现为"能响但不对"，靠耳朵很难当场判定是哪一类错了**。
    V49 的做法是引入控制节拍 `ctrl_en`（每 2 个采样点 1 拍 = 原来的 48.828 kHz 等效），
    把"时间语义"的 16 处整体改挂它 —— 于是这些量的时间常数**逐位不变**。
    ★★ **最阴的一处是"两类混在同一个 if 里"**：`top.v` 里滑音斜坡和相位累加原本共用
      `if (sample_en)`。整块改成 `ctrl_en` → 音高掉一个八度；整块不动 → 滑音快一倍。
      **必须拆成两个块**（V49 已拆，并在两处都写了注释说明为什么）。
    ★ 落地手段：写一个**结构扫描式**的自检（V49 是 `sim_v49_rate.py` 的 [H] 段），
      逐条断言"某条语句所处的使能必须是 sample_en / ctrl_en"，把分类错误钉死在回归里。

56. **★★★ 采样率一变，所有"按半个帧设计"的东西都要跟着缩**（V49 踩）：
    V44 的延迟测量脉冲当初特意做成 **10µs = 半个音频帧**（帧周期 20.48µs），
    理由写在注释里："脉冲比被测量间隔还宽就会糊在一起量不出来"。
    V49 把帧周期压到 **10.24µs** 之后，这条注释里的前提就失效了 ——
    10µs 脉冲几乎占满一整帧，T1→T2 只有 5.12µs，两段会糊成一片。
    **治法**：脉冲跟着缩到 **2µs**（≪ 5.12µs），并在自检里加一条**相对判据**
    （`脉宽 < 半个帧`，而不是写死"=10µs"）。
    ★ 通用教训：凡是"宽度/阈值/延时"是按某个速率算出来的，改速率时都要回头看一眼
      **它当初为什么取这个值**——注释里那句"上限是××"就是唯一的线索。

57. **★ 延迟线加深可能是【免费的】—— 别把"当前尺寸"当成硬上限**（V49 的好消息）：
    吉他弦模型在 48 kHz 下最深只要 444 格（512 格 RAM 够用），
    96 kHz 下要 **888 格**，第一反应是"要加一块 BSRAM / 做不到"。
    实际算一下位宽：**1024×16 = 16 Kbit，而一块 SDPB 是 18 Kbit**
    → 加深到 1024 格**仍然只占 1 块**，实测 BSRAM 从头到尾都是 **87/118**。
    ★ 同类判断在 V49 里还有一处：36 份波表看着"每键一块 BSRAM"，
      实际是 **LUT 实现（36×122 = 4392 LUT，0 块 BSRAM）**，
      `syn_ramstyle="block_ram"` 没生效 —— **别用注释里的资源描述去算资源账，
      要用 `impl\gwsynthesis\music_syn_resource.html` 的逐实例表**。
