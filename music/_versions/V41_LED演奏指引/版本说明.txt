V41 —— LED 演奏指引（36 颗灯跟着乐谱和手弹走）
========================================================================

一、这一版做了什么
------------------------------------------------------------------------
把独立工程 D:\...\Documents\60k\LEDs 里【已经实机点亮确认】的 LED 驱动
接进主工程，做成"演奏指引"：

    · 乐谱这一格要弹的键（midi_keys）→ 暗（DUTY_SCORE = 0x28，约 16%）
    · 手按下去的键（hand_mask）      → 亮（DUTY_HAND  = 0xC0，约 75%）

两者同时成立时【手弹优先】—— 按对了键那颗灯由暗变亮，
等于给你一个即时回执（"这颗按对了"）。

★★ 顺手把 CLKOUT1（UART+LCD）那条【历史遗留的临界时序路径】真正治好了
   —— 见第四节。这一条比 LED 本身更值钱：
   V40 的 CLKOUT1 只有 +0.014% 余量（50.007MHz / 约束 50MHz），
   现在有 +16%（58.0MHz），三个时钟域 TNS 全 0。

三、架构决定：为什么整个 LED 模块放在 clk_audio 域
------------------------------------------------------------------------
交接文档的待办 -3 原本写着"I2C 要挂在 CLKOUT1 域上，所以要先解决 -2 的
CLKOUT1 余量"。**这一版把那个前置依赖直接消掉了**：

    · led_guide 要用的两根线 midi_keys_aud 和 hand_mask
      【本来就已经在 clk_audio（12.5MHz）域】——
        midi_keys_aud = midi_keys_s2，是 top.v 里早就做好了的、
        从 clk_50m_ext 过来的两级同步；
        hand_mask 更是在音频域里生成的。
      → 所以【一处跨时钟同步都不用新增】。
    · 而 CLKOUT1 域 V40 实测余量只剩 0.014%，往那儿加逻辑很危险。
    · 音频域 Fmax 是 27.6MHz（2.2 倍余量），放这里最安全。
    · I2C 时钟只要 ≥ 400×SCL 就够：12.5MHz / 100kHz = 125。
      QUARTER = 12_500_000/(100_000×4) = 31 → 实际 SCL ≈ 100.8kHz
      （芯片上限 400kHz，和独立工程一样保守）。

★ I2C 走的是【第二条总线】，和 ADS1115 那条完全独立：
      ADS1115（摇杆）: i2c_scl = G22 / i2c_sda = V19   ← 原有的
      LED 指引        : led_scl = V17 / led_sda = W17   ← 本次新增
  V17/W17 在本工程里原本是空脚（music.cst 里没有），而且已经实测确认：
  独立工程就是用这两个脚把 36 颗灯点亮的。

四、★★ CLKOUT1 时序治本（这一版最重要的一条）★★
------------------------------------------------------------------------
【现象】加入 led_guide 之后第一次构建（V41 第 2 次），CLKOUT1 退化：
        约束 50.000MHz，实测只有 48.039MHz，TNS = -4.938ns / 8 个端点。
        （V40 是 50.007MHz —— 也就是说它本来就贴在刀刃上，
          任何改动都会把它压过线。这不是 led_guide 逻辑的问题：
          它在音频域，一个门都不在 CLKOUT1 上。）

【根因】报告里 8 条 setup 违例【全是同一条路径】：
        u_lcd/wave_buf.../DO[1]  ->  u_lcd/cur_data_*_s1/D
        数据延迟 20.1~20.7ns，周期 20ns。
        也就是 LCD 波形显示里，BSRAM 输出之后挂了【21 级组合逻辑】：
            BSRAM 输出 -> 取绝对值 -> 16 位桶形移位(>> wave_sh)
              -> 补符号 -> 17 位加中线 -> 上下限幅 -> 线段比较
              -> 像素字节 -> cur_data
        这正是交接文档里说的"CLKOUT1 上剩一条 u_lcd 的临界路径（历史遗留）"。

【治法】沿用本文件里【已有的先例】——V17c 就干过一次同样的事
        （把 peak_msb 打一拍，把 22.5ns 从中间切断，注释里写着"时序治本，别删"）。
        这次在同一串上再切两刀：

          第一刀：wave_y0/y1 打一拍  ->  wave_y0_r / wave_y1_r
          第二刀：缩放结果打一拍    ->  v0_sc_r / v1_sc_r
                  （★ 符号位 v0_sgn_r 必须【同步】打一拍 ——
                    否则符号比幅值早一拍，负半周会画反）

【为什么一定安全】（不是"应该没问题"，是有依据的）
    1. 读地址 wave_rd_addr0 = frame_wr - 320 + wave_col，只跟 wave_col 走。
       frame_wr 是"一帧开始时锁住的写指针"（lcd_master 第 246 行的注释），
       【不是连续推进的指针】，所以一整列里 wave_v0/v1 和 wave_sh 都不变
       —— 这两级寄存器每一拍寄存的都是同一个值，只是晚 20ns 生效。
    2. 时序上也够：wave_col 一整列才 +1 一次，之后 state 先跳到 S_WAVE_WIN
       把整条窗口命令发完（WIN_COUNT=11 字节 = 88 拍）才开始读第一个像素；
       而 wave_y0 在 wave_col 变化后 3 拍内就稳定。
       一整列 ≈ 5760 拍，这 3 拍占 0.05% —— 显示上看不出来。
    3. 下游一个字没动：wave_seg_lo/hi、wave_draw_seg、wave_pix_hi/lo 全部照旧，
       波形的"哪一列用哪两个采样点"逐位不变。

【结果】（两次构建都验过，见第六节）
        CLKOUT1:  48.039MHz -> **58.046MHz**（余量 16%）
        CLKOUT1 TNS: -4.938ns/8 条 -> **0.000 / 0 条**
        最长路径也不在 LCD 里了 —— 现在全工程最长的是 clk_50m 域的一条
        js_z -> vel_send，slack 还有 +2.435ns。

★ 顺带说明：交接文档待办 -2 建议的"把超时阈值改成 2 的幂 + 合并两个计数器"
  治不了这个病 —— 实测 UART 那几条超时路径 slack 有 +2.0ns，是【通过】的。
  真正的瓶颈就是上面这条 LCD 波形链。所以 -2 那条待办可以降级了。

五、上电后应该看到什么 / 怎么确认接线顺序
------------------------------------------------------------------------
  · 上电后 LED 全灭（初始化 76 笔里 PWM 写的是 0）。
  · 按琴键 -> 对应那颗灯亮到 75%。**松手就灭。**
  · 播放乐谱 -> 当前时间格要弹的键以 16% 的暗亮度亮着。
  · 手按到乐谱要的那个键 -> 那颗灯由暗变亮（回执）。

★★ 接线顺序自检（不用改代码、不用额外测试模式）：
    逐个按琴键，看亮的是不是【同一个编号】的灯。
    如果 36 个都对 -> 现在的恒等映射就是对的，什么都不用改。
    如果不对 -> 把 src\led_guide.v 里 ch2key() 的 case 改成对应的置换表，
                重新构建即可，别的地方一个字都不用动。
                （例：若"第 0 路 LED 其实接的是键 5"，就写 6'd0: ch2key = 6'd5;）
