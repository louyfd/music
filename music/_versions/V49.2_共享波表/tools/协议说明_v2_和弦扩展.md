# 第 0 章  一句话总结

v1（现状）只能"一个字节 = 一个音 = 一拍"，所以**放不了和弦**。
v2 在不改动任何 v1 语义的前提下，新增两个控制字节 0xC0 / 0xC1 作为
**和弦帧头 / 帧尾**，把"一拍里同时响的多个音"包成一组，仍然占一拍。

    v1:  [16×FF] AA  05 05 09 09 ...                        FF
    v2:  [16×FF] AA  05 05 C0 05 09 0C C1 09 ...            FF
                          └── 这一拍同时响 05/09/0C 三个音 ──┘

★ 老固件收到 v2 帧：0xC0/0xC1 被静默丢弃，和弦被当作连续单音播放
  （节奏不准，但不会死机、不会误响）。
★ 新固件收到 v1 帧：行为与现在**逐位相同**。
  这就是"不冲突、不破坏"的含义。

# 第 2 章  v1 协议完整规范（现状，必须保持不变）

## 2.1 帧结构

```
[前导冲刷] [开窗] [事件流] [帧尾]
  16×0xFF   0xAA     ...     0xFF
```

## 2.2 字节语义（v1，36 键单音）

| 字节 | 含义 | 行为 |
|------|------|------|
| `0x00`~`0x23` | 音，值 = **键号** = MIDI 音符号 − 48 | 写进 BRAM，**不发声**，原样回显 |
| `0xEE` | 休止符，占 1 拍 | 写进 BRAM，原样回显 |
| `0xAA` | 清空 / 开窗 | `armed<=1`、写指针归零、长度清零（= 停播）；**不回显** |
| `0xFF` | 帧尾 | 关窗、长度锁定、**从头开播**、回传一个 `0xFF` |
| 其它 | 未分配 | **丢弃**：不入 BRAM、不回显 |

## 2.4 时序与播放行为

| 项目 | 值 | 出处 |
|------|-----|------|
| 事件节奏 | **0.5 秒 / 事件**（`PLAY_DIV = 26'd25_000_000`） | `uart_packet_echo.v:183` |
| 每音按住 | **0.2 秒**（`HOLD_DIV = 26'd10_000_000`），余 0.3s 留白让包络衰减 | `:194` |
| BRAM | `note_buf[0:255]`，256 字节 | `:79, 162` |
| 直通模式 | `BYTE_STREAM = 1'b0`（默认：存 BRAM，等 FF 再放） | `:76` |
| 一帧上限 | 256 字节（v1 即 256 拍 = 128 秒） | — |

**`HOLD_DIV` 必须 < `PLAY_DIV`**：`top.v` 的包络要求 gate 连续低满 8ms 才承认
"松手"，否则同一音连按两次不会重新起音（小星星的 `05 05` 会听成一下）。

**发声链**：`uart_packet_echo.midi_keys[35:0]` → `top.v:3247-3257` 两级同步
→ `midi_keys_aud` → `top.v:519` `key_mask = pressed_mask | auto_keys | midi_keys | bt_keys`
→ 36 路独立 ADSR + DDS。**与物理琴键是 OR 关系，互不干扰。**

★ 顺带说明：`midi_keys` 本来就是 **36 位掩码**，理论上天然支持同时多个键。
  真正把和弦挡住的只是"一个字节只能表示一个键号"这个编码层。v2 解决的就是它。

## 2.5 为什么前导必须是 16×0xFF 再 0xAA（顺序不能反）

蓝牙链路刚建立/串口刚打开时线上有被截断的半个字节，会被 UART 状态机当起始位
凑成**假字节**。`0xFF` 的特殊性在于它**同时**是"关窗 + 清 BRAM + 停播"，
所以灌一串之后 BRAM 一定干净、播放一定停；而 `0xAA` 只能清指针，
**管不了 `AA` 之后才到的脏字节**。

```
FF×16  →  AA  →  乐谱  →  FF
└冲掉一切┘ └清指针┘        └开播
```

# 第 3 章  字节空间占用表（决定和弦标记能用哪些值）

| 区间 | 个数 | 状态 |
|------|------|------|
| `0x00`~`0x23` | 36 | **已占用** = 音 |
| `0x24`~`0xA9` | 134 | 未分配（当前被丢弃）<br>其中 `0x5A`/`0x5B`/`0x5C`/`0x5D` **已分配给演奏录音回传**（第 9 章）<br>其中 `0x5E` **已分配给节拍器状态回传**（第 15 章） |
| `0xAA` | 1 | **已占用** = 清空/开窗 |
| `0xAB`~`0xED` | 67 | 未分配（当前被丢弃） |
| `0xEE` | 1 | **已占用** = 休止符 |
| `0xEF`~`0xFE` | 16 | 未分配（当前被丢弃） |
| `0xFF` | 1 | **已占用** = 帧尾/开播 |

**结论：和弦标记必须从"未分配"区里取。**

### 候选评估

| 候选 | 是否可用 | 评价 |
|------|---------|------|
| `0xC0` / `0xC1` | ✅ **采用** | 助记好（Chord 0/1）；远离 AA/EE/FF；老固件静默丢弃 → 优雅降级 |
| `0xA0` / `0xA1` | ✅ 可用 | 也安全，但离 0xAA 近，误码时更危险 |
| `0x24` / `0x25` | ✅ 可用 | 紧贴音域，将来扩音域到 48 键会冲突，不推荐 |
| `0xF0` | ❌ 不推荐 | MIDI 里是 SysEx 起始，调试时容易看错 |
| `0xAA`/`0xEE`/`0xFF` | ❌ **冲突** | 已占用 |


# 第 4 章  v2 协议规范（和弦扩展）

## 4.1 新增控制字节（定稿）

```verilog
localparam [7:0] CHORD_ON  = 8'hC0;   // 和弦帧头
localparam [7:0] CHORD_OFF = 8'hC1;   // 和弦帧尾
localparam [7:0] DUR_EXT   = 8'hC2;   // 时值延长：后跟 1 字节 N = 本事件再延长 N 个时间格
localparam [7:0] SET_TICK  = 8'hC4;   // 设置时间格：后跟 3 字节 LE = 一个时间格多少微秒
localparam [7:0] SET_REL   = 8'hC5;   // 设置释音提前量：后跟 3 字节 LE = 每事件末尾提前多少微秒松键
```

★ 这 5 个字节全部落在"未分配区"（§3），且**老固件会静默丢弃**，所以是平滑升级。

## 4.2 文法（BNF，定稿）

```
帧      := 前导 开窗 设置* 事件* 帧尾
前导    := 0xFF × 16
开窗    := 0xAA                       // 同时把"设置"复位成默认值
设置    := SET_TICK 微秒(3B LE)
         | SET_REL  微秒(3B LE)
帧尾    := 0xFF
事件    := (单音 | 休止 | 和弦) DUR_EXT*
单音    := 音号
休止    := 0xEE
和弦    := 0xC0 音号{1,36} 0xC1
DUR_EXT := 0xC2 N                     // N = 0..255，本事件时长 = 1 + N 个时间格
音号    := 0x00 .. 0x23
```

**语义要点**

| 要点 | 说明 |
|------|------|
| **时间格（tick）** | 协议里唯一的时间单位。默认 **500000 µs（0.5 s）**，由 `SET_TICK` 改。上位机按曲谱 BPM 与最短时值自动算（取所有时值的最大公约数） |
| **事件时长** | `1 + ΣN` 个时间格。默认（无 `DUR_EXT`）= 1 格 |
| **和弦** | 一个事件里同时起音的多个音，时长规则与单音完全相同 |
| **释音提前量** | `SET_REL`，默认 **300000 µs（0.3 s）**。事件末尾提前这么多松键，剩余时间留白。<br>→ 500ms 格 + 300ms 提前 = **响 0.2 s、留白 0.3 s，与 v1 现状逐位等价** |
| **松键间隙下限** | FPGA 内部强制留 ≥ **10 ms** 静音（`top.v` 包络要求 gate 连续低满 8 ms 才承认松手），所以连着的同音一定会重新起音 |
| **时间格下限** | FPGA 内部把时间格钳到 ≥ **20 ms** |

**★ 操作数不受控制字节解释**

`DUR_EXT` 的 N、`SET_TICK`/`SET_REL` 的参数字节是**原始操作数**：
即使它们的值恰好是 `0xAA` / `0xEE` / `0xFF` / `0xC0`，也**一律当数据**，绝不解释成控制字节。
（接收器用一个"待收操作数"计数器保证这一点。这是本协议的硬性规定，不可省略。）

**唯一对 v1 的"变动"：新增 4 种控制字节 + 时值模型。单音/休止的字节与音高语义一字未改。**

## 4.3 示例

### 例 1：v1 老帧（不带任何新字节）—— 行为必须与现在逐位相同

```
FF×16  AA  05 05 09 09 0A 0A 09 EE 08 08 07 07 06 06 05  FF
```
时间格 = 默认 500ms，每个事件 1 格，释音提前 = 默认 300ms
→ 每个音响 0.2s、留白 0.3s，**与 v1 完全一致**。

### 例 2：带和弦（只有和弦扩展）

```
FF×16 AA C0 05 09 0C C1 09 EE C0 05 0C C1 FF
          └── 事件1 ──┘  事件2 事件3 └─ 事件4 ─┘
          三音同时响     单音  休止    双音同时响
```

### 例 3：速度可调 + 真实时值（推荐用法，BPM=90、时间格=八分音符）

BPM=90 → 四分音符 = 666667µs；时间格取八分音符 = **333333µs**（3 字节 LE = `15 16 05`）

```
FF×16
AA
C4 15 16 05                     ← SET_TICK = 333333µs（0.333s/格）
C5 3C 04                        ← SET_REL  = 300000µs（0.3s 提前量，保持断奏手感）

05 C2 01                        ← 事件1：C4 四分音符 = 1+1 = 2 格 = 0.667s
09 C2 01                        ← 事件2：同上
0A C2 05                        ← 事件3：二分音符 = 1+5 = 6 格 = 2.0s
EE C2 01                        ← 事件4：休止 2 格
C0 05 09 0C C1 C2 05            ← 事件5：三音和弦，二分音符 = 6 格
FF
```

### 例 4：连奏（legato）—— 想把音按住就连长提前量调小

```
C5 10 27                        ← SET_REL = 10000µs = 10ms（最小间隙）
```
此时每个事件的 gate = 事件时长 − 10ms，音符之间几乎没有缝 → 连奏。

## 4.4 边界情形（FPGA 侧必须按此处理，不能死机）

| 情形 | 处理 |
|------|------|
| `0xC0 0xC1`（空和弦，0 个音） | 等价一个**休止格**（不发声） |
| 和弦内出现 `0xEE` | **忽略**，不参与掩码（上位机不应产生） |
| 和弦内又出现 `0xC0` | 视为重新开始收集；前一组的音**参与本组** |
| 和弦内出现 `0xC2 N` | 跳过这 2 字节（当作畸形输入，不当音号） |
| 和弦内出现 `0xFF`（未闭合） | **已收集的音照常发声**，该事件结束 → 不静默丢音 |
| 和弦内音号重复 | 掩码 OR 后自然去重，无副作用 |
| 和弦音数 > 36 | 不可能：键号只有 36 个，掩码固定 36 位 |
| `DUR_EXT` 的 N 使总时长 > 256 格 | 计数饱和在 256 格 |
| `SET_TICK` / `SET_REL` 在事件之后才发 | 只影响其后的事件；上位机应放在帧首（`0xAA` 之后） |
| `SET_TICK` 的值 < 20ms | FPGA 内部钳到 20ms |
| `SET_REL` 的值 ≥ 时间格 | 内部钳到 `时间格 − 10ms`，保证每事件末尾仍有 ≥10ms 静音 |
| 帧被截断（只发一半） | 因为没有 `0xFF`，**永不开播**（`armed` 仍为 1，等下一帧的 `0xAA` 重置） |

## 4.5 帧长与容量（**定稿：不再存字节流，改成"每事件一条记录"，上限 1024 事件**）

> ★★ 落地后修正（本文档原稿写的是"扩容到 4096 字节"）★★
> 实际实现换了个思路，容量口径也跟着变了 —— 以本节为准。
>
> 原稿的思路是"把收到的**字节流**存进 BRAM，播放时再逐字节解析"。
> 真做下来发现：要和弦就得在播放时向后扫描到 `0xC1`，于是 BRAM 出现
> **两个读地址**（当前字节 + 前瞻），单口 RAM 推断不出来，直接退化成一堆触发器。
>
> **改成：接收时就把和弦拼好，每个时间格只存一条记录**
>
> | 数组 | 内容 | 位宽 × 深度 |
> |------|------|-------------|
> | `slot_mask[i]` | 第 i 格要点亮哪些键（和弦 = 多个位） | 36 × 1024 |
> | `slot_dur[i]`  | 第 i 格占几个时间格（1..255） | 8 × 1024 |
>
> 于是播放器退化成一句 `midi_keys <= slot_mask[当前格]`，
> 而且**字节数根本不再是容量限制** —— 接收是流式的，不缓存原始字节。

| 项目 | 值 |
|------|-----|
| 存储 | `slot_mask[0:1023]` + `slot_dur[0:1023]`（≈ 44 Kbit） |
| 事件数上限 | **1024**（`SLOT_MAX`）；下发超过就按**事件边界**截断，绝不切开和弦 |
| 单事件时长上限 | **255 格**（`slot_dur` 8 位；`0xC2` 的 N 会饱和到 255） |
| 字节数 | **无上限**（只有 9600 波特率的发送耗时：约 1.04 ms/字节） |
| 指针位宽 | `wr_slots` / `frame_slots` / `rd_slot` 都是 **11 位**（0..1024） |
| 单事件字节数 | 单音 1、和弦 n+2、时值每 255 格再加 2；都很小 |
| 对 `top.v` 的影响 | **零**。`play_start` / `play_len` / `score_*` 一律恒 0（那条 LCD 自动演奏链保持死链） |
| 参考量级 | 小步舞曲（252 事件 / 768 格 / 3 分半）= **1994 字节，2.1 秒发完** |

★ 综合结果佐证（Gowin V1.9.11.03，`gw_sh` 全流程）：
  `slot_mask` / `slot_dur` 两个数组都被 `Extracting RAM` 正常推断成 RAM，
  Register 只有 5636/60780（10%）；若推断失败会涨到 4 万以上。

## 4.6 回显规则（v2 定稿）

| 收到的字节 | 回显 |
|-----------|------|
| 音号 / `0xEE` | 原样回显 |
| `0xC0` / `0xC1` / `0xC2` 及其操作数 N | **原样回显**（便于上位机逐字节核对） |
| `0xC4` / `0xC5` 及其 3 个参数字节 | **原样回显** |
| `0xAA` | **不回显**（与 v1 相同） |
| `0xFF` | 回显一个 `0xFF`（与 v1 相同） |
| 其它（未消费的脏字节） | 不回显（与 v1 相同） |

**统一规则：凡是被本模块"消费"了的字节都回显，只有 `0xAA` 例外。**

★ **上位机绝不能把回显再发回去**（25K 那版 `1.py` 就是这么造成死循环重播的）。
  上位机校验完回显后必须丢弃。


# 第 5 章  兼容性证明

| 方向 | 情形 | 结果 |
|------|------|------|
| 老固件 ← v2 帧 | `0xC0/0xC1/0xC2/0xC4/0xC5` 不在 `(<=0x23) \|\| (==0xEE)` 条件里 → 不写 BRAM、不回显 | 所有新字节与它们的操作数**全部被丢弃**；和弦里的音被当成**连续单音**播放，`0xC2` 的操作数 N 也可能被当成音号（**可能冒出杂音**）→ 所以**新协议帧不要发给老固件** |

| 键号语义 | 未改 | `0x00~0x23` 含义、`delta[]` 频率表全部不动（键号 ↔ 音高的对应见 §2.3，**不是** MIDI−48） |

★ **升级顺序建议：先烧 FPGA 新固件，再用新上位机。**（反过来会冒出杂音）
★ 老固件 ↔ 老上位机 这一对始终可用，不受影响。


# 第 6 章  上位机侧转换规则（乐谱/MIDI → v2 帧，定稿）

## 6.1 时间模型：先定时间格，再算时值

```
① 读节拍：BPM（简谱的"每分钟多少拍" / .mid 的 set_tempo）
   一拍时长(µs) = 60_000_000 / BPM

② 找最短时值：把所有音符时长（以拍为单位）取【最大公约数】
   例：只有四分/八分/二分 → GCD = 1/8 拍
       有附点四分(=3/8拍) + 八分 → GCD = 1/8 拍
       有三连音 → GCD = 1/12 拍

③ 时间格(µs) = 一拍时长(µs) × GCD分数
   例：BPM=90（一拍 666667µs）、GCD=1/8 → 时间格 = 83333µs

④ 每个事件的时长(格) = 音符时长(拍) / GCD分数
   八分音符 → 1 格；四分 → 2 格；附点四分 → 3 格；二分 → 8 格

⑤ 帧首发 SET_TICK(时间格µs) 与 SET_REL(释音提前量µs)
   释音提前量默认 300000µs（= 保持 v1 的断奏手感）；
   想连奏就改小（最小 10000µs）
```

★ 时间格下限 **20 ms**（低于此值 FPGA 会钳位）；实际几乎不会碰到。
★ 取 GCD 后如果格数太多导致一帧装不下，就把 GCD 放大一档（牺牲一点精度换容量），
  并在预览里告警。

## 6.2 事件装配

1. 把音符按起始时间量化到时间格格位：`格位 = round(t0 / 时间格)`。
2. 同一格位上的音集合：
   * **1 个音** → `音号`
   * **≥2 个音** → `0xC0` + 各音号 + `0xC1`（**这就是"和弦"**）
   * **0 个音** → `0xEE`
3. 时值：`N = 时长(格) − 1`；`N > 0` 时在事件后追加 `0xC2` + `N`（N 最大 255）。
4. `音号 = MIDI 音符号 − 48`；超出 `0..35`：
   默认**丢弃并计数告警**；可选"±12 折叠到音域内"。
5. 拼帧：
   ```
   bytes([0xFF]*16) + b'\xAA' + settings + body + b'\xFF'
   settings = SET_TICK + 3字节LE + SET_REL + 3字节LE
   ```
6. 事件数超过 **1024**（`SLOT_MAX`）→ **截断点必须对齐到事件边界**
   （绝不能把一个和弦从中间切开），并在报告里告警。
   ★ 注意口径是【事件数】不是字节数：接收是流式的，不缓存原始字节。

## 6.3 连音 / 断音

| 想要的效果 | 做法 |
|-----------|------|
| 断奏（默认，同 v1） | `SET_REL = 300000`（每事件末尾留 0.3s） |
| 自然连奏 | `SET_REL = 10000`（只留 10ms 安全间隙） |
| 显式停顿/换气 | 插 `0xEE`（1 格静音）；`0xEE C2 01` = 静音 2 格 |
| 长音 | `音 + C2 (N−1)` —— **真正按住 N 格**，不再是"响一下 + 补静音" |

★ **连着的同音必须保留**（`05 05` 不能去重）—— 板子靠"松手再按"重新起音。
  在 `SET_REL ≥ 10ms` 的前提下这一点自动成立。

# 第 9 章  演奏录音回传（`0x5A` / `0x5B` / `0x5C` / `0x5D`）

板子把**手弹的每一个动作**回传给上位机，上位机合成 MIDI 并在电脑上放出来。
和前面几章方向相反：**第 4 章是上位机 → 板子（发谱），本章是板子 → 上位机（回传）**。

## 9.1 四个新字节

```verilog
localparam [7:0] REC_EV_HEAD  = 8'h5A;   // 板子 → 上位机：一个录音事件
localparam [7:0] REC_ST_HEAD  = 8'h5B;   // 板子 → 上位机：录音开关状态
localparam [7:0] REC_CMD_BYTE = 8'h5C;   // 上位机 → 板子：翻转录音开关
localparam [7:0] REC_FX_HEAD  = 8'h5D;   // 板子 → 上位机：效果开关状态
```

## 9.2 帧格式

```
事件帧： 0x5A | mask(36 位, 小端 5 字节) | dt(2 字节, 小端, 单位 10ms)   共 8 字节
开关帧： 0x5B | 0x00 或 0x01                                            共 2 字节
效果帧： 0x5D | 8 位效果开关                                            共 2 字节
开关指令：0x5C                                                          共 1 字节
```

| 字段 | 含义 |
|------|------|
| `mask` | 那一刻 `sounding_mask` 的 36 位快照。**第 36 位以上恒为 0**（只有 36 个键）—— 上位机就拿这一点当帧校验 |
| `dt` | 距**上一个事件**过了多少个 10ms。累加才得到绝对时间；单帧最大 65535×10ms ≈ 655 秒 |
| 采样 | 板子每 10ms 采一次 `sounding_mask`，**一变就发一帧**（不变不发） |

**★ `mask` 采的是"门控"，不是"包络输出"：**

```
key_mask          = 手指按下了哪些键
sounding_mask_aud = key_mask | sustain_latch_aud   ← 回传的就是这个（门控）
sounding_mask     = env[键] != 0                   ← 这个【不能】用，见下
```

`sounding_mask`（包络非 0）看着更"实际"——它带着释音尾巴——但**不能用**：

| 问题 | 后果 |
|------|------|
| 尾巴没走完就重击同一个键 | 包络非 0 一直成立，掩码连着不变 → **两下被并成一个长音**。实测：音高 62 弹两次（1000ms / 2600ms）合成了一个 3730ms 的长音 |
| 掩码里"一直为 1"的键 | 会在**每个事件**上重新触发一遍 → 8 个音弹出来是 **32 次起音** |

门控信号的起音 / 放音 / 重击边沿才是真的，延音锁存也天然在里面
（`sounding_mask_aud` 本身就 = `key_mask | sustain_latch_aud`）。

**释音尾巴由上位机按 RTL 的常数补**（`top.v`）：

```
松手 → 包络要先连续低满 8ms 才承认松手（gate_off_cnt[3]）
     → env 每 env_rel_div 个采样点降 1，从 env_sus_lv 降到 0

默认音色：255 × 280 / 48828 ≈ 1.46 秒
笛子音色：200 ×  61 / 48828 ≈ 0.25 秒
（采样率 SAMPLE_RATE_HZ = CLK_FREQ_HZ / FRAME_DIV = 12_500_000 / 256，整数除法 = 48828）
```

★ 这几个常数由 `check_rtl_contract.py` 盯着 —— RTL 改了、上位机没跟着改会报红。

## 9.2b ★ `dt` 必须把当前这一拍算进去

```verilog
// 错的：报的是"两次变化之间隔了几个【没变的】采样边界"
rec_fire_dt <= rec_dt;
// 对的：采样边界本身就已经过去了 10ms
rec_fire_dt <= rec_force ? 16'd0 : (rec_dt + 1'b1);
```

差这一拍，**每来一个事件就少 10ms**。12 个事件累积 −110ms，17 个事件 −170ms；
几百个事件就是好几秒 —— 听感正是"间隔不对、越放越赶"。这条也是拿
`testfiles\diag_rec_timing.py` 量出来的。

★ 另外**开始录音时要强制报一次当前掩码**（`rec_force`，dt=0）。
  否则"按着键再开录音"这种情形下，那个键从头到尾都不会作为"变化"出现，
  整条不在录音里。

## 9.3 效果状态帧（`0x5D`）

板子上真正影响声音的效果开关全是二值开关（按一下翻一次），8 位正好一个字节：

| 位 | 寄存器 | 效果 | 影响声音 |
|---:|--------|------|:--------:|
| 0 | `glide_en` | 滑音（音高从上一个音滑过来） | ✅ |
| 1 | `sustain_on` | 延音锁存（点过的键一直响） | ✅ |
| 2 | `timbre_50m` | 音色（基波 / 基波+2 次谐波） | ✅ |
| 3 | `trem_on` | 颤音 | ✅ |
| 4 | `dly_on` | 延迟 | ✅ |
| 5 | `flute_on` | 笛子音色（包络 + 谐波） | ✅ |
| 6 | `rev_on` | 混响 | ✅ |
| 7 | `cho_on` | 合唱 | ✅ |

★ **按钮 3 的 `wave_mode` 故意不在里面**：它只喂给 `lcd_master`（频谱/波形显示），
  对音频链路一个采样点的影响都没有，录它没有意义。

★ **只在状态变了的时候发**：效果开关是人手按的，一个演奏里通常就几次，
  带宽可以忽略（事件帧才是大头）。**开始录音时强制发一次初始状态**，
  保证上位机一定知道"这一遍是从什么效果配置开始的"，不用猜。

★ **这一路是只读的**：`top.v` 只是把这 8 个寄存器"看"一眼打包送到
  `uart_packet_echo`，一根线都没有连回效果链路，效果本身的行为一个字节没变。

## 9.4 上位机怎么复现（**接近即可，不追求逐位一致**）

| 板子上的效果 | MIDI 里怎么还原 |
|--------------|-----------------|
| 笛子 / 音色 | `program change`（82 Lead 3 calliope / 79 Ocarina / 73 Flute） |
| 颤音 | `CC1`（调制轮）0 / 100 |
| 混响 | `CC91` 0 / 100 |
| 合唱 | `CC93` 0 / 100 |
| 延迟 | `CC94` 0 / 100 |
| 延音锁存 | **不用还原** —— 它已经体现在"音有多长"上了（锁住的键门控一直是 1） |
| 滑音 | 弯音（`pitchwheel`）。见下 |

**★★ 音色必须挑【持续型】的，绝对不能用钢琴 ★★**

GM 的钢琴音色**自带衰减** —— 按住不放也会越弹越轻。而板子的包络在按住期间是
**恒定满幅**：`ENV_SUSTAIN_LV = 255`，顶层那句 `else if (env[ge] > env_sus_lv)`
的衰减条件根本不成立，env 攻到 255 就一直停在 255，一点都不掉。

★ 而且板子的默认音色是 `sine_rom` 那张 256 点整周期正弦表出来的【纯正弦】
  （"基波"档），所以**不能用方波/锯齿**：80/81 谐波太丰富，用户实测反馈
  "太尖锐了，不是柔和的正弦波的声音"。要用【正弦感 + 起音干脆 + 按住满幅】的。

| 板子上的音色 | GM 音色 |
|--------------|---------|
| 纯基波（正弦） | **82** Lead 3 (calliope) —— 正弦感的口哨/风琴音色 |
| 基波 + 2 次谐波 | **79** Ocarina —— 频谱正好是"基波 + 2 次谐波"，中空不刺耳 |
| 笛子 | **73** Flute（软起音 + 轻微颤音，和板子的笛子包络对得上） |

★ 备选（都是"持续型"，随便换）：16 Drawbar Organ（起音干脆、很柔）、
  89 Pad 2 Warm（更柔，但起音偏慢）、74 Pan Flute、19 Church Organ。

★ **拿不准就让人耳听**：`python testfiles\make_timbre_candidates.py` 会生成
  `D:\\CODE\\SPP_txandrx\\MIDI\\_候选音色.mid`，把同一句用各候选音色依次弹一遍，
  挑一个报编号即可。音色好不好听这件事，看名字是判断不了的。

★ **第一个状态必须明确发一次 `program change`**：音源上"当前是什么音色"是
  未知的（可能是上一次播放残留的），不发就会用错音色。所以第一条效果状态的
  `prev_state` 传 `None`，而不是 0。

**滑音的近似**：`top.v` 里 `dcur` 从【上一个音】的频率朝本音滑，每个采样点挪
`GLIDE_STEP=2048`，所以

```
时长 = |delta(本音) − delta(上一个音)| / GLIDE_STEP / 采样率
delta(f) = f × 2^32 / 采样率          （就是 top.v 的 calc_delta）
```

★ 注意板子的滑动在**【频率】上是线性的，不是半音线性的** —— 同样跨一个八度，
  音越高频率差越大、滑得越久（A2→A3 是 97ms，A3→A4 是 194ms）。
  上位机按频率线性插值再折算成半音偏移，所以形状和板子一致。

★ 弯音是**整通道**的，和弦里没法一个音一个音地弯，而板子上滑音是每个键各自滑的
  —— 所以上位机只在**单音**上做滑音，和弦时跳过。这是这个近似方案的天花板。
  弯音范围会先用 RPN 0 设成 ±12 半音（默认只有 ±2，大跨度会被削平）。

## 9.5 时间基准

`dt` 的单位固定 10ms，是板内 `REC_TICK_DIV = 20'd500_000`（`clk_50m_ext` 50MHz × 10ms）。

★ **和 §4 的"时间格"完全无关**：录音回传走的是真实毫秒，不受 `SET_TICK` 影响。
  上位机合成 MIDI 时再按 BPM 换算成 tick（见 `fpga_rec.events_to_midi`）。
  BPM 只影响谱面记号 —— 时间戳本来就是真实毫秒，一进一出正好抵消，放出来还是原速。

## 9.6 ★ 录音期间必须抑制回显（本章最关键的一条）

§4.6 定的回显规则是"凡被消费的字节都回显"。**录音期间必须整体关掉回显**，原因：

回显内容是**任意字节**（音号 `0x00~0x23`、`0xEE`、`0xC0`…），其中完全可能
出现 `0x5A`。一旦出现，上位机就会把它当帧头，把后面 7 个字节当成
mask + dt 吃掉 —— **凭空多出一个不存在的事件**，时间轴还会跟着错位。

```verilog
wire echo_push = tx_req && !rec_on;      // 录音时一个字都不回显
```

上位机侧还有第二道防线：`mask >> 36` 必须为 0，否则判为假帧头，
**只后退一格重新同步，不整段清空**（`fpga_rec.RecParser.feed`）。
两道加起来，就算线上混进杂字节也不会污染录音。

## 9.7 开关：两端都能开、两端都能关，状态以板子为准

板子上是**按键 10**（TTP229 那块 16 键按钮板的第 10 个键，`scl_btn` E13 / `sdo_btn` E14）。
前 9 个键已经被 滑音/延音/波形/音色/颤音/延迟/笛子/混响/合唱 占满了，第 10 个是空的。

```
板子按按键10 ──┐
               ├──> rec_on 翻转 ──> 回一帧 [0x5B][新状态]
上位机发 0x5C ─┘
```

| 步骤 | 板子 | 上位机 |
|------|------|--------|
| 点勾选框 | — | 发 `0x5C`，状态栏显示"已发出开关指令…" |
| 收到 `0x5C` | 翻转 `rec_on`，回 `[0x5B][0/1]` | — |
| 收到 `0x5B` | — | 勾选框跟着变成板子报的状态（**板子是权威**） |
| 按按键 10 | 翻转 `rec_on`，回 `[0x5B][0/1]` | 同上，勾选框自动跟着变 |
| 0.8 秒没等到 `0x5B` | — | 勾选框退回真实状态，日志说明"开关没生效" |

★ 上位机**不能**自作主张先改自己的状态再发命令 —— 板子可能不在线，
  那样界面就在骗人。所以是"发请求 → 等回报 → 以回报为准"。

★ `btn_rec` 过的是 `clk_50m`（按键）→ `clk_50m_ext`（串口）的 CDC：
  两级同步 + `s2 ^ s3` 取边沿。**不能直接拿按键电平当触发**（跨时钟域，
  会重触发或漏触发）。

## 9.8 上位机合成规则

`fpga_rec.py`：

| 步骤 | 规则 |
|------|------|
| 解析 | 逐字节状态机；`0x5A` 收满 8 字节、`0x5B`/`0x5D` 各收满 2 字节；非帧头字节丢弃并计数 |
| 校验 | `mask >> 36 != 0` → 假帧头 → **退一格重同步**（不要整段清空，后面那帧还是好的） |
| 时间 | `t += dt × 10ms`，得到每个事件的绝对毫秒 |
| **音长** | **逐键跟踪门控边沿**：每个键从"它的位 0→1"响到"1→0"，**再补一段释音尾巴**（§9.2 的常数）<br>★ 不能写"响到下一个事件为止"：先起的音会被下一个事件拦腰截断，而且掩码里一直为 1 的键会被每个事件重复触发 |
| **同名键重击** | 前一个音**掐在新起音那一拍上**。不掐的话后一个音的 `note_off` 会把新的音一起掐掉（很多音源按音高配对、不区分第几个实例）；钢琴上重击同一个键本来也会制住前一次振动 |
| 音高 | 必须过 `score_jp.key_to_midi` 的置换表（§2.3），**绝不能拿键号当半音数** |
| 效果 | `0x5D` 的时间轴 → `program change` / `CC` / 弯音（§9.4） |
| 排序 | 同一 tick 上 **效果(0) → 弯音(1) → `note_off`(2) → `note_on`(3)**。顺序不能乱：弯音要排在 `note_on` 前，否则滑音的头一个音不是从上一个音的音高起滑的；`note_off` 要排在 `note_on` 前，否则同音高的前后两个音会互相掐掉（同名键重击就是靠这一条接上的） |
| 重开 | **开始录音那一帧（`0x5B` 且值为 1）在解析流里就地清空**上一遍的事件和效果时间轴。★ 不能等整批解析完再清 —— 开始标志和这一遍最早的事件完全可能落在同一个串口批次里 |

**★ 时间轴怎么验（`fpga_rec.py selftest` 第 [10] 节 + `testfiles\diag_rec_timing.py`）**

拿"每 400ms 一个音、按住 250ms"当基准，走完整条链路
（真实演奏 → 板子 10ms 采样 → 回传字节 → 解析 → 合成 MIDI → 把 MIDI 的时间
反算回毫秒），逐个和真实演奏比。当前结果：

```
起音时刻      误差 +0 ms（全部）
相邻起音间隔  400ms 就是 400ms，完全一致
整轨总长      4720ms / 真实 4720ms = 1.00x
每个音长度    1720ms（= 按住 250 + 尾巴 1470），一致
```

合成出来的 `.mid` 落在 `<程序目录>\MIDI\录音_<时间戳>.mid`，可以直接
「发回板子」—— 板子认自己那套帧，能原样弹出来，形成闭环。

## 9.9 为什么不破坏现有协议

| 担心 | 结论 |
|------|------|
| `0x5A`~`0x5D` 会不会和乐谱帧撞车 | 不会。它们落在 `0x24`~`0xA9` 未分配区（§3），**且方向相反**：`0x5C` 只从上行进（板子当乐谱字节，因为不在音域里、会被丢弃）；`0x5A`/`0x5B`/`0x5D` 只从下行出（板子从不在发谱路径上产生它们） |
| 上位机发谱时会不会被误当录音命令 | 不会。`0x5C` **不在** `0x00~0x23`/`0xEE` 里，乐谱编码器永远不会产生它 |
| 录音时发谱会不会串 | 会互相干扰，所以**别边录边发谱**。录音时回显被抑制（§9.6），发谱的回显也就没了 |
| 会不会拖慢/改变发声 | 不会。`sounding_mask` 和 8 个效果开关都是**只读**地引到新模块，发声链路一个字节没动 |
| 效果会不会被录音改动 | 不会。`top.v` 里 8 个效果寄存器的赋值语句一个字没改，只是被"看"了一眼打包送出去 |
| 老的 v1/v2 帧还能不能用 | 能。收谱/播放路径逐位不变；默认 `rec_on = 0`，不录就完全没有回传 |

★ 唯一的代价：TX 加了一个 16 字节 FIFO（`txf_mem`），用来把"回显 / 开关帧 /
  效果帧 / 事件帧"四种来源合并到同一个串口上。

★★ **三种回传帧必须互斥**（同一时刻只允许一种在发）。不互斥的话两路会在同一拍
  都想入队，优先级只能决定写进 FIFO 的是哪一个，**另一路的移位寄存器却照样前进**
  —— 那一路的字节就被悄悄吞掉了（事件帧会因此缺一个字节，上位机整帧错位）。
  所以各路的**启动**条件都带 `rec_busy`。回显也要让路：录音刚关掉时那两个字节
  还在飞，这期间上位机要是发了个字节，同样会抢。

★ FIFO 指针是 **5 位**（16 深的 FIFO 用 4 位指针时，"满 16 个"和"空"读出来是
  同一个值，`txf_full` 永远为假，第 17 个字节会静默覆盖最早那个）。

★ **带宽**：事件帧 8 字节 / 最短 10ms 一次 = 800 B/s，9600 波特只有 960 B/s，
  余量不大但够（8 字节要发 8.3ms < 10ms）。效果帧只在状态变的时候发，可以忽略。

# 第 12 章  效果开关与音色（`0xC9` / `0xCA` / `0xCB`）

## 12.1 为什么加

板子上那 8 个效果（滑音/延音/音色/颤音/延迟/笛子/混响/合唱）原来**只能用 TTP
触摸按钮切**。上位机（蓝牙串口助手）里看不到、也改不了。这一版让**两端都能切**：
板上的按钮继续保留，谁改了都会通过 `0x5D` 状态帧告诉对方，两边始终一致。

## 12.2 上位机 → FPGA

| 字节 | 载荷 | 含义 |
|------|------|------|
| `0xC9` | 1 字节位号 `0..7` | **翻转** `fx_state` 的第 bit 位 |
| `0xCA` | 1 字节 `0..3` | **直接设定音色**：0 普通 / 1 笛子 / 2 吉他 / **3 小号**（★ 4 档，**V48.3 起**） |
| `0xCB` | 无 | 请板子立刻回报一次状态 |

- 位号就是 `fx_state` 的位（见 §9 / `top.v`）：
  bit0 滑音、bit1 延音锁存、bit2 音色（基波+2 次谐波）、bit3 颤音、
  bit4 延迟、bit5 笛子**（= 音色档，V48.3 起四档）**、bit6 混响、bit7 合唱。
- ★ **为什么效果用"翻转"而不是"设成 1/0"**：翻转的语义和按物理按钮完全一样，
  板子永远是权威 —— 上位机不需要知道当前状态就能安全地切，也就不会出现
  "软件以为它是关的、其实是开的，一设反而设反了"。
- ★ **音色为什么单独一条命令**：多档没法用一位翻转表达。`0xC9` 的位 5 仍然保留
  "音色循环"的语义（等价于按板上按钮 7），但上位机的多选一控件用的是 `0xCA`。
- 两个操作数都是**原始数据**（可以是 `0xAA`/`0xFF`/`0xC0` 任意值），
  所以 RTL 里用 `fx_left` / `tone_left` 两个计数器挡着 —— 和 `0xC2`/`0xC6` 同理。
- ★★ **越界值怎么退化：两条命令【故意不一样】，别互相看齐**（这是踩过的坑，见交接文档坑 48）：
  - `0xCA` 音色：位号取低 3 位；**音色 `>3` 一律退化成 `0`（普通）** ——
    `tone_val <= (rx_data > 8'd3) ? 2'd0 : rx_data[1:0];`
    理由：越界值不该让板子突然发出一档**用户没选过的音色**，最保守 = 什么都不加。
  - `0xD0` 显示模式（第 17 章）：**夹紧**到 `0..4`，不是退化成 0，也不是取模。
  - 一个是"退化"，一个是"夹紧"，**各有各的理由**；上位机/安卓两边都已按此对齐
    （电脑版 `pack_tone_set` / 安卓 `safeTone()`；★ 安卓那个方法**故意不叫 `clamp*`**）。

## 12.3 FPGA → 上位机（`0x5D` 状态帧）

| 固件 | 格式 |
|------|------|
| V29 及以前 | `[0x5D][效果 8 位]` |
| V31 ~ V42 | `[0x5D][效果 8 位][音色]` |
| **V43 起** | `[0x5D][效果 8 位][音色][跟谱模式 0/1]`（第 14 章） |

★ **帧长/帧头一个字节都没变过**；变的只是**音色的值域**：V48.2 及以前是 `0..2`，
**V48.3 起是 `0..3`（多了小号）**。

- ★ **改为"只要变了就上报"**：原来只在录音时上报；现在板上的按钮一按、
  或者上位机改了，都会上报一次，两端才能互相同步。
- ★ **上位机解析要兼容三种固件**：读到第 3 个字节时，**`<= TONE_MAX` 才算音色吃掉**
  （现在是 `<= 3`；老固件只会发 `0..2`，所以放宽上界不会误判），
  否则说明是老固件，那个字节要按正常流程继续处理。音色字节也可能落在
  **下一个串口批次**里，所以解析器要留一个"等一个字节"的状态。
  ★ V43 又把这一层套了一遍：音色之后**再等一个字节，`<= 1` 才算跟谱模式**，
  认不出就【不吃掉】它，按正常字节走 —— 所以新的解析器对着老固件的
  3 字节帧也不会错位（电脑版 `fpga_rec.py` 的 `_fx_wait_mode`、
  安卓版 `FpgaRec` 的 `fxWaitMode` 都是这个写法）。
- 音色值 `0..3`、跟谱模式 `0/1` 都不会和任何帧头混淆
  （帧头都是 `>= 0x5A`），这是设计性质。

## 12.4 RTL 落点

- `uart_packet_echo.v`：`FX_TGL_BYTE`/`TONE_SET_BYTE`/`FX_REQ_BYTE` 三个
  localparam；`fx_left`/`tone_left` 计数器；`fx_tgl`+`fx_bit`、`tone_we_tgl`+`tone_val`
  两组"翻转沿 + 数据"写口（和 `0xC6` 的 keymap 写口同一套做法）；
  状态帧 `fx_idx` 从 2 位扩到 3 位（帧头/效果/音色三个字节）。
- `top.v`：写口在 `clk_50m_ext`，效果寄存器在 `clk_50m`，用两级同步 + 边沿检测接收；
  每个效果那一个 `always` 块的翻转条件从 `btn_xxx` 变成 `btn_xxx | fxw_xxx`；
  音色多一条 `else if (tonw_we) tone_sel <= tonw_val_s2;`（直接选档）。
  ★ V48.3：音色的值域扩到 4 档后，写口那行的夹取/退化就一句话 ——
  `tone_val <= (rx_data > 8'd3) ? 2'd0 : rx_data[1:0];`（**越界退化成 0**，
  和 `0xD0` 的"夹紧到 4"不是一回事，见 §12.2 的 ★★ 那三行）。
- ★ 校验脚本：`check_rtl_contract.py` 第 `[2c]` 节会把三个字节和
  `fpga_rec.py` 逐个对，并检查"操作数计数器排在命令字分支之前"。


# 第 13 章  和弦内逐音八度（`0xCD`，V37）

## 13.1 为什么加：V32 留下的那个洞

`0xCC`（第 4 章）只能给**一整格**一个八度偏移。于是：

- 一句"高两个八度"的旋律 → 整格挪，能解决 ✔
- 但**同一格里**左手 C2 + 右手 C6（跨 4 个八度）→ 一个八度救不了两个音，
  多出来的那个只能按八度折返进来。`fpga_midi.py` 的 `_fold_into_board()`
  就是干这个的，它的注释写得很诚实：
  > 折返只是那个音掉/升了个八度，旋律线还连得上

  —— 连得上，但那**不是原音高**。V32 的 selftest 里甚至有一条断言把这个
  现象钉住了：`"跨 4 个八度的一格：仍然折返，但一个音都没丢"`。

## 13.2 关键认识：缺的不是振荡器，是"每个音自己的八度"

板子上实际发出来的音高是

```
    key_to_midi(键)  +  12 × 这个键的八度偏移
```

而 `top.v` 里 `voice_oct[]` **本来就是逐声部存的**（V32 为了"释音尾巴不被一起
搬八度"就已经做成 36×3 位了）。缺的只是**把逐键八度从协议送进来**：

- 36 个键 = **3 个完整八度**（每个半音都有）→ 任何音高 m 只要能找到
  `o` 使 `m − 12o ∈ 45..80`，就有键能**精确**发出它（`o ∈ −4..+3`）
- 同一格里不同的音走不同的键 + 各自的 o → 跨 4 个八度也能同时按原音高发

所以这一版**一个振荡器都没加**：LUT / DSP / Register 基本不涨，
只多了一条"逐键八度"的通路和 6 块 BSRAM（存逐键八度）。

## 13.3 字节定义（定稿）

| 字节 | 载荷 | 含义 |
|------|------|------|
| `0xCD` | 1 字节有符号八度 | 作用于**紧跟其后的那一个音号** |

- **只允许出现在 `0xC0`..`0xC1` 之间**（和弦内部）。和弦外收到只被记下，
  下一个 `0xC0` 会把它清掉，所以不会串到下一格。
- 语义与 `0xCC` **完全一致**：`0..3` = `+0..+3`；`4..7` = `-4..-1`（两补数）。
- ★ 操作数是**原始数据**，RTL 用 `key_oct_left` 计数器挡着 —— 和
  `0xC2`/`0xC6`/`0xC9`/`0xCC` 同理。否则一个 `0x01` 之类的八度值会被
  音号分支当成"第 1 号键"点亮。
- ★ 没有 `0xCD` 前缀的音号**继续用本事件的 `oct`**（整格八度）。
  一个 `0xCD` 都不发的帧**逐字节不变**。
- ★ `0xCD` 不会和音号撞车：音号最大 `0x23`，`0xCD` 在命令区且此前未分配。

## 13.4 文法（在第 4 章基础上的增量）

```
    chord  ::= 0xC0  note+  0xC1
    note   ::= [ 0xCD oct ] 0x00..0x23        ← 本版新增方括号里那一段
    oct    ::= 0x00..0x07                     （有符号 3 位，两补数）
```

## 13.5 例子

**例：同一格里 C2 与 C6 同时响（V32 必须折返，V37 不用）**

```
    C0 CD 07 01  CD 01 19  C1
    │  │  │  │   │  │  └──┴─ 音号 0x19 = C5 那个键，带 +1 八度 → 发 C6
    │  │  │  └───┴──┴─────── 音号 0x01 = C3 那个键，带 -1 八度 → 发 C2
    │  └──┴───────────────── 逐音八度前缀：0x07 = −1
    └─────────────────────── 和弦帧头
```

板内 `voice_oct` 分别记 −1 和 +1，两个音各按各的八度发，**零折返**。

**例：音域内的和弦（与 V36 逐字节相同）**

```
    C0 0D 15 19  C1          ← C4/E4/G4 全在 A2..G#5 内
```
一个 `0xCD` 都不发、`0xCC` 也不发 —— 字节流和 V36 完全一样。

## 13.6 板内实现落点

`uart_packet_echo.v`

- `KEY_OCT_BYTE = 8'hCD`；`key_oct_left`（等操作数）、`key_oct_seen`
  （刚收到 0xCD，留给下一个音号）、`key_oct_pend`（那个八度）
- 和弦累积：`acc_oct`（36 键 × 3 位 = 108 位）+ `acc_oct_set`（36 位，
  哪些键被 `0xCD` **显式指定过**）
- **落盘时烘平**（全文件唯一写 `slot_oct` 的地方）：
  ```verilog
  slot_oct[wr_slots][g] <= acc_oct_set[g] ? acc_oct[g] : pend_oct;
  ```
  没被指定的键一律填整格八度 —— 这就是"老谱子逐位不变"的来源
- 新存储 `slot_oct[0:1023]`（108 位 × 1024 → 6 块 BSRAM）。
  ★ 与 `slot_mask`/`slot_dur` 一样**单读单写**，读地址只有 `rd_slot` 一个
- `midi_octs`（108 位）与 `midi_keys` **同一拍、同一个 always 块、同一个 `gate`**
  输出 —— 掩码和它的八度天生配对

`top.v`

- `midi_octs_s1/s2` 两级同步（级数与 `midi_keys` 的"当前格" `midi_keys_s2` 对齐，
  `score_new` 用的就是它）
- 起音：`voice_oct[gt] <= midi_octs_s2[gt*3 +: 3]`（原来是 `oct_s2`）
- 滑音判据：
  ```verilog
  wire [2:0] oct_new_g = score_new[g] ? midi_octs_s2[g*3 +: 3] : oct_s2;
  ```
  乐谱起音用**本键自己的**新八度；手弹/其它来源仍用 `oct_s2`（与 V36 逐位相同）。
  ★ 这一条不能省：拿整格八度去比，跨八度大跳时会从**另一个八度**滑上来 ——
  那正是 V33 修过的"大跳时音头跑到别的八度"换个形式复现。

## 13.7 兼容性证明（为什么不带 `0xCD` 的帧逐位不变）

| 层 | 论据 |
|---|---|
| 帧字节 | `Event.key_octs` 为空 → `_encode_event` 一个字节都不多发 |
| 板内存储 | `acc_oct_set` 全 0 → 每个键都被填成 `pend_oct` |
| 声部八度 | `midi_octs_s2[gt*3+:3]` ≡ `oct_s2`（同一个 `pend_oct`）→ 赋值逐位相同 |
| 滑音判据 | `score_new[g]` 时 `oct_new_g` = `midi_octs_s2[...]` = `oct_s2`；手弹时仍取 `oct_s2` |

## 13.8 上位机侧（`fpga_midi.py` 的 `assign_keys()`）

给一格的音**逐个**分配 `(键, 八度)`：

- 候选：对 `o ∈ {0,1,−1,2,−2,3,−3,4,−4}`，只要 `m − 12o ∈ 45..80` 就是一个候选
- 约束：**键互不相同**（一个声部同时只能发一个音）
- 求解：二分图匹配（Kuhn 增广路）。n ≤ 36、每个音 ≤ 3 个候选，
  代价可以忽略，而且**只要存在"不撞键"的方案就一定找得到**
- 偏好（越靠前越优先）：
  1. 与**上一格同一个音高**用同一个 `(键, 八度)` —— 稳定优先。
     V33 的教训：同一个音高在两格之间换键，前一个音的余音会被后掐掉（听感是"截断"）
  2. 避开上一格还在响的键
  3. `|八度|` 小
  4. 优先原调（0），再升，再降
  5. 键号小（保证结果确定性 —— 回归测试要能复现）

★ **物理上限**：36 个键只覆盖 3 个八度，所以任何音名**最多只有 3 个键**
能精确到达它。同时响 4 个以上同音名的音（比如 C2/C3/C4/C5/C6）时，
匹配必然不够 —— 这时多出来的音会折返到还空着的键，**保证一个音都不丢**，
并在报告里记进 `folded`。这是物理约束，不是缺陷。

## 13.9 与 `0xCC` 的关系（两条路都要留着）

- `0xCC` 仍然有效，**语义一个字没改**：一整格的整体八度。
  `fpga_midi.py` 在**单音事件**上仍然用它（`Event.__post_init__` 会把
  单音的 `key_octs` 提升成 `oct`），所以旧帧、旧上位机、旧测试全部照旧。
- 新上位机对**和弦**一律走逐键八度（`oct = 0`，全部八度都进 `key_octs`）。
  音域内的和弦算出来 `key_octs` 是空的 → 帧字节与 V36 完全相同。

# 第 14 章  跟谱演奏模式（`0xCE`，V43）

## 14.1 为什么加

练琴时希望板子"等你"：这一格该弹的键没按对，就不要走到下一格。

- **默认关闭** —— 不跟谱时播放行为和以前【完全一样】。
- 打开之后：**当前时间格要求的键全部按住**才前进到下一格；
  ★ **必须松开再按**才算下一格（用上升沿，不用电平）——
  否则按住不放会自己一格一格往下走，同音重复的地方尤其明显。
- **休止格自动通过**（不用按任何键）。

## 14.2 上位机 → FPGA

| 字节 | 操作数 | 含义 |
|------|--------|------|
| `0xCE` | 1 字节 | `0x00` = 正常播放（默认）；非 `0` = 跟谱演奏 |

- ★ 和 `0xC9`/`0xCA`/`0xCB` 同类：**不受开窗限制、随时可用、可插队**。
- ★ 用「直接设」而不是「翻转」：跟谱是明确意图，而且板子上按键13 也能翻它，
  直接设能保证"点这一下 = 进入跟谱"，不会因为两边一时不同步就设反。
- ★ `0xCE` 不会撞车：现有命令用到 `0xC0`~`0xCD`。
- ★★ **操作数必须登记进操作数长度表** —— 否则 `safe_chunk_ranges` /
  `safeChunkRanges` 分块时可能把"命令 + 操作数"从中间切开，而命令是插队发的，
  正好落进那一对中间就会被当成操作数吃掉（`check_rtl_contract.py` 有一条判据专钉这个）。

## 14.3 FPGA → 上位机

跟谱模式搭 `0x5D` 状态帧的**第 4 个字节**回传（见 §12.3）：**模式一变就上报**，
所以板子上按 TTP 按键13 翻转时，上位机按钮会跟着变。也可以发 `0xCB` 主动要快照。

## 14.4 板内落点

| 位置 | 内容 |
|------|------|
| `uart_packet_echo.v` | `MODE_SET_BYTE`；`mode_left`（等操作数）、`wait_mode`（模式电平）、`btn_mode_tgl`（按键13 脉冲入）、`midi_guide` / `midi_keys_next`（只给 LED 的指引掩码，不参与发声） |
| 播放器 | `need_mask` / `keys_ok` / `keys_ok_d` / `slot_go` / `can_load`；装载事件那一句加了 `can_load` 门 |
| `top.v` | 按键13：`btn_mode_hold`（clk_50m 翻转保持）→ 三级同步 → `btn_mode_s2 ^ btn_mode_s3` 单拍脉冲 |
| `led_guide.v` | 四档亮度（§14.5） |

★ **不卡死**：`wait_mode` 是**电平状态**，`0xCE` 和 TTP 按键13 随时能翻回 0；
一翻回 0，`slot_go` 立刻被置 1，播放马上继续 —— 这是"开关自动恢复"，
不是"门控永久失灵"（见 §5 坑 20/22）。
★ **正常模式零影响**：`wait_mode = 0` 时 `slot_go` 恒为 1 → `can_load` 恒为 1
→ 播放器行为与 V42 **逐位相同**。

## 14.5 ★ LED 四档亮度

灯是照着**物理琴键位置**一颗一颗焊的，所以先把"物理位置 → 键号"置换一次
（`led_guide.v` 的 `ch2key()`）：物理第 1~12 个键 → 键号
`05 00 06 01 07 08 02 09 03 0A 04 0B`，后两个八度各 +12 / +24。
★ 这只影响"哪颗灯显示哪个键"，**与发声、与键位映射完全无关**。

| 档位 | Duty | 含义 |
|------|------|------|
| **90%** | `0xE6` | 现在要弹，且下一格也要弹 |
| **75%** | `0xBF` | 现在要弹 |
| **30%** | `0x4D` | 下一格要弹（提前预告） |
| **70%** | `0xB3` | 手弹按下的键（不在谱子要求里的） |

★ 优先级就是上表顺序，**手弹放最后** —— 谱子要求的键保持自己的档位，
不然一按对灯反而从 90% 掉到 70%。
★ "下一格"来自影子数组 `slot_nxt[j] = slot_mask[j+1]`：写 `slot_mask` 时顺手
多写一格，**发声路径一个字都不改**，BSRAM 地址前也没有多串选择器。
★ 跟谱模式等待期间由 `guide_en`（= `wait_mode ? play_run : gate`）保持显示；
**正常模式下 `guide_en` 就等于 `gate`**，所以 LED 行为与 V41 逐位相同。

## 14.6 版本影响

- 不发 `0xCE` 的帧 **逐字节不变**；板子复位后 `wait_mode = 0`（和以前一样）。
- `0x5D` 从 3 字节变 **4 字节**：**上位机两端必须同步更新**（电脑版 + 安卓版）。


# 第 15 章  节拍器（`0xCF` / `0x5E`，V44）

## 15.1 为什么加

板载 **READY 灯（引脚 `U12`）** 原来是"音色指示"灯，现在改成**节拍器**：
按设定的 BPM **匀速闪**，★ **每拍闪得一样长**（**不区分强拍弱拍**）。
它**不参与任何其它模块**，纯粹是给演奏者的一个外部时间参考。

- 出厂默认：**BPM = 100，拍号 4/4（分子 4 / 分母 4），节拍器【开着】**。
- 速度（BPM）、拍号分子、拍号分母都能**通过蓝牙（SPP）在电脑上位机和安卓 App 上调**。

## 15.2 上位机 → FPGA

| 字节 | 操作数 | 含义 |
|------|--------|------|
| `0xCF` | **3 字节** | `BPM` `NUM` `DEN` |

```
0xCF  BPM  NUM  DEN
       │    │    └── 拍号分母的【编码】：0 -> 2 / 1 -> 4 / 2 -> 8（超出夹紧到 0~2）
       │    └─────── 拍号分子 1~8（超出夹紧）
       └──────────── 速度：30~240；★ 0 = 关闭节拍器（1~29 夹到 30，>240 夹到 240）
```

★ **线上传的是编码不是分母本身**：分母只有 2/4/8 三种可能，编码更省字节，
也免得"分母 = 0"这种非法值出现在线上。

**夹紧规则（两端必须完全一致）**：

| 参数 | 合法值 | 越界怎么办 |
|------|--------|-----------|
| `BPM` | `0`，或 `30`~`240` | ★ `0` = **关闭**（**不是**"最慢"，不能被夹成 30）；`1`~`29` → `30`；`>` `240` → `240` |
| `NUM` | `1`~`8` | 夹到最近的边界 |
| `DEN` | `0`~`2` | 夹到最近的边界 |

★ 上位机**发之前就先夹好**：板子回报的是**夹紧之后**的值，不先夹就会出现
"界面填 999 → 板子回报 240 → 界面被刷成 240 → 用户以为控件坏了"的来回拉扯。
夹好之后：**界面显示的值 = 发出去的值 = 板子回报的值**。

例：

```
0xCF 0x64 0x04 0x01     →  100 BPM，4/4（出厂默认，分母编码 1 = 四分音符）
0xCF 0x00 0x04 0x01     →  关闭节拍器
0xCF 0xF0 0x03 0x01     →  240 BPM，3/4
```

- ★ 和 `0xC9`/`0xCA`/`0xCB`/`0xCE` 同类：**不受开窗限制、随时可用、可插队**。
  节拍器不碰乐谱、不碰效果、不碰演奏状态，所以插队发不会影响正在播的谱子。
- ★ `0xCF` 不会撞车：现有命令用到 `0xC0`~`0xCE`，`0xCF` 是最后一个空位。
- ★★ **这 3 个操作数必须登记进「操作数长度表」**（电脑版 `fpga_proto.py` 的
  `_OP_LEN`，安卓版 `FpgaProto.java` 的 `opLen()`）—— 否则分块时可能把
  "命令 + 操作数"从中间切开，而命令是插队发的，正好落进那一对中间就会被
  板子当成操作数**吃掉**（参数被污染 + 整帧错位；`check_rtl_contract.py`
  里有一条判据专钉这个，工程里俗称「坑 21」，§14.2 那条同理）。

## 15.3 FPGA → 上位机（`0x5E` 状态帧）

```
0x5E  BPM  NUM  DEN  BEAT          ← 固定 5 字节
```

| 字节 | 含义 |
|------|------|
| `BPM` | 板子当前**实际生效**的 BPM（★ 已经是**夹紧之后**的值；`0` = 关） |
| `NUM` | 实际生效的拍号分子（`1`~`8`） |
| `DEN` | 实际生效的拍号分母**编码**（`0`/`1`/`2` = 2/4/8 分音符） |
| `BEAT` | 当前在小节内的第几拍，★ **0 起算**（`0` .. `NUM-1`） |

- ★ 板子在**设置发生变化时主动发**这一帧，**不是周期发送** ——
  所以收到它就等于"刚才那次设置已经生效"。
- ★ 上位机 / 安卓收到后做两件事：**确认设置已生效**（撤掉「待确认」）、
  **把 UI 同步成板子的真实状态**（板子永远是权威）。
  ★ 确认条件是 **`BPM`/`NUM`/`DEN` 三个值全对上**（只有一个对上不算）。
- ★★ **`0x5D` 一个字节都没有动**：它还是 `[0x5D][效果 8 位][音色][跟谱模式]`
  4 字节（§12.3）。`0x5E` 是**全新独立**的一帧，两端各解析各的 ——
  节拍器和效果/音色/跟谱模式**没有任何耦合**，混进 `0x5D` 既会改已有布局，
  又会让"节拍器改了"和"效果改了"在解析层分不开。
- ★ `0x5E` 不会撞车：现有回传帧头是 `0x5A`/`0x5B`/`0x5D`。
- ★ 解析侧要做帧校验：真帧里 `NUM` 恒在 `1`~`8`、`DEN` 恒在 `0`~`2`，
  拿它挡掉"从帧中间接上"产生的假帧头（`BPM` 恒合法，不拿它校验）；
  挡掉之后**只后退一格重新找**，别整段清空 —— 后面那帧还是好的。
- ★ 帧长固定 5 字节，**可能被串口切成几批**送来；不够就等下一批，不能猜。

## 15.4 FPGA 侧行为要求（实现自由，行为必须一致）

- 收到 `0xCF` 后**先夹紧再生效**；`0x5E` 里回报的就是**生效后**的那三个值。
- 三个值**任一发生变化**就发一帧 `0x5E`（`BEAT` 带上当前小节内位置）。
- READY 灯（`U12`）按 BPM **匀速闪，每拍时长相同**（不区分强拍弱拍）。
- `BPM = 0` = **关闭**：灯不再按节拍闪（关闭时的灯电平由 RTL 定，不影响协议）。
- ★ 与其它模块**零耦合**：节拍器不改 `key_mask`、不改效果、不改播放状态。

## 15.5 版本影响

- **`0x5D` 逐字节不变**（还是 4 字节）；不带 `0xCF` 的帧**逐字节不变**。
- 新增两个字节：`0xCF`（上位机 → 板子）、`0x5E`（板子 → 上位机）。
- **两端必须同步更新**（电脑版 `fpga_proto.py` / `fpga_rec.py` / `spp_assistant.py`
  + 安卓版 `FpgaProto.java` / `FpgaRec.java` / `MainActivity.java`）。
- 老固件不认 `0xCF`：上位机会在 1.2 秒后把这次设置标成「未确认」并说明原因 ——
  协议里**没有查询节拍器的命令**（板子只在变化时主动发 `0x5E`），
  所以只能如实提示"没等到回报"，**不能假装成功**。


# 第 16 章  逐事件力度（`0xC3`，V47）

## 16.1 为什么加

赛题要求"≥3 维表情"。在力度之前，本设计的表情已经有：**滑音**（`0xCC`/`0xCD` 八度）、
**颤音**（摇杆 2）、**延音**、**音色**、**效果深度**。缺的那一维正是最基础的一维：
**每个音自己的响度**。

没有它时，蓝牙放 MIDI 是全篇一个音量 —— 强弱拍、渐强渐弱全被抹平，
听起来像八音盒而不像演奏。这一维加完之后，`0xC3` 就把 MIDI 的 velocity
一路带到了包络峰值上。

## 16.2 字节定义

```
上位机 -> FPGA：  [0xC3] [VEL]          —— 共 2 字节
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `VEL` | `0x00`~`0x7F` | 力度，即 MIDI 的 velocity。`> 0x7F` 一律**夹到满幅**（★ 不能简单截低位：`200` 截成 `72` 会把"很响"变成"很小声"） |

**语义**：和 `0xC2`（时值）/ `0xCC`（整格八度）/ `0xCD`（逐音八度）完全一样 ——
**只作用于紧接着的下一个事件**，作用完自动回默认值。

★★ **默认值是 127（满幅）**。所以**不带 `0xC3` 的帧，行为与加这个功能之前逐位相同**。
这也是上位机侧的优化依据：`VEL == 127` 时**一个 `0xC3` 都不发**（省 2 字节，结果一样）。

**不受开窗限制**：`0xC3` 和 `0xC9`/`0xCA`/`0xCE`/`0xCF`/`0xD0` 一样随时可用。

## 16.3 板内落点（★ 这一节是本功能最容易做错的地方）

RTL 在 `src\uart_packet_echo.v`：

- `vel_wait`：`0xC3` 的 1 个操作数还没到（**必须挡在命令解析前面**，否则操作数会被当成音符 ——
  见第 4 章的"操作数不当音符"纪律）；
- `vel_hold` → `pend_vel`：**两个寄存器**。"先存 hold、落盘时搬到 pend"这个流水
  和 `oct_hold` → `pend_oct` 一模一样。合成一个寄存器的话，事件字节那一拍会把刚设的力度清掉；
- `slot_vel[wr_slots]`：和 `slot_mask`/`slot_dur`/`slot_oct*` 一起**在同一个门里落盘**
  （全文件只有那一处写这些数组）；
- 超时：`vel_wait` 必须同时进 `op_wait`（挡音符）和 `any_op_wait`（统一超时），
  而且到点要被清掉。**两个集合漏一个**就会分别退化成"操作数被当成音符"或"卡住不恢复"。

★★★ **力度最终乘在【每个音自己的包络峰值】上（`gen_env` 里的 `vel_peak_k`），
绝不乘在共用的混音路径上**：

| 做法 | 后果 |
|---|---|
| 乘在 `mix_scale`（混音总增益，**所有发声部共用**） | 力度一变，**所有正在响的音**（含延音尾巴）跟着跳 → 每个音一声"噗" |
| 乘在 `mix_scale_r` 那条斜坡的**目标**上 | 斜坡要走 ~2ms，起音那 2ms 按旧的大音量出来再缩下去 = 又一声"噗" |
| **乘在每个音自己的包络峰值（正解）** | 起音就从正确音量开始，**没有任何增益跳变**，正在延音的音一个比特都不动 |

★ 判据：**如果一个量是"逐音"的，它就不能乘在"共用"的路径上。**

## 16.4 上位机生成规则（`fpga_midi.py`）

1. **每一格的力度 = 这一格里所有音 velocity 的【最大值】**。
   协议是逐事件力度（一个和弦只带一个 `VEL`），所以必须挑一个代表。
2. `note_on` 且 `velocity == 0` 是 MIDI 的**抬手**，**不是"力度 0"** —— 不产生 `VEL = 0`。
3. **休止事件（`0xEE`）不带力度**：`0xC3` 是"挂着等下一个事件"的，
   挂在休止上等于被休止吃掉。休止一律用默认 127、不发 `0xC3`。
4. **`VEL == 127` 不发**（板子默认就是 127）。
5. **手工曲谱那条路（`score_import.arrange()`）根本不填力度** → 一个 `0xC3` 都没有，
   帧与加这个功能之前**逐字节相同**。
6. 界面上的「MIDI 力度」勾选框只影响**生成帧**这一个环节：
   关掉时一个 `0xC3` 都不发，用于 A/B 对比试听。**勾选框本身不发任何字节**
   （协议里 `0xC3` 没有状态回报，板子那边没有这个状态）。

## 16.5 版本影响

- **`0x5D` 逐字节不变**；**不带 `0xC3` 的帧逐字节不变**（板子默认满幅）。
- 新增 1 个下行字节：`0xC3`（只有下行，**没有上行**）。
- **两端必须同步更新**（`fpga_proto.py` / `fpga_midi.py` + `FpgaProto.java` / `FpgaMidi.java`）。
- 老固件不认 `0xC3`：操作数会被当成**音符号**（`0x00`~`0x23` 范围内的力度值）
  或走到 500ms 超时被丢掉。所以**只有刷了 V47 之后的固件才能开这个开关**。


# 第 17 章  LCD 显示模式（`0xD0` / `0x5F`，V48）

## 17.1 为什么加

用户的验收标准是：**"所有 TTP 上的可调按键全部在上位机上也可调，并且状态保持同步。"**
把按钮板 16 个键逐个对过一遍，真正缺口只有两个：

| 键 | 功能 | 缺口 |
|---|---|---|
| **键3** | LCD 显示画面循环 | **完全没有接上位机** —— 既设不了，也不知道板子现在是哪一档 |
| **键10** | 录音开关 | 能发（`0x5C`），但**板子按下时不回报**（`0x5B` 只在录音开着时才发） |

其余 9 个功能都已经有上位机控制了。本章补的就是这两个缺口，做**双向**。

## 17.2 上位机 → FPGA（`0xD0`）

```
上位机 -> FPGA：  [0xD0] [DISP_MODE]     —— 共 2 字节
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `DISP_MODE` | `0` = 频谱，`1` = 波形，`2`/`3`/`4` = 李萨如的三档 | 超出范围**夹到 0~4** |

★★ **是"夹紧"不是"取模"**：`5 → 4`、`255 → 4`、`-1 → 0`。
两边（`fpga_proto.clamp_disp` 与 RTL）逐字同规则，有专门的回归项钉住这一条。

★★★ **V48.2：五档一一对应（不再折叠）**。V48 第一版只到 `0~2`，
把李萨如的三档折叠成了一档 —— 用户指出"**李萨如图形有三档**"，改成现在就对了：

| `DISP_MODE` | 画面 | 板内 `liss_src` |
|---|---|---|
| `0` | 频谱 | — |
| `1` | 波形 | — |
| `2` | 李萨如 · 左×右 | 0 |
| `3` | 李萨如 · 干声×效果后 | 1 |
| `4` | 李萨如 · 相位 | 2 |

**是"直接设定"，不是"循环切换"** —— 板载按键 3 是"按一下换下一个"，命令是"设成某一档"。

**不受开窗限制**（和 `0xC9`/`0xCA`/`0xCB`/`0xCE`/`0xCF` 同类），
★ 而且**刻意不加任何 `armed` 门控** —— V38 那道门造成过"效果开关永久失灵"
（用户无法自救的死状态），是本工程最贵的一次教训。

## 17.3 FPGA → 上位机（`0x5F`）

```
FPGA -> 上位机：  [0x5F] [DISP_MODE] [REC_ON]   —— 共 3 字节的【独立新帧】
```

| 字段 | 取值 | 说明 |
|---|---|---|
| `DISP_MODE` | `0`~`4` | 板子**当前实际生效**的显示模式（★ 五档，和上面那张表一一对应） |
| `REC_ON` | `0` / `1` | 板子当前的录音开关 |

★ 上位机侧**必须按 `0~4` 校验**：超出的一律当假帧丢掉并重新同步
（真帧里 `DISP_MODE` 恒在 0~4）。

**发送时机**（三条，合起来才叫"双向同步"）：

1. **这两个值任意一个变化时** —— 包括**用户在板子上按 TTP 键3 / 键10**。
   ★ 这一条是关键：上位机不是单方面下命令，板子也会主动说话。
2. **复位后**强制发一次（让上位机一定拿得到出厂状态）。
3. **收到 `0xCB`（请求回报一次状态）时**强制发一次。

★★ 第 3 条是**"上位机一连接就对得上"的关键**：电脑版打开串口 600ms 后会自动发一条
`0xCB`，板子顺势把显示模式/录音状态报上去，界面那行小字立刻从"未知"变成真实状态 ——
**不用等用户在板子上按一下**。协议里没有"查询显示模式"的专门命令，靠的就是搭 `0xCB` 这趟车。

★ **不做周期上报** —— 免得跟录音的 `0x5A` 事件流抢带宽。

★ `REC_ON` 这一半和 `0x5B`（2 字节老帧）**故意重复**。板子按 TTP 键10 时两帧都会发，
**谁先到没有约定**，所以上位机侧必须把"上升沿 = 新一遍录音开始（要清空已录事件）"
抽成**一个共用入口**给 `0x5B` 和 `0x5F` 共用 —— 各写一份的话会把刚录的第一遍清两次、丢音符。

## 17.4 ★★ 五档一一对应（V48.2 定稿；V48 第一版的"粗粒度"已废弃）

板子内部 `disp_mode` 就是**5 档**循环（TTP 键3），协议现在**原样用它**：

```
频谱 → 波形 → 李萨如(左×右) → 李萨如(干声×效果后) → 李萨如(相位) → 循环
  0      1            2                  3                 4
```

**`DISP_MODE` 就是这 5 个值本身**，上下行都是 —— 上位机五个单选按钮，
一个档对一个按钮，谁也不用猜。

> ★★ **V48 第一版曾经做过"5 档 → 3 档"的折叠**（2/3/4 一律上报 2、下行只到 0~2），
> 理由是"李萨如那三档在上位机看来是同一档"。**用户一句话就把它否了**：
> 「**李萨如图形有三档**」—— 三档当然要能直接选，也要能看出板子现在在哪一档。
> 教训：**"信息合并"这种设计决定，只要界面上存在对应物，就该先问用户**，
> 不要替用户决定"他不需要区分"。

★ 由此带来的行为变化（V48.2 起）：**板子在 2→3→4 之间切换时【会】发 `0x5F`**
（V48 第一版因为三档编码相同所以不发）。这正是"双向同步"要求的。

★★★ **为什么上位机必须校验 `DISP_MODE ∈ 0..4`**：
板子内部 3 位、相邻档之间会**同时翻多位**（`1 → 2` 是 `001 → 010`，
`3 → 4` 是 `011 → 100` 三位全翻）。如果直接用两级同步器把这 3 位搬过时钟域，
采到的可能是**中间态** —— `1 → 2` 有可能读成 `000`（= 频谱）或 `011`（= 3）。
而 `0x5F` 是"变了就发"，**发出去的假帧收不回来**：读到 0 会真的把界面切到"频谱"。
所以跨时钟域用**"翻转沿 + 数据握手"**（数据先稳、沿后到、接收侧在沿上锁存），
**两个方向都是** —— ★ 5 档有 3 位，比 3 档时**更需要**握手。
逐拍仿真 `testfiles\sim_disp_mode.py` 第 10 节专门做了这个对照。

## 17.5 板内落点

**`src\uart_packet_echo.v`（clk_50m_ext 域）**

- `DISP_SET_BYTE` / `DISP_STAT_BYTE` 两个 localparam；
- `disp_wait`：`0xD0` 的 1 个操作数还没到 —— ★ 和 `vel_wait` 一样，
  **两个集合（`op_wait` / `any_op_wait`）都要加、超时也要清**；
- `disp_tgl` / `disp_val`：给 top.v 的写口（见下）；
- `disp_mode_in`：top.v 回送来的"当前显示模式"（已同步到本域），本模块**只看不写**；
- `dp_*`：0x5F 的独立组帧状态机（3 字节）。
  ★★ **绝不复用 `fx_idx`** —— 那是 `0x5D` 的索引，它的字节映射是钉死的，
  塞进去就必须改 `0x5D` 的长度或映射，而 `0x5D` 是**已经上线、两端都在解析**的帧。
- ★★ **新帧必须接进"总线仲裁"**：`st_start` / `fx_start` / `mt_start` / `rec_load`
  四条启动条件里都要加 `dp_idx == 0`，`rec_busy` 里也要算上它，
  `dp_push` 要接进统一入队。
  **漏一个的后果是"两路在同一拍启动，后一路的字节被悄悄吞掉"** ——
  帧缺字节、整帧错位，而且查不出来。`check_rtl_contract.py` 第 [9] 节会把这一组条件逐条钉住。

**`src\top.v`（跨两次时钟域）**

| 方向 | 做法 |
|---|---|
| 上位机 → 板子 | `disp_tgl` 三级同步 → 沿检测 `dsp_we` → 在**唯一那个** `disp_mode` always 块里锁存 `{1'b0, disp_val}` |
| 板子 → 上位机 | `dsp_rep = (disp_mode >= 2) ? 2 : disp_mode[1:0]` → 变化时翻转 `dsp_rep_tgl` 并锁存 → 三级同步 → 沿上锁存成 `disp_mode_rep` → 送 `uart_packet_echo` |

★★ **`disp_mode` 全文件仍然只有【一个】always 块驱动**（两个块驱动同一个 reg 会 `EX2000`）。
写口只是**优先级更高的一条路**，板载按键那条 5 档循环**一个比特都没改**：

```verilog
if (!rst_n)        disp_mode <= 3'd0;
else if (dsp_we)   disp_mode <= {1'b0, disp_val};   // ★ V48 上位机写口
else if (btn_wave) disp_mode <= (disp_mode >= 3'd4) ? 3'd0 : (disp_mode + 3'd1);
```

## 17.6 界面对齐规则（电脑版与安卓版必须一致）

1. **0.35 秒防抖**再发 —— 连点三个按钮只发最后那一个（命令是"设定"，中间态没有意义）。
2. **插队发** —— `0xD0` 不受开窗限制，所以要插到队列前面（和 `0xC9`/`0xCA`/`0xCB`/`0xCE`/`0xCF` 同类）。
3. **防回环**：收到 `0x5F` 回写控件时必须立一个标志位（`setChecked` 会触发监听器），
   否则两端乒乓 —— 这是第 12 章的老坑，照那道闸抄。
4. **「待确认」要值对上才撤**；**1.2 秒超时如实写"未确认"**，不能假装成功。
   ★ 有一个正常会出现"未确认"的情形：**点的正好是板子当前那一档** ——
   值没变，板子按协议不发帧。这时界面显示"待确认…"，随后连接时那条 `0xCB`
   的回报会把它确认掉（或者用户在板子上动一下）。
5. **串口没开时点的改动要记着，连上以后补发一次**。

## 17.7 版本影响

- **`0x5D` 逐字节不变**（仍然 4 字节）；**`0x5B` 逐字节不变**（仍然 2 字节）。
- 新增 2 个字节：`0xD0`（上位机 → 板子）、`0x5F`（板子 → 上位机）。
- **两端必须同步更新**（`fpga_proto.py` / `fpga_rec.py` / `spp_assistant.py`
  + `FpgaProto.java` / `FpgaRec.java` / `MainActivity.java`）。
- `0xD0` / `0x5F` 必须登记进**操作数长度表**（`_OP_LEN`），
  否则分块时可能把"命令 + 操作数"从中间切开，而命令是插队发的，
  正好落进那一对中间就会被当成操作数吃掉。
- 老固件不认 `0xD0`：操作数会被当成音符号或走超时；也不会发 `0x5F`，
  界面就一直显示"未知"——**不会显示错的档位**（这一点是刻意设计的：
  不知道就说不知道）。

## 17.8 ★★★ `0xD1` 手动重置 LCD（V48.5）

**一句话**：`[0xD1]`，**没有操作数**。板子收到后**重跑整张初始化表 + 全屏清 +
作废谱线缓存**，而且**先等 1 秒**（比开机的 0.2 秒更长）。

**为什么加**（用户实测报的，原话）：

> 「还是容易在数据量多时卡死，**虽然在软件上各个按键状态同步没问题，
>   但是就是 LCD 卡住不动**」

实测三条，缺一条都推不出结论：

| # | 现象 | 说明什么 |
|---|---|---|
| ① | 卡住时**连换显示模式画面都不变** | 不是"某一块画面不更新"，是整屏不响应 |
| ② | 画面**完全定住** | 同上 |
| ③ | **看门狗毫无动作**（屏幕不闪、不清） | ★★ FPGA 的**状态机是活的** —— 是【屏自己失步了】 |

★★ **这类失效看门狗救不了**，原因是结构性的：

- 看门狗只看**状态机**（`state` / `play_idx`），**它看不到屏**；
- 而"**屏失步**"和"**画面本来就是静态的**"在没有反馈的情况下**长得一模一样**；
- 按时间瞎重置就是退回"每 0.8 秒刷一次屏"的老毛病 ——
  V48.4 刚刚把"合法的静态画面"从误触发里摘出来（见第 5 节坑 50），
  绝不能再走回去。

所以这一类只能给**人来按**的逃生通道。**屏为什么会失步**（板级原因，不是 RTL 的锅）：
排线受干扰、命令被截断（CS 在字节中间被拉开）、或者密集按键时 36 颗 LED
一起亮导致电流/噪声上去、屏那一侧抖了一下。

**板子侧行为**（`uart_packet_echo.v` → `lcd_master.v`）：

1. 解到 `0xD1` → **把 `lcd_rst_tgl` 翻转一次**（★ 用翻转沿，不是脉冲/电平：
   电平方案万一接收侧正忙漏采一拍，用户这一下就白按了）；
2. `lcd_master` 打两拍 + 边沿检测 → 得到干净的单拍请求；
3. **优先级最高**（高于看门狗）→ 回 `S_POWER_ON`，**等待 1.0 秒**
   （给失步/抖动的屏更长的稳定时间），然后重跑 `S_INIT` 的整张初始化表
   （★ 表尾是 `SLPOUT(0x11)` + `DISPON(0x29)`，**足以把被假命令搞乱的屏救回来**），
   接着全屏清 + 重画；
4. **顺手把 `bar_bad` 整片置 1** —— 否则清完屏一列都不会重画
   （这正是第 5 节坑 50 修过的那个坑，新路径上不能再犯一次）。

**上位机侧规则**：

1. **插队发**（不受开窗限制、随时可用，和 `0xC9`/`0xCA`/`0xCB`/`0xD0` 同类）——
   发谱子发到一半卡住时，正是最需要按它的时候；
2. ★ **不设"待确认"**：板子**不回报**这条命令（协议里只有 `0x5F` 报显示模式 +
   录音开关），所以界面只能如实写"已发出"，**能不能救回来以画面为准**；
3. `0xD1` **不登记进 `_OP_LEN`**（它没有操作数，登记成长度 0 没有意义）。

**`0xD1` 不会和任何帧头混淆**：上行帧头是 `0x5A/0x5B/0x5D/0x5E/0x5F`，都不等于 `0xD1`；
它也不是任何命令的操作数（无操作数命令，和 `0xC7`/`0xC8`/`0xCB` 同类）。

**这一条命令救不了什么**（如实说）：如果屏是**硬件坏**（背光灭、排线断、供电没了），
软件做什么都没用 —— 那时需要的是拔电重上或查硬件。它的作用是
**把"屏被搞乱了"和"屏真的坏了"区分开**：按一下能回来 = 前者。


# 第 18 章  ★★ 回显与状态帧头的冲突（V48.1）

> ★ 这一章不属于任何一条新协议，而是**协议里一个一直存在、V48 才被实测抓出来的陷阱**。
> 它害得用户以为"软件自己把混响和合唱打开了"。凡是以后要**新增状态帧头**，
> 或者**新增带任意值操作数的命令**，都必须先读这一章。

## 18.1 机制

板子会把收到的字节**原样回显**给上位机（v1 就有的行为，只有 `0xAA` 不回显，
见 §4.6）。而上位机要在**同一条串口流**里找板子**主动发**的状态帧：

```
板子 -> 上位机（回传帧头）： 0x5A 0x5B 0x5D 0x5E 0x5F
```

于是有一个天生的危险：

> **只要上位机【发出去】的操作数里出现了这 5 个字节之一，
> 它的回显就会被上位机当成一帧真状态。**

而协议里有好几类操作数是**任意值**：

| 命令 | 操作数 | 值域 |
|---|---|---|
| `0xC3` 力度 | VEL | 0~127（每格事件一个，**最常见**） |
| `0xC2` 时值 | N | 0~255 |
| `0xC4`/`0xC5` 时间参数 | 3 字节 µs | 任意 |
| `0xCF` 节拍器 | BPM | 30~240（**含 5 个帧头值**） |

## 18.2 真实事故（2026-10-11 用户实测）

> "每次发谱，软件自己就把**混响和合唱**显示成打开，音色有时还变成**笛子**；
>  点一下「刷新状态」就正常了。"

根因：某格事件的**力度正好是 93（`0x5D`）**，而它是和弦：

```
发出去（也会被回显）：  C3 5D C0 01 ...
上位机读成：            0x5D 帧 -> fx = 0xC0 = 混响+合唱
                                  下一个字节 0x01 被当成音色 = 笛子
```

★ 本机 MIDI 目录 **12 首里有 10 首**会命中（93 是很常见的力度值）。
★ **"刷新一下就好了"是这个 bug 的指纹** —— `0xCB` 会让板子回一帧真状态把它盖掉。

## 18.3 治法（两道一起上）

### ① 发送侧消毒：操作数不许等于帧头

`fpga_proto.safe_operand()` / `safe_u24()`：凡是落在 `{0x5A,0x5B,0x5D,0x5E,0x5F}`
上的操作数值，**微调 1~2** —— 力度差 1/127、时间参数差几 µs、时值差 1 格、
BPM 差 1，都是听不出来的量级。

> ★★ 帧头是 **90/91/93/94/95 连在一起**的，所以"取 ±1"不够 ——
> `94` 的左右邻居 `93`/`95` **也都是帧头**。必须一圈一圈往外找。
> ★ 四处都要过：**力度、时值、时间参数、`0xCF` 的 BPM**，漏一处就还漏一个洞。
> ★ `BPM = 0`（关）不受影响（0 不是帧头）。

### ② 接收侧：`0x5D` 改成"候选帧"

`fpga_rec` 里 `0x5D` 不再立刻写 `fx_state`，先存成候选：

| 下一个字节 | 结论 |
|---|---|
| `≤ TONE_MAX`（合法音色，**V48.3 起 = `≤ 3`**）→ 再下一个 `≤ 1`（合法跟谱模式） | 真帧，提交 |
| 帧头（老固件的 2/3 字节帧） | 真帧，提交（**不吃掉**那个字节） |
| 其它 | **假帧，整帧作废**（`fx_state` 一个比特都不动） |
| **这一批读到底了，还没等到反证** | **当它是真帧，结清** |

> ★★ 最后那一行是关键：老契约要求"`[0x5D][fx]` 单独一批到也要**立刻**更新状态，
> 音色可以下一批再补"（帧完全可能被串口分批切开）。所以判据是
> **"批内能证伪就证伪、批内证不了就当真的"** —— 既修了回显撞帧头，
> 又不动任何已有行为（`selftest.py` 会验这一条）。
> ★ `0x5B` 也补了校验（开关字节必须 ≤ 1）。它比 `0x5D` 更危险：
> **假帧的"上升沿"会把已录到的事件整段清空 —— 那是真丢数据。**

## 18.4 判据

`test_echo_collision.py`（**30 项**）：

1. MIDI 目录 + 工程测试谱子**全部**：整帧发出去 → 回显 → 解析，状态不许变；
2. 穷举力度 0~255 × 4 种后继 = 1024 组（**走真实编码器**，不是手搓字节）；
3. 时值 255 组 + 时间参数 3006 组 + **256 个 BPM**（含板子紧接着回的 `0x5E`）；
4. 真帧照旧（`0x5D` 4 字节 / `0x5B`）—— 不能因为加校验就不认板子的状态帧。

## 18.5 ★ 更彻底的做法（已列入待办）

**板子侧"操作数不回显"。** 回显里真正危险的只有操作数 —— 命令字全在
`0xC0~0xD0`，一个都不是帧头。这和"**录音期间不回显**"（§9.6）是**同一个理由**，
项目自己已经有先例。做了它，这一类就从根上没了，
**第三方上位机（串口助手之类）也不会再踩**。

> ★ 纪律：以后**新增状态帧头**时，必须同时问两句：
> ① 现有操作数里有没有可能出现这个字节？② 我的发送侧消毒覆盖到它了吗？
> 新增**带任意值操作数的命令**时同理。

## 17.9 ★★★ `0xD2` 测试模式开关 / `0x60` 状态帧（V49）

**一句话**：`[0xD2]`，**没有操作数**，收到就**翻转**测试模式；
板子用**独立新帧** `[0x60] [TEST_ON]`（2 字节）把当前状态回报上来。

### 17.9.1 它做什么

赛题的**现场验证要求**是"支持测试模式下输出多路不同频率音频，频谱可观测
对应数量的独立谱峰"。测试模式就是那 **52 路**：

| 组成 | 路数 | 说明 |
|---|---|---|
| 键位测试音 | **36** | 36 个键位各给一个固定频率 |
| 专用测试振荡器 | **16** | 频率安排在 36 个键位之外的频段，便于在频谱上分开数 |

★ 这 52 路是**同时发声**的，所以"数谱峰"这一条现场可以直接做。

### 17.9.2 上位机 → FPGA（`0xD2`）

| 字节 | 值 | 含义 |
|---|---|---|
| 0 | `0xD2` | 翻转测试模式（**没有第 1 个字节**） |

- ★ **不受开窗限制、可插队**（和 `0xC9` / `0xCA` / `0xCB` / `0xD0` / `0xD1` 同类）——
  现场演示时随时要进、要出。
- ★ **不设"待确认"**：这条命令不单独应答（回显是原样回显），
  能不能进以 `0x60` 为准。

### 17.9.3 FPGA → 上位机（`0x60`）

| 字节 | 值 | 含义 |
|---|---|---|
| 0 | `0x60` | 帧头 |
| 1 | `TEST_ON` | `0` = 普通模式，`1` = 测试模式（★ 真帧恒 0/1） |

- **发送时机**（与 `0x5F` 完全同构）：
  ① 两个值**任意一个变化**就发一次（含**板子上按 TTP 第 11 键**那条路）；
  ② **复位后强制发一次**（上位机一连上就对得上，不用等用户去按）；
  ③ 收到 `0xCB`（"回报一次状态"）时跟着 `0x5D` / `0x5E` / `0x5F` 一起补发一次。
- **不做周期上报**：只有变化时才发。
- ★ `0x5D` / `0x5E` / `0x5F` 的**字节映射一个都没动**（另开一台 `ts_*` 状态机）。

### 17.9.4 为什么用"翻转"而不是"设成 1/0"

和 `0xC9`（效果开关）/ `0xD1`（重置 LCD）**同一个理由**：

> 翻转的语义和"按板子上那个按钮"**一模一样**，**板子永远是唯一权威** ——
> 上位机不需要知道当前状态就能安全地切，也就不会出现
> "软件以为它是关的、其实是开的，一设反而设反了"。

所以**板载按钮和上位机按钮走的是同一条路**：

| 来源 | 板内落点 |
|---|---|
| 按钮板**第 11 键**（`btn_new[10]`） | `top.v`：`test_hold <= ~test_hold` |
| 上位机 `0xD2`（`test_tgl` 翻转沿） | 同上（`tst_we` 边沿） |

★ 于是"**按键与软件双向同步**"这条要求在这条命令上天然成立：
在板子上按一下，上位机会收到 `0x60`；在上位机点一下，板子状态跟着变。

### 17.9.5 板内落点

| 位置 | 作用 |
|---|---|
| `uart_packet_echo.v` | `0xD2` 解析 → `test_tgl <= ~test_tgl`；`test_state_in` 只读回读状态；`ts_*` 一台小状态机负责 `0x60` 组帧 |
| `top.v`（`clk_50m`） | `test_hold` = 唯一权威状态；`btn_new[10]` 与 `tst_we` 两条路都翻它 |
| `top.v`（音频域） | `test_hold` 两级同步成 `test_on`，驱动 52 路测试引擎 |
| `top.v`（`clk_50m_ext`） | `test_hold` 两级同步成 `test_state_out` → `uart_packet_echo.test_state_in` |

### 17.9.6 上位机怎么用

- **电脑版**：`fpga_proto.pack_test()` 发 `0xD2`；面板上「显示」那一行的
  **「测试模式」按钮**（就在「重置LCD」旁边），小字显示板子回报的状态
  （未报过时显示"未知"）。
- **安卓版**：同一个按钮、同一个 `0x60` 回报，状态跟着板子走。
- ★ 收到 `0x60` 时**只改显示、不回发**（否则会和板子来回打架）。

### 17.9.7 按第 17 节那条纪律自查（新增帧头必须问两句）

| 问题 | 答案 |
|---|---|
| ① 现有操作数里有没有可能出现 `0x60` 这个字节？ | **不会**：`0xD2` 无操作数；有操作数的命令（`0xC0`~`0xCF`）操作数都有明确值域，`0x60` 不在任何一条的值域内 |
| ② 发送侧消解覆盖到它了吗？ | **覆盖了**：板子把收到的字节原样回显，上位机的解析器先按"是不是帧头"分流，`0x60` 已在帧头集合里；而且 `TEST_ON` 只认 0/1，越界当假帧丢弃并重新同步 |

### 17.9.8 版本影响

- **V49 新增**。`0x5D` / `0x5E` / `0x5F` / `0xD0` / `0xD1` 的行为**一个字节都没动**。
- 老上位机（不认识 `0x60`）收到这一帧会把它当成"杂字节"丢掉，
  **不影响任何既有功能**（这正是另开新帧、不动旧帧的价值）。
