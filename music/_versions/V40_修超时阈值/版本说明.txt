一、一句话
------------------------------------------------------------------------
V40 = **V39 的全部内容** + **修掉一个我自己引入的严重 bug**（超时阈值太小，
导致蓝牙播放全乱）。合成链路、协议语义、上位机行为都没再动。

二、这一版修的 bug：超时阈值设小了
------------------------------------------------------------------------
### 现象（用户实测）
  · **"蓝牙播放完全乱了，一直播放着不知道什么旋律"**
  · **"所有的效果都没法通过上位机软件进行修改了"**

### 根因
V39.2 给"等操作数"加的兜底超时是 **6 个字节时间 = 6.24ms**。
我当时想的是"操作数紧跟命令字，间隔 1 个字节约 1.04ms，6 倍余量够了"——
**这个前提是错的**。

真实的时间尺度是【上位机分批之间的间隔】，不是字节间隔：

    · 一批 256 字节 @9600 波特 = 266ms
    · 安卓版还有背压：while (pendingCount() > 64) Thread.sleep(20) = 20ms

**266ms / 20ms 都远大于 6.24ms**。于是只要 `0xC2`（时值）落在批的末尾、
它的操作数在下一批开头，超时先把 `dur_wait` 清掉，操作数随后到达就
**被当成音符** —— 凭空多一个音。一首曲子几百个事件累积下来，
就成了"一直播放着不知道什么旋律"。
效果改不动是同一个根因的连带（谱子在乱放、界面状态也对不上）。

### 修法
`OP_WAIT_MAX` 从 6 个字节时间 → **500ms**，`op_wait_cnt` 位宽 **16 → 25 位**
（16 位最大只有 1.3ms，根本不够）。

★ 500ms 比最坏的真实间隔（266ms）还大近 2 倍，比背压间隔（20ms）大 25 倍。
★★ **这个修复不依赖上位机版本** —— 即使跑的是老的 App（按 256 字节硬切、
会把"命令+操作数"切开），500ms 也足够等它跨过批边界，不会再误判。
这一点是刻意选的：让它在【任何上位机组合】下都成立。

### 顺带把检查脚本的判据也改了
`check_rtl_contract.py` 第 [8] 节原来写的是"**OP_WAIT_MAX ≥ 4 个字节时间**"——
**那正是导致这次事故的错误标准**。现在改成：

    ok  OP_WAIT_MAX = 25000000 拍 = 500ms，必须远大于背压间隔 20ms

并注明判据依据（正常间隔上限 = 批间隔 ≤ 266ms / 背压 20ms）。
跑这次回归时它还顺手抓出两个小 bug：Verilog 数字里的下划线分隔符
（`25_000_000` 让正则只抠出 `25`）、以及位宽 16→25 后正则里写死的 `16'd1` 漏改。

三、V39 那批改动（这一版全部包含）
------------------------------------------------------------------------
V40 = V39 + 上面那个修复，所以 V39 的内容都在：

**① 回滚 V38 的"效果开关门控"**（用户实测"延迟关不掉"）
   · 撤掉 `uart_packet_echo.v` 里 `0xC9`/`0xCA` 上的 `&& !armed` 门；
   · `spp_assistant.py` 的 `_send_front` 恢复【无条件插队】，
     `_write_loop` 的 `_tx_busy` 一并移除；
   · `BtSpp.nextBatch()` 恢复"每一批都先看优先队列"；
   · 两侧测试断言改回"插到队首"。
   → `spp_assistant.py` 与 V37 **逐字节一致**（只多了说明注释）。

**② V39.1：整帧分块切在【协议单元边界】上**
   原来按 256 字节硬切，会把"命令字+操作数"从中间切开，而控制命令是【插队】
   发的 —— 插队命令正好落进那一对中间，被板子当成参数吃掉（参数被污染 +
   整帧错位）。现在 `fpga_proto.safe_chunk_ranges()` /
   `FpgaProto.safeChunkRanges()` 按协议单元边界切块：**插队最多落在两个完整
   单元之间，完全无害**。`fpga_proto` selftest 30 → 36 项。
   ★ 这解释了为什么这个毛病"一直是偶发的"（每帧约 1% 机会），
     也印证了用户说的"原来就没有误触发的 BUG" —— 不是没有，是极罕见。

**③ V39.2：板内两个"状态卡住"的隐患，用超时治**（阈值已在 V40 修正）
   · 五个"等操作数"状态（`map_left`/`oct_left`/`key_oct_left`/`cfg_left`/
     `dur_wait`）原来**一个超时都没有** → 操作数丢了就永久卡住，
     之后每个字节被当成操作数吃掉（`map_left` 是每 2 字节吃一对）；
   · `armed` 只在 `0xAA` 置 1、`0xFF` 清 0，而**上位机的「停止演奏 / 重播 /
     按键映射下发」都会清发送队列**，能把帧发到一半截断 → `armed` 永久为 1。
   → 两处都改成**超时自动恢复**（500ms），而不是"卡住就失灵"。

**④ 契约脚本加了 8 项超时纪律检查**（68 → 76 项）：`any_op_wait` 必须覆盖
   全部 7 个等待状态、超时分支必须把它们全部清掉、`armed` 必须有超时关窗、
   阈值必须远大于背压间隔。

  Max Frequency Summary（V39 / V38 / V37 放在括号里）：
    clk_50m   约束 50.000  实际 **55.624**（56.470 / 57.495 / 66.708）
    CLKOUT0   约束 12.500  实际 **25.936**（24.686 / 28.445 / 31.245）  ← 音频域
    CLKOUT1   约束 50.000  实际 **50.007**（50.053 / 50.054 / 50.246）

  ★★★ **CLKOUT1 只剩 0.007 MHz 余量（0.014%），这是当前最危险的一条** ★★★
     TNS = 0，所以**这个 bitstream 是时序收敛的、可以烧**；
     但它已经贴着约束线，**温度/电压稍有变化就可能出问题**。
     来源：这个域（UART + LCD）从 V36 起就没有余量，而 V38/V39 又往里面
     加了 UART 三次采样表决、等操作数超时计数器（25 位 + 比较器）。
     ★ **下一步必须处理它**：把 25 位计数器的比较器去掉
       （阈值改成 2 的幂，只判断最高位），并把两个计数器合并成一个 ——
       能省 25 个寄存器 + 2 个 25 位比较器。

  ★ CLKOUT0（音频域）25.936，余量 2.07 倍，健康（V39 是 24.686，这一版略回升）。

★ 关于这次 bug 的验证缺口（如实记）：**我没有任何测试能抓住"超时阈值太小"** ——
  它是一个跨"板内计数器 / 上位机分批 / 背压"三者的时间尺度问题，
  而工程里的仿真都是单侧的。现在只补上了**契约层面的静态判据**
  （阈值必须 ≥500ms），真正的行为验证仍然只能靠上板听。
  ★ 教训：**给"兜底超时"选阈值时，必须先把【所有真实的间隔上限】列出来**
    （这里至少有三个：字节间隔 1.04ms、批间隔 266ms、背压 20ms），
    取最大的那个再留几倍余量 —— 我当时只看了最小的那个。

六、上板看什么
------------------------------------------------------------------------
  · **最要紧的**：放一首熟悉的曲子，应该是**原样**，不能有任何错音/乱音。
  · 效果开关（延迟/滑音/混响…）：点一下立刻生效，界面状态跟着板子回报落定。
  · 起音"噗"声应该没有（V38 的斜坡修复保留着）。
  · 播放中点「停止演奏」再点「重播」：板子 500ms 后自己关窗恢复（V39.2 修的）。
