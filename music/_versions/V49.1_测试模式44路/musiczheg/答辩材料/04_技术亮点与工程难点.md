## 案例 1 ★★★ 时序瓶颈的真实病因，和当初猜的完全不一样

### 发现问题

`CLKOUT1`（UART + LCD 域）的时序余量长期只有 **0.014%** ——
实测 **50.007 MHz** 对约束 50.000 MHz，**slack 只有 +0.003 ns**。
这条路径贴在约束线上，**任何改动都会把它压过线**，是工程里最大的定时炸弹。

### 最初的猜测（错的）

团队一致认为瓶颈在 **UART 的那几个超时计数器**上——因为它们位宽大、
比较逻辑长，看起来最像"长得慢"的东西。
对应地设计了两个优化方案：
① 把超时阈值改成 2 的幂，让比较器退化成位选；
② 合并两个计数器。

### 定位过程

**关键动作：不猜，去读时序报告的路径明细。**

从 `impl\pnr\music_tr_content.html` 的 Setup Paths Table 里读出来的
**最差路径根本不是 UART**：

```
u_lcd/wave_buf.../DO  →  …  →  u_lcd/cur_data_*/D
          数据延迟 20.7 ns
```

**是 LCD 波形显示的那条 21 级组合链。**

而且**实测 UART 那几个超时计数器的 slack 还有 +2.0 ns，是通过的**——
当初的猜测被数据直接否掉。

那条链的组成（逐级列出来，这就是"21 级"的来源）：

```
BSRAM 输出 (wave_buf.DO)
  → 取绝对值
  → 16 位桶形移位（>> wave_sh）
  → 补符号
  → 17 位加中线
  → 上下限幅
  → 线段比较
  → 像素字节
  → cur_data 寄存器
```

### 修复

**治法：从中间插两级流水线寄存器**（沿用本工程 V17c 把 `peak_msb` 打一拍的同一个套路）：

| 插入点 | 寄存器 |
|---|---|
| 波形 y 坐标打一拍 | `wave_y0` / `wave_y1` → `wave_y0_r` / `wave_y1_r` |
| 缩放结果打一拍 | `v0_sc_r` / `v1_sc_r` |

> ★ **一个必须同步的细节**：符号位 `v0_sgn_r` **必须和幅值同步打一拍**。
> 否则**符号比幅值早一拍，负半周会画反**。

### 为什么插在那里一定安全（三条论证）

**这是本案例最值得讲的部分——插流水线不是"插了就完事"，要能证明它无害：**

1. **读地址只跟 `wave_col` 走**：`wave_rd_addr0 = frame_wr - 320 + wave_col`，
   而 `frame_wr` 是"**一帧开始时锁住的写指针**"，**不是连续推进的指针**。
   所以**一整列里 `wave_v0/v1` 和 `wave_sh` 都不变** ——
   这两级寄存器每拍寄存的都是同一个值，只是**晚 20 ns 生效**。
2. **时序余量充足**：`wave_col` 一整列才 +1 一次，之后状态机先跳到
   `S_WAVE_WIN` 把 11 字节窗口命令发完（**88 拍**）才读第一个像素；
   而 `wave_y0` 在 `wave_col` 变化后 **3 拍内**就稳定。
   一整列 ≈ **5760 拍**，这 3 拍占 **0.05%** —— 显示上看不出来。
3. **下游一个字没动**：`wave_seg_lo/hi`、`wave_draw_seg`、`wave_pix_hi/lo`
   全部照旧，波形的"哪一列用哪两个采样点"**逐位不变**。

### 验证

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| `CLKOUT1` Fmax | **48.039 MHz**（拥塞后） | **58.046 MHz** |
| 对 50 MHz 约束的余量 | **−3.9%**（TNS −4.938 ns / 8 条） | **+16%** |
| 三域 TNS | 有违例 | **全部 0** |
| 最长路径位置 | LCD 里 | **已不在 LCD 里** |

> ★ 后续版本 `V43` 把 `CLKOUT1` 进一步做到 **59.197 MHz**。

### 教训

> **"改阈值 + 合并计数器"治不了这个病** —— 那条优化可以不做。
> **瓶颈必须从时序报告的路径明细里读出来，不能靠"看起来最像"来猜。**

**出处**：`impl\pnr\music_tr_content.html`；`lcd_master.v`（代码注释里标了**「别删」**——
删掉任何一级，`CLKOUT1` 立刻回到 48 MHz）

## 案例 2 ★★ 「我的改动不在那个域」≠「那个域的时序不会变差」

### 发现问题

`V41` 给工程加了 **LED 演奏指引**（`led_guide.v`，约 **190 个 LUT**）。

它的逻辑**全部在音频域，一个门都不在 `CLKOUT1` 上**。
按常理，`CLKOUT1` 的时序**不应该受影响**。

**但实测**：

| 时钟域 | V40 | **V41 加了 led_guide 之后** |
|---|---:|---:|
| `CLKOUT1` | 50.007 MHz | **48.039 MHz** ← 反而变差了 |
| `CLKOUT1` TNS | 0 | **−4.938 ns / 8 条** |

### 定位

**根因不是"新逻辑本身慢"，而是布局被扰动。**

`V40` 那条 `CLKOUT1` 的最差路径本来就只有 **+0.003 ns 余量**
（19.997 ns / 20 ns 周期）—— **它贴在约束线上**。
任何新增逻辑都会改变布局布线，**把这条本来就悬着的路径压过线**。

### 修复

修的就是**案例 1** 那条 LCD 21 级组合链——因为它是 `CLKOUT1` 唯一的历史遗留瓶颈。
**治本之后，`CLKOUT1` 从 48.039 → 58.046 MHz**，余量从 −3.9% 变成 +16%。

### 验证

修复后重新加 LED 逻辑，`CLKOUT1` 仍然是 58.046 MHz，三域 TNS 全 0。

### 教训

> ★★ **「我的改动不在那个域」≠「那个域的时序不会变差」。**
> **加完任何东西，都要重新看【每一个】时钟域的 Fmax 和 TNS，不能只看自己那个域。**
>
> 附带的操作纪律：**当一条路径余量只剩 0.015% 时，它已经不是"通过"，
> 而是"随时会挂"**。这种情况必须先治本，再谈加功能。

**出处**：`impl\pnr\music_tr_content.html`（`V40` 与 `V41` 两次构建的对比）

## 案例 3 ★★ 跨时钟域：数据必须先稳定，翻转沿要晚 1~2 拍

### 发现问题

**用户实机报告**：「按『谐波』，结果翻了『滑音』。」

也就是说：**用户按下一个按钮，变的是另一个功能。**

### 定位

这是一个典型的**跨时钟域（CDC）握手错误**。当时的写法是：

```
数据与翻转沿【同拍变化】
```

**为什么这会导致"张冠李戴"**：

接收侧用**两条并行的两级同步链**：
- 一条同步**翻转沿**
- 一条同步**数据总线**（多位）

这两条链在物理上走**不同的布线**，各自的延迟**不一样**。
当"沿"和"数据"在同一拍发出时，**接收侧谁先到取决于布线**：
- 如果**沿先到、数据后到** → 采到的是**旧数据**；
- 如果数据先到、沿后到 → 采到的是新数据。

**同一次设计，不同位置的两个开关（谐波 / 滑音）可能落在两种情况上** ——
于是"按谐波翻了滑音"。

### 修复

**遵守 CDC 握手的经典规则**：

```
① 数据先变化并【保持稳定】
② 晚 1~2 拍之后，再翻转"有效"标志沿
③ 接收侧看到沿之后才去采样数据（此时数据已经稳定很久了）
```

这套模式在本工程里被固化成标准写法（`*_tgl` + `*_d1/d2/d3` 三级同步）。

### 验证

修复后所有跨域控制信号都遵守该规则；`music.sdc` 里把这些路径
显式声明为异步，STA 不再报假违例。

### 教训

> ★ **多位数据绝对不能和它的"有效沿"同拍过时钟域。**
> 这不是理论风险——**它是"按 A 键改了 B 功能"这种玄幻 bug 的经典成因**。
>
> 附带的一条：本工程在 `music.sdc` 里用
> `set_clock_groups -asynchronous -group [get_clocks {clk*}]`
> 把三个域声明为异步。**加这条之前**，STA 会把 50 MHz 域和 12.5 MHz 音频域
> 当**同步域**去算，报出一堆两级同步器第一级的 HOLD 违例
> （最差 **−1.367 ns**，端点全是 `pressed_mask_sync1` / `tr_audio_r` /
> `event_toggle_d1`）—— 这些**都是假违例**。

**出处**：`music.sdc` 第 44~73 行；`top.v` 的 CDC 同步段

## 案例 4 ★★ 存储数组多一个读口 → BSRAM 推断失败

### 发现问题

给 `uart_packet_echo.v` 加一块"下一格按键"的影子数组之后：

| 指标 | 加之前 | 加之后 |
|---|---:|---:|
| `BSRAM` | 88 | **88**（没涨） |
| `--SSRAM(RAM16)` | 214 | **808** ← 暴涨 |
| `Logic` | 38687 | **43894** ← +5207 |
| `CLKOUT1` 余量 | — | **被吃光** |

**1024 × 36 位的数组没有进 BSRAM，退化成了分布式 LUT RAM** ——
多出来的 ~594 块分布式 RAM 正好等于一块 36×1024 的数组。

### 定位（这一段是本案最有价值的部分）

**做了 5 次单变量实验，全部失败**，最后靠**对比一个已知能进 BSRAM 的写法**找到答案：

| 尝试 | 写法 | 结果 |
|---|---|---|
| V43 | `if (wr_slots != 0) slot_nxt[wr_slots - 1] <= ...`（地址是**组合线**） | ❌ 没进 |
| V43.1 | 去掉条件门，地址仍是组合线 `wr_nxt` | ❌ 没进 |
| V43.2 | 使能/地址/数据全打进寄存器，但写在**独立的 always 块**里 | ❌ 没进 |
| V43.3 | 读口改成寄存器直读 | ❌ 没进，还让 Tech-Mapping 卡住 |
| V43.4 | **地址用寄存器 `wr_m1`、写在同一个 always 块里** | ✅ **进了** |

**关键推理**：同文件里 `slot_oct0/1/2` 那三块**都进了 BSRAM**，它们的写法是

```verilog
slot_oct0[wr_slots] <= oct_blob[35:0];   // ← 地址是【寄存器】、在【同一个块】里
```

所以补齐唯一没试过的组合：**地址用寄存器、写在同一个 always 块里**，形状与
`slot_oct0` 完全一致 → **成功**。

### 修复

```verilog
reg [10:0] wr_m1;   // 每拍无条件更新，正好等于 wr_slots - 1
```

> ★ **延后一拍完全安全**：一个事件至少要等一个 UART 字节
> （9600 波特 @50 MHz = **5208 拍**），`flush_ok` 绝不可能连着两拍来，
> 所以不会出现"后一笔覆盖前一笔"。

### 验证

`BSRAM` 恢复正常，`SSRAM(RAM16)` 回落，`Logic` 降回 74%。

### 教训（两条可迁移的规则）

> ★★ **规则一：BSRAM 推断对"写口形状"极其敏感。**
> **地址、使能、数据三样都必须是寄存器，而且必须在同一个 always 块里。**
> 地址前串一个组合逻辑（哪怕只是一个条件或一个加法器）就可能掉出 BSRAM。
>
> ★★ **规则二：存储数组必须保持【单读单写】。**
> 多开一个读口综合器就不肯推断 RAM，**会退化成几千个 LUT**。
> 本工程的 `slot_mask` / `slot_dur` / `slot_oct0~2` / `slot_vel`
> **全部只有一个写口（`wr_slots`）和一个读口（`rd_slot`）**——这是硬约束。
>
> ★ **附带一条诊断纪律**：`syn_only.tcl`（只综合）的正确用途**只有一个**——
> **快速看"数组有没有进 BSRAM"**（看 `BSRAM` / `SSRAM` 两项）。
> **别用它比 LUT 数**：综合之后 PnR 还会做一轮优化，
> post-PnR 的逻辑数通常比 post-综合**少**，两个阶段的数字混着比会得出完全错误的结论。

**出处**：`uart_packet_echo.v:442-520`；`impl\pnr\music.rpt.txt`

## 案例 5 ★★★ 不要做"卡住就永久失灵"的设计

### 发现问题

**用户实机报告**：「**现在的『延迟』关不掉了，感觉逻辑乱了。**」

表现：一旦触发，**效果开关从此再也点不动，用户没有任何办法自救**（只能重新上电）。

### 定位

上一版为了挡住"插队命令吃掉谱子字节"，在板内加了一道门控：

```verilog
else if ((rx_data == FX_TGL_BYTE) && !armed)
```

**看着很合理** —— `armed` 表示"正在接收一帧"，不是接收期间就不理效果开关命令。

**但致命问题在 `armed` 的赋值上**：`armed` **全工程只有两处赋值**：
- `0xAA` 置 1
- `0xFF` 清 0

**而 `0xC7`（停止演奏）不清 `armed`。**

所以：**只要发帧中途出过任何状况**（发了 `0xAA`、`0xFF` 没等到），
`armed` 就**永久卡在 1** → 效果开关**永久失效**。

### 验证

静态检查 `armed` 的**全部赋值点**（只有 2 处），确认没有任何路径能把它清掉。

### 修复

**回滚这道门控**，恢复成"点一下立刻生效"。
`V40` 起改用**超时自动恢复**代替门控。

### 教训（本工程最贵的一次教训）

> ★★★ **加任何门控之前，先问两句：**
> **① 这个状态位会不会卡住？② 卡住之后用户还能不能自己恢复？**
> **只要任一答案是"会 / 不能"，这个门控就不能加。**
>
> ★★ **"门控"和"超时"的区别**：
> - **门控** = 「状态不对就**不许**用户操作」→ 状态卡住 = 用户死锁；
> - **超时** = 「状态不对就**自己退回去**」→ 状态卡住能自愈。
>
> **凡是要引入状态位影响用户操作的改动，优先做成后者。**
>
> ★ **修复要算总账**：这道门控修的是"偶发帧错位"
> （还只在"一边发谱子一边点开关"时才发生），代价是"开关可能永久失灵"。
> **宁可接受偶发的小毛病，也不要引入用户无法自救的死状态。**
>
> ★ 如果以后真要治"插队打断帧"，**正确做法是给帧加帧级校验**
> （让错位的帧整帧作废），**不是**去堵命令。

**出处**：`uart_packet_echo.v` 的 `armed` / `any_op_wait` 段

## 案例 6 ★★ 给"兜底超时"选阈值，必须先把所有真实间隔列出来

### 发现问题

**用户实机报告**：
> 「**蓝牙播放完全乱了，一直播放着不知道什么旋律，所有效果都没法通过上位机修改。**」

### 定位

上一版给"等操作数"状态加了一个兜底超时，阈值选的是
**6 个字节时间 = 6.24 ms**。理由是：

> 「操作数紧跟命令字，间隔 1 个字节约 1.04 ms」

**这个前提是错的。** 真实的时间尺度是【上位机分批发谱子时，**两批之间的间隔**】：

| 真实的间隔上限 | 数值 |
|---|---:|
| 一批 256 字节 @ 9600 波特 | **266 ms** |
| 安卓版背压 `while (pendingCount() > 64) Thread.sleep(20)` | **20 ms** |

**两个都远大于 6.24 ms。**

**失效链条**（每一环都可复算）：

```
0xC2（时值延长命令）落在批尾
        ↓
操作数在【下一批】的开头
        ↓
6.24 ms 超时【先】触发了，把 dur_wait 状态清掉
        ↓
操作数随后到达 → 被当成【音符】处理
        ↓
凭空多一个音 → 一首曲子累积下来全乱
```

### 修复

阈值改成 **500 ms**。

### 阈值怎么定的（这是本案的核心方法论）

> ★★ **判据：把所有可能的时间间隔列全 → 取最大的那个 → 至少留 2 倍余量。**

| 候选间隔 | 值 | 500 ms 的余量 |
|---|---:|---:|
| 一批 256 字节 @9600 | 266 ms | **1.88 倍** |
| 安卓背压间隔 | 20 ms | **25 倍** |

**还有一个刻意的选择**：
> **阈值要大到"不依赖上位机版本"** —— 即使跑的是老的 App
> （按 256 字节硬切、会把命令+操作数切开），500 ms 也够等它跨过批边界。
> **让修复在任何组合下都成立。**

### 验证

检查脚本原来写的判据是「**≥ 4 个字节时间**」——
**那正是错的标准**，已改成「**≥ 500 ms 且必须远大于背压间隔 20 ms**」。

### 教训

> ★★ **超时阈值不能凭"逻辑上应该够"来猜，必须去查真实时间尺度。**
> 本案里"操作数紧跟命令字"这个前提在**单批内**成立，
> 但**跨批时完全不成立**——而跨批是常态（一批只有 256 字节）。
>
> ★ **写检查脚本时，判据本身也要复核。**
> 本案里脚本用了一个错的标准（4 个字节时间），所以它**一直是绿的**，
> 没能拦住这个 bug。

**出处**：`uart_packet_echo.v` 的超时段；版本说明 `V39.2` / `V40`

## 案例 7 ★★ Verilog 非阻塞赋值：同一拍里"写进去"和"读出来"是两个时刻

### 发现问题

在给 UART 加"三次采样多数表决"抗噪之后，**抗噪效果反而比原来的单点采样更差**。

### 定位

看代码：

```verilog
if (bps_cnt == samp_c) samp_v[2] <= rx_i;                 // ← 下一拍才成立
if (bps_cnt == samp_c) recv_reg <= {maj(samp_v), ...};    // ← 同一拍读 = 旧值！
```

**两句话在同一个时钟沿**：
- `samp_v[2]` 在**这一拍结束时**才被写入；
- `recv_reg` 在**这一拍**读 `samp_v`，读到的是**旧的 `samp_v[2]`**（即上一位的采样）。

**结果：所谓"三次采样多数表决"实际用上了【上一位】的采样值** ——
比单点采样还糟。

### 修复

> ★ **规则：凡是"先寄存、后使用"的流水，取用点必须比写入点晚一拍。**

### 验证（关键——这类错误肉眼审不出来）

**专门写了一个逐拍仿真**：`testfiles\sim_uart_rx.py`，它**逐拍复刻**
`uart_rx.v` 的行为，第 **[1]** 节专门钉住这个不变量：

```
samp_d = samp_c + 1        ← 取用点比写入点晚一拍
```

### 教训

> ★★ **非阻塞赋值的"同一拍写读 = 旧值"是 Verilog 最容易犯、
> 又最难靠肉眼发现的错误。**
> 这类 bug **每个分支单看都对**，必须靠**逐拍仿真**钉住。
>
> ★ 工程纪律：**改 UART / 采样类逻辑后，务必重跑 `sim_uart_rx.py`。**

**出处**：`uart_rx.v`；`testfiles\sim_uart_rx.py`（23 项）

## 案例 8 ★★ 「上一笔 done 了就发下一笔」必须带 `!done` 条件

### 发现问题

**实机现象：36 颗 LED「全部亮了一瞬间就灭了」。**

更准确地说：点亮的那一瞬间能看见，但**立刻就全灭**。

### 定位

状态机里写的是：

```verilog
if (!busy && !go) begin
    if (step <= STEP_LAST) go <= 1'b1;
```

**少了 `!done` 条件。** 握手时序是这样的：

```
从机的 done 脉冲和 busy <= 0 是【同一拍】生效的
  → done 那一拍 busy 已经是 0
而 step 要到【那一拍结束】才 +1
  → done 那一拍拿【旧的 step】又排了一笔 go
  → 下一拍 step 已经 +1，那笔 go 就发出去了
  → 一共发了 N+1 笔
```

**那多出来的一笔落在哪里**：LED 驱动的寄存器解码器最后一个 `else` 分支，
而那里写的是

```verilog
reg_a = 8'h00;  dat = 8'h00;   // ← SSD=0 软件关断！
```

**于是**：

| 笔号 | 内容 | 结果 |
|---|---|---|
| 第 76 笔 | 写 `SSD=1` | **点亮** |
| 第 77 笔（多发的） | 写 `SSD=0` | **关断** |

中间只隔一笔事务 ≈ **290 µs** —— 人眼看到的就是"亮了一瞬间就灭了"。

### 修复

```verilog
if (!busy && !go && !done) begin    // ← 加上 !done
```

并把越界的兜底分支改成**安全值**（`SSD=1`，而不是关断）。

### 验证（逐拍仿真 + 两条断言）

写了 `testfiles\sim_led_guide.py`（**50 项**），里面有两条**专门钉住这个不变量**的断言：

| 断言 | 检查什么 |
|---|---|
| 「**恰好 N 笔**」 | 初始化必须正好发 76 笔事务，不多不少 |
| 「**`go` 与 `done` 从不同拍**」 | 发起条件里必须含 `!done` |

> ★ **这类 bug 肉眼审不出来**（每个分支单看都对），
> **必须靠逐拍仿真钉住。**

### 教训（写任何"逐笔推进"的状态机都照这个查）

> ★★ **三条判据**：
> ① 发起条件里**有没有 `!done`**？
> ② **`done` 那一拍 `busy` 到底是 0 还是 1**？（去从机的 `S_DONE` 看：
>    它和 `busy <= 0` 是同时赋值的，所以那一拍**已经是 0**）
> ③ **越界的 step 落到哪个分支**？那个分支**绝不能**做"关掉 / 清空"这类动作
>    —— 要写成**安全值**。

**出处**：`led_guide.v:243-253`（注释里写明了这条）；
`testfiles\sim_led_guide.py`

## 案例 9 ★★★ 症状在屏幕上，根因在"一个没被作废的标记"

> ★ 本案特别之处：**第一次修复打偏了触发点，而且就算触发点对了，
> 修法本身也带一个没人算过的隐藏前提。** 两处都是靠"把数算出来"抓到的，
> 不是靠盯代码看出来的。适合回答"你怎么保证改对了"。

### 发现问题

用户实测报的原话：

> 「切到李萨如图形后再切回来，**频谱就被清空了，但是那些音还在发出**！」

关键线索是**后半句**：声音完全正常。也就是说
**音频链路一个比特都没错，坏掉的只是"屏幕上该不该重画"这个判断**。

### 定位：缓存有，失效没有

频谱画面由 **60 根柱子**组成，每根柱子对应一个琴键的电平。为了不做无谓的
重画，代码里有一份 **"每列上次画完的高度"缓存**：

```verilog
reg [8:0] bar_state [0:59];                       // 每列上次画完的 {高度>>1, 颜色类别}
wire bar_dirty = (bar_state[col] != tgt_q);       // 和当前高度不一样才重画
```

**逐列增量重画**是必须的：重画一列要发 **1091 字节**（11 字节窗口命令 +
180 像素 × 3 像素宽 × 2 字节色），SPI 6.25 MHz 下一列就是 **1.40 ms**
—— 60 列全画一轮 **83.8 ms**。不这么做的话，包络每掉 1 个 count 都要重画一列，
LCD 根本追不上。

**病灶**：切显示模式时，代码把主区**清了屏**（`S_CLEAR_BAR`），
但**没有动 `bar_state`**。切回来时每列算出的高度和缓存里记录的**一模一样**
→ `bar_dirty` 恒为 0 → **一根柱子都不会重画** → 屏幕一片空白。

> ★★ 这类 bug 的通用症状：**"界面不对，但功能全正常"。**
> 丢的不是数据，是"该刷新了"这个标记。

### 第一次修复（错的，而且错了两层）

第一版修法看起来很合理：切模式时置一个"强制重画"标志，过 0.35 s 清掉。

```verilog
reg bar_force;                        // 切模式置 1
wire bar_dirty = (bar_state[col] != tgt_q) || bar_force;   // 或上它
// 25'd17_500_000 拍 = 0.35s 后由计数器清掉
```

**两层错，都是靠"把数算出来"才发现的：**

**① 触发点打偏。** 这个标志只加在了 `S_BAR_WIN`（频谱绘制状态）里，
而那里的判据是 `wave_mode != wave_mode_d`。问题是：

| 显示档 | `wave_mode` | `liss_on` |
|---|---|---|
| 频谱 | 0 | 0 |
| 波形 | 1 | 0 |
| 李萨如（3 档） | **0** | 1 |

**频谱和 3 档李萨如的 `wave_mode` 全都是 0** —— 用户报的那条路
（频谱 ↔ 李萨如）**永远进不了那个分支**。
更关键的是：频谱显示时状态机在 `S_BAR_WIN ↔ S_BAR_DATA` 里**自循环**，
**根本不回 `S_IDLE_WAIT`**，所以"进出李萨如"这个切换只能在
`S_IDLE_WAIT` 里被发现 —— 而那里**没有置标志**。
把状态机的三个切换检测点画出来之后，结论很清楚：

```
① S_BAR_WIN   : wave_mode 变了        （频谱 ↔ 波形）
② S_IDLE_WAIT : 进出李萨如            （★ 用户报的就是这一条）
③ S_IDLE_WAIT : wave_mode 变了        （波形 → 频谱）
```

**② 窗口长度是个没人算过的隐藏前提。** 标志必须在
"清屏 + 重画一整轮"结束之前一直有效。实测：

| 动作 | 耗时（按 RTL 常数算） |
|---|---|
| 清主区（`S_CLEAR_BAR`，57600 像素） | **147.5 ms** |
| 全屏清（`S_CLEAR_WIN`，76800 像素） | **196.6 ms** |
| 重画 60 列一整轮 | **83.8 ms** |
| **合计（退出李萨如那条路）** | **280.4 ms** |

而那个常量写的是 `24'd17_500_000` —— **24 位最多装到 16,777,215，装不下**，
被工具**静默截断**成了 **722,784 拍 = 14.5 ms**：

```
WARN (EX3792) : Literal value 'd17500000 truncated to fit in 24 bits
```

**14.5 ms 连清屏的 147.5 ms 都盖不住** —— 标志会在清屏中途就掉，
**一列都不会重画，用户报的现象原样复现**。

> ★★ 顺带一提：本工程**已经栽过同一个坑**。`top.v` 里留着一行血泪注释 ——
> 有人把 `FRAME_BITS` 写成 `6'd64`（64 需要 7 位）→ 截断成 0 →
> `FRAME_DIV = 0` → 除零 → **DDS/ROM/包络/混音整块被优化掉**，
> 寄存器从 4319 掉到 124，烧进去**完全没声音**。
> 两次都是"综合不报错、只有一行 WARN"。

### 最终修复：不作废标志，作废缓存

换成**直接把缓存写成哨兵值**：

```verilog
// 切模式时（三个触发点各一处）
for (dm_i = 0; dm_i < 60; dm_i = dm_i + 1) bar_state[dm_i] <= 9'h1FF;
```

`9'h1FF = 511` 是 `tgt_q` **永远取不到**的值（`col_target` 最大只有 **179**，
因为 `col_h_pix ≤ 179`）。于是：

| | 第一版（标志 + 计时器） | 最终版（作废缓存） |
|---|---|---|
| `bar_dirty` 表达式 | 被改（`\|\| bar_force`） | **逐字回到原样** |
| 需要假设窗口多长 | **需要**（而且算错过） | **不需要** |
| 反复快按按钮 3 | 标志**不会重新计时** → 可能漏 | 每次都重新作废 → **不漏** |
| 强制什么时候结束 | 计时到点（可能太早/太晚） | **每列画完自动消耗掉** |
| 代价 | 1 个标志 + 26 位计数器 | Logic **+96**、Register **+34** |

> ★★ **这一条是本案最值钱的地方**：
> **"置一个标志 + 计时清掉"这种修法，永远隐含一个"窗口必须比 X 长"的前提，
> 而 X 往往是能算出来的 —— 算出来就会发现余量没想象中那么宽。**
> 而"把缓存作废"是**自终止**的：标脏了多少列，就画完多少列，与时间无关。
> 能用"状态自然消耗"表达的修复，不要用"计时器"表达。

### 验证

新增 `testfiles\sim_bar_cache.py`（**36 项**）——它的重点不是"判据对不对"，
而是**把耗时算出来 + 把三种修法放在一起对照**：

```
每字节 64 拍；重画一列 1.40 ms；60 列一轮 83.8 ms
清主区 147.5 ms；全屏清 196.6 ms
★★ 用户报的那条路：第一版 0 列重画 -> 最终版 60 列全重画
★★ 截断版：同样 0 列（bug 原样复现）
★  作废后的第一轮 60 列全画；第二轮自动回到 0 列（哨兵值被逐列消耗）
★  稳态高度没变时一列都不重画（和 V47.2 逐位相同）
```

另外把两条判据做成了**永久契约**（`check_rtl_contract.py`）：

- **第 [10] 节**：扫全工程 `.v` 里**所有**"定宽字面量装不下它的值"的地方
  （必须先剥注释 —— `top.v` 那条反面教材 `6'd64` 就写在注释里）。
  ★ 这条扫描现在**全工程零命中**，以后谁写出第三个会被立刻抓住。
- **第 [11] 节**：`bar_dirty` 里不许有强制项、作废点必须**恰好三处**、
  而且**"进出李萨如"那一处必须在**（就是用户报的那条路）。

### 教训（三条可迁移的）

> ① **"缓存没失效"的症状永远是"界面不对但功能正常"。**
>    看到"显示错了但声音/数据都对"，第一反应就该是"某个缓存没清/没作废"。
> ② **修复要先算清"多大窗口才够"，再决定用什么机制。**
>    本案算出来是 280 ms —— 于是任何"拍脑袋 0.35s"的方案都必须复核，
>    而"作废缓存"根本不需要这个数。
> ③ **静默截断（`EX3792`）只给 WARN，不给 ERROR。**
>    本工程栽了两次，现在有全工程扫描兜底 ——
>    **凡是"N 位常量"，先算 2^N 够不够。**

**出处**：`lcd_master.v`（`bar_state` 声明处那一大段注释 + 三个作废点）；
`testfiles\sim_bar_cache.py`；`check_rtl_contract.py` 第 [10]/[11] 节

## 案例 10 ★★ 「满量程」不等于「看着亮」——一个被自检抓回来的错误决定

### 发现问题

用户反馈（原话）：

> 「把黑键对应的谱线的颜色改的**明亮一点**，现在的**太暗了**，
> 基本**和背景融为一体**了。」

背景：频谱那一屏用颜色区分黑键/白键（`col_is_blk` 判断"每八度的第 2/4/7/9/11 列"）。
白键是亮红 `16'hF800`；黑键原来写的是 `16'h7800` —— 也就是
**"同一个红色系、亮度减半"**（R = 15/31），在黑背景上确实几乎看不出来。

### 第一次修复（错的：我选了纯蓝，理由是"满亮度"）

第一版改成 **`16'h001F`（纯蓝）**，注释里写的理由是：

> "现在改成【换色调、不降亮度】：白键亮红(F800) / 黑键亮蓝(001F)，
> 两个都是满亮度，红蓝对比在 320×240 的小屏上一眼就分得开。"

**这句话是错的。** 红色通道和蓝色通道在"满量程"时对**人眼**的贡献完全不同：

| 颜色 | RGB565 | 感知亮度（≈ 0.30·R + 0.59·G + 0.11·B） |
|---|---|---|
| 原来的黑键色 | `0x7800`（R=15） | **0.145** |
| 我第一版选的"亮蓝" | `0x001F`（B=31） | **0.11** ← **比原来还暗** |
| 最终选的亮青 | `0x07FF`（G=63,B=31） | **0.70**（约旧色的 **4.8 倍**） |

也就是说：**那一版正好和用户的要求相反 —— 用户要"亮一点"，我给了一个更暗的。**

### 定位：判据只写了"看着够亮"，没写成可复算的数

这个错误**没有靠肉眼发现**（我手里没有那块屏），是被**自检脚本**抓住的：
我给"黑键颜色"写契约检查时，顺手把"感知亮度"按
`0.30/0.59/0.11` 的三通道权重算了一遍，要求 **≥ 0.55** ——
结果 `0x001F` 算出来只有 **0.11**，当场就红了。

### 修复

改成 **`16'h07FF`（亮青）**：感知亮度 **0.70**，并且和这一屏其余四种颜色
**都不撞色**（白键红 `0xF800` / 2 次谐波黄 `0xFFE0` / 背景黑 `0x0000` /
边框暗灰 `0x4208`）。改动只有**一个 `localparam`**，谱线/网格/背景一个像素没动，
备选色写在它旁边那几行注释里（白 `0xFFFF` / 品红 `0xF81F` / 橙 `0xFD20` /
更亮的红 `0xC800`）。

### 验证

判据写进 `check_rtl_contract.py` 第 **[12]** 节，**把用户的诉求本身变成判据**：

- 新色的感知亮度 **≥ 0.55**；
- ★★ 新色必须是旧色（`0x7800`，0.145）的 **2 倍以上** —— 也就是"**改亮**"
  这一条被固化下来，以后谁再改成个更暗的颜色会立刻红；
- 新色不许和本屏其余四种颜色撞色，也不许等于背景色。

### 教训（三条可迁移的）

> ① **"满量程"是电学量，"看着亮"是感知量，两者不是一回事。**
>    人眼对蓝最不敏感（权重只有红的 1/3、绿的 1/5）——
>    **凡是"亮度/对比度/可读性"的改动，先按感知权重算个可复算的数，
>    再动手选色**，不要凭"这个名字听起来很亮"。
> ② **用户的形容词要翻译成判据。** 用户说的是"改明亮一点"，
>    我该写下来的判据是"**亮度必须比原来高**"，而不是"我觉得这个够亮"。
>    本案的最后一条判据（≥ 旧色 2 倍）正是这么来的。
> ③ **没有屏幕的人更要靠算术把关。** 这次错误是自检脚本抓的 ——
>    证明"把主观要求写成可复算判据"这件事本身就是一种验证手段。

**出处**：`lcd_master.v`（`COLOR_KEY_BK` 定义处那一段注释，含这次弯路的完整记录）；
`check_rtl_contract.py` 第 [12] 节

## 案例 11 ★★★ 看门狗：「没活干」和「卡死」在状态编码上是同一种形状

### 发现问题

用户实测报告（原话）：

> 「LCD **不会卡死了**，但是**延音时谱线会被刷掉**，即延音没办法保持谱线，
> **这个看门狗把延音状态当卡死给刷掉了**。」

背景：上一版（V47.2）为了治"LCD 偶尔卡死不动"，加了一个看门狗：
**状态机连续 0.8 秒不推进就整台重新初始化**。它确实治好了卡死 ——
但用户发现它**误伤了正常画面**。

### 定位：两层根因，缺一层都解释不通

**① 判据漏了一种"合法的原地踏步"。**
频谱这一屏的状态机是 `S_BAR_WIN <-> S_BAR_DATA` 自循环的，
而"这一列要不要重画"由 `bar_dirty` 决定：

| 情况 | 状态机行为 | 看门狗怎么看 |
|---|---|---|
| 有列脏（高度在变） | 每画完一列都在两个状态间跳 | 状态一直在变 → 正常 |
| **没有列脏（高度恒定）** | `S_BAR_WIN` 的 phase0 只做「`play_idx` 自增 + `phase <= 0`」，**状态一个时钟都不变** | **误判成卡死** |

而"延音"正是"**高度恒定不变**"的典型场景 —— 所以用户只在延音时看见它。

逐拍算过（见验证段）：**每列 3 拍 = 6 时钟，一圈 60 列 = 360 时钟 = 7.2 µs**，
于是**第 111,112 圈、正好 0.800 s** 就攒满阈值 ——
也就是说静态画面**每 0.8 秒就被整台重来一次**（`S_POWER_ON` → `S_INIT` → 全屏清）。

**② 恢复路径不作废谱线缓存。**
全屏清完之后，`bar_state[]` 里存的还是清屏前的高度，
**和当前目标高度一模一样** → `bar_dirty` 恒 0 → **一列都不重画** → 屏幕空在那里。
这就是"谱线被刷掉"。
★ 这个缓存失效点，上一版（V48）已经为"切显示模式"补过**三个**作废点，
**这次是第四个场景** —— 同一个不变量又漏了一处。

### 修复（两条一起做，缺一条都不行）

1. **把"谱线在空转"也算成活着**：
   ```verilog
   if ((state != lcd_state_d) || (play_idx[5:0] != lcd_play_d))
       lcd_wd_cnt <= 26'd0;          // state 动了【或】谱线列号动了 -> 都算活着
   ```
   空转一圈只要 7.2 µs，"列号"必然一直在动，计数器再也攒不到 0.8 s；
   而**真卡死时 `play_idx` 是冻住的，照样会触发** —— 看门狗的本职没有丢。
2. **看门狗一旦触发，把谱线缓存整片作废**（60 列各重画一次）。

### 修复过程中又踩了一个坑：**"照抄一遍"让它多吃了 1023 个 LUT**

第 2 条最直觉的写法是照抄 V48 那三处"把 `bar_state` 整片写 `9'h1FF`"。
**实测 Logic 从 46941 涨到 47988（+1047，79% → 81%）**；
翻综合报告，涨的**全在 `u_lcd`**：`Lut 3000 → 4023`，其它模块一个数没变。

| 做法 | 代价 | 为什么 |
|---|---|---|
| 再写一遍 9 位哨兵 | **+1023 LUT** | `bar_state` 是 **60 列 × 9 位 = 540 位**的数组，**再加一个写入源 = 每一位多一级选择**（6 选 1 变 7 选 1） |
| **把"作废"拆成每列 1 位**（`bar_bad`） | **~60 LUT** | 写入源只加在 **60 位**上；语义完全一样（**画完那一列就地清掉**，逐列自消耗，不需要任何窗口） |

> ★★ 关键区分：`bar_bad` **不是** V48 明确否掉的 `bar_force` 那种写法 ——
> `bar_force` 是**一个**标志位 **+ 一个计时器**清它，"窗口要多长"这个假设正是当初
> 翻车的地方；`bar_bad` 是**每列一位**，由**画完那一列的同一条语句**清掉。
> 判据里专门钉住了这两条：`bar_dirty` 里**只允许**出现 `bar_bad` 这一项，
> 且 **`force` 字样不许出现**。
>
> ★ 一般化的教训：**"加一个写入源"的代价 = 数组总位数，不是"改了一个地方"。**
> 往宽数组里加一条通路之前，先算 `位数 × 选择级数` —— 这次是 540 位，
> 一眼就该知道便宜不了。

### 验证（逐拍对照仿真，`testfiles/sim_lcd_watchdog.py`，21 项）

| 判据 | 结果 |
|---|---|
| 逐拍数出"每列 3 拍 / 一圈 360 时钟"（常数不手抄，从 RTL 抠） | ✅ 7.2 µs |
| **旧判据在静态画面下必然误触发** | ✅ 第 111,112 圈 = **0.800 s** |
| **新判据在 20000 圈里一次都不触发** | ✅ 最大累计仅 **6 拍**（余量 **666 万倍**） |
| **真卡死仍然触发**（阈值语义没放宽） | ✅ 仍是 **0.800 s**；差一拍不触发 |
| 恢复后重画：**不作废 → 0 列**（复现 bug） | ✅ 0 列 |
| 恢复后重画：**作废 → 60 列** | ✅ 60 列，且缓存写回真实高度 |
| 反面例子：高度真在变时，不作废也会重画 60 列 | ✅ 解释了"为什么偏偏延音才看得见" |
| 施工代价：**照抄哨兵 vs 拆出一位** | ✅ **+1023 LUT → +约 60 LUT**（综合报告实测） |

★ 另外把 `sim_bar_cache.py` 里那句"作废点必须是**三处**"改成**四处**，
并新增一条"作废点④必须在看门狗分支里"——**不变量变了，判据必须跟着变**。

### 教训（三条可迁移的）

> ① **看门狗判的必须是"有没有在干活"，不能只看状态编码。**
>    "在等一个永远不会来的事件"（真卡死）和"本来就没活干"（空转）
>    **在状态这一维上完全同形** —— 必须找一个"真干活时一定会变"的伴生量陪着看。
>    这里的伴生量就是谱线列号。
> ② **"清屏 / 重开一屏"的地方都要作废显示缓存。**
>    这个不变量已经栽过两次（V48 切模式、V48.4 看门狗恢复）——
>    它不是"某个 bug"，而是**一条该被当成清单逐处对照的规则**。
> ③ **防住 A 可能弄坏 B —— 修完看门狗一定要回归它保护的界面本身。**
>    这次的报告正是这种形状："卡死确实治好了，但画面内容丢了"。
>    用户那句"**XX 好了但 YY 坏了**"，本身就是最有价值的定位线索。
> ④ **"加一条通路"的代价 = 数组总位数，不是"改了一个地方"。**
>    给 540 位的数组再加一个写入源，代价就是 540 个选择器（实测 +1023 LUT）；
>    把标志位拆出来单独放一位，同样的语义只要约 60 个。
>    **写之前先算一笔"位数 × 选择级数"的账。**

## 附：三条贯穿全工程的"省资源"原则

这 11 个案例之外，本工程还有三条反复起作用的资源优化原则。
它们解释了为什么 Logic 只有 79%、DSP 只有 48%：

### 原则一：把"运行时常量"变成"编译期常数"

| 改动 | 代价 |
|---|---|
| 滑音目标、KS 弦长用 `localparam` **常数** | 改成运行时常量会各烧一套 32 位加减器：**实测 24 键 +2300 ALU** |

> 常数化之后，`dif × FR` 里的 `FR` 也是常数，
> **乘法可以展开成移位相加**（6 级 ALU），不占 DSP。一条优化省两处。

### 原则二：小常数乘法一律换移位相加

| 位置 | 原写法 | 换掉之后 |
|---|---|---|
| KS 插值 `dif × FR` | 36 个 `MULT12X12` | **DSP 从 53.5 → 若改回 `*` 则 104.5**（89%，太满） |
| KS 起振噪声 `nz × vel` | 36 个 `MULT12X12`（占 DSP 61%） | 4 级移位相加 |

> **本设计的资源取舍是明确的**：**DSP 稀缺（118 个），LUT 相对富裕**。
> 小常数乘法用 LUT 换 DSP 是划算的。

### 原则三：避免"变量下标写数组"

```verilog
inc[tr_gi] <= ...      // ✗ 综合器生成寄存器堆 + 36 路 36:1 选择器，多烧几千 LUT
```

**要用 `generate` 展开成固定下标的独立寄存器。**

> 同类教训还有：**两个 `always` 块驱动同一个 `reg`** 会直接报 `EX2000`；
> 加寄存器前先想清楚"**谁拥有它**"（`fx_req`、`fx_tgl`、`oct_cur` 都踩过）。

## 一句话总结

> 这 11 个案例的共同点是：**每一个瓶颈的真实病因，都和最初的猜测不一样**——
> `CLKOUT1` 的病不在 UART 在 LCD；`BSRAM` 推断失败不在写语句在地址形状；
> 蓝牙播放错乱不在协议在超时阈值的量级；
> "黑键太暗"的第一版修复不在"选了哪个颜色"，而在**我把"满量程"当成了"看着亮"**；
> "LCD 卡死"的看门狗治好了卡死，却把**"没活干"当成了"卡死"**。
>
> **本工程真正的技术含量不在"实现了什么功能"，
> 而在"有一套能定位到真实病因的方法"**：
> 读时序报告的路径明细、做单变量实验、写逐拍仿真钉住不变量、
> 把主观要求翻译成可复算的判据、
> 以及最重要的——**不靠猜**。
